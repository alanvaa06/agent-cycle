# Pydantic AI - build binding

Facts below cite the same sources as the card (`skills/design/references/stacks/pydantic-ai.md`) and the research file `docs/superpowers/research/2026-10-07-stack-catalog/pydantic-ai.md`; a URL is repeated where a rule depends on it. Source-code citations are the files at the tag v2.54.0 under `https://raw.githubusercontent.com/pydantic/pydantic-ai/v2.54.0/pydantic_ai_slim/pydantic_ai/` (named by path below). This binding replaces the pre-V2 mapping: V1 names (`MCPServerStdio`, `Agent.to_a2a()`, `Usage`, `Agent(instrument=...)`) do not exist in V2 (https://pydantic.dev/docs/ai/overview/migration/index.md ). Statements marked inference are the binding's own reasoning; statements marked unverified are not confirmed by a page or the source, and a spike below confirms them on the pinned version.

Shape: one `Agent` built by `build_agent(model, tools, caps)` in `src/agent/`, with `output_type=[str, DeferredToolRequests]` (required so a paused run can return the pending approvals: https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/ ). `tools` is a list of toolsets already wrapped by the tier gate (see HITL gate); `caps` carries the spec's two per-turn limits. The agent gets one `Hooks` capability holding the requested-tool-call counter (see Caps; `from pydantic_ai.capabilities import Hooks`, https://pydantic.dev/docs/ai/core-concepts/hooks/index.md ), and the worker passes a per-turn `TurnState` object (the requested-tool-call counter and the turn id) as `deps`. Pydantic AI has no session store: the loop is its own loop, so the conversation history lives in a repository table behind the repository interface, and `src/agent/` never imports DB drivers, boto3 or Firestore clients; the adapter in `adapters/<target>/` implements `load_history(session_id)`, `commit_turn(...)` (the single post-run transaction, see HITL gate step 4) and the pending-approval and turn-state reads, and is injected. Dedupe and the spec's data schemas stay in their own repository tables. This replaces a hand-written model-tool loop and any V1 `Agent`/`MCPServer*` wiring.

## Sessions and state
- Own tables, all behind the repository interface (the core only serializes history and says the schema is yours: https://pydantic.dev/docs/ai/core-concepts/persistence/ ):
  - `messages(session_id, seq, message_json, created_at)`, one row per message, written with `ModelMessagesTypeAdapter` (`to_jsonable_python` / `validate_python`, or `to_json` / `validate_json`; https://pydantic.dev/docs/ai/core-concepts/message-history/ ). Write only the rows that changed (the store rule under Caps): the persistence page recommends appending `new_messages()` so each write stays proportional to the turn, and the diff keeps that property because only the tail differs. Older histories deserialize without migration when message parts are added (persistence page).
  - `pending_approvals(approval_id, session_id, tool_call_ids, requested_at, elapsed_s, usage_json, tool_calls_requested, resume_started)`: every pause writes a NEW row with a fresh UUID `approval_id` (never the session id; at most one live row per session, enforced by a unique index) when a run returns `DeferredToolRequests` and completes without an exception or timeout (`requested_at` = now, taken just before the prompt is sent; a wall-clock abort with a gated call pending writes no row). Any run started from a row deletes it in the SAME transaction that stores the run's messages, unless the run ended in a NEW pause, which writes a fresh row (new `approval_id`) in that transaction; within the transaction, delete the old row before inserting the new one (the unique index is per session). `elapsed_s` is the wall-clock time the turn has used so far (see Caps). `usage_json` is the `RunUsage` of the turn so far (the persistence page: `RunUsage` lives outside the messages; store it and hand it back with `usage=`). `tool_calls_requested` is the requested-tool-call counter (see Caps).
  - `turns(session_id, turn_id, status, started_at)`: `status` is `running` from turn start (written after the repair, before the run) and is overwritten with the outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`, `error`; names follow the spec) on every exit. A turn that ended in a pause is `awaiting_approval`, and a resume sets it back to `running` in the same committed write that sets `resume_started`. The next turn's repair reads the latest row (see Caps): `running` or no row means a crash, and `awaiting_approval` means nothing to repair (the pending row owns it).
  - Serialize `RunUsage` with the same pydantic JSON path (inference: it is a dataclass; the usage spike round-trips it).
- Postgres (incl. Supabase): the `messages` table has primary key `(session_id, seq)`; `commit_turn` inserts the turn's rows in one transaction and fails on a duplicate `seq`, which turns a second writer into an error instead of a forked history. The core gives no per-session locking guidance, so the guarantee is the queue (inference). Use the direct connection or the Supavisor session mode (port 5432); never the transaction pooler (port 6543), which does not support prepared statements (the driver may use them, inference). Source: https://supabase.com/docs/guides/database/connecting-to-postgres . Put the tables in a schema not exposed through the Data API (for example `agent_state`) and enable RLS on them (the docs say to enable RLS on every table in an exposed schema; that an unexposed schema is not reachable is implied, not stated): https://supabase.com/docs/guides/database/postgres/row-level-security . The Free plan pauses projects after 1 week of inactivity, so it is not for production: https://supabase.com/pricing
- DynamoDB: one item per message, partition key `session_id`, sort key `seq`, written with a condition that the key does not exist yet (inference); `pending_approvals` and `turns` are items keyed by session. Item-size limits apply to a message with large tool output: check them against the target table in the store spike (not verified here: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html does not state the item limit).
- Firestore: `sessions/{session_id}/messages/{seq}` (a subcollection per session, one document per message, inference); a document is limited to 1 MiB (https://firebase.google.com/docs/firestore/quotas ), so a very large tool result needs trimming before it is stored.
- Queue ordering key = the session key, so one turn per session holds even when an approver is a different sender. Ingress resolves an approver's reply to the pending session's key before enqueueing.
- Schema setup (tables, indexes) runs once as a named one-shot migration job (`agent-migrate`: compose service / ECS task / Cloud Run job), never from the worker and never per request.
- Durable-execution engines (Temporal, DBOS, Prefect, Restate, AWS Lambda durable functions and others) are NOT the session store: they keep one run alive and "do not store your chat threads" (https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/ ). The binding uses none; the approval pause is application-level (HITL gate).
- Spikes (each runs at build-guide Step 4). A failed store spike STOPS and raises a re-entry on the design's sessions seam, never a silent store swap; the other spikes state their own failure path:
  - Store (store spike; pass test: a history containing a user prompt, a tool call, a tool return and a deferred pause is appended, reloaded in `seq` order and `ModelMessagesTypeAdapter.validate_*` equals the original; a duplicate `seq` insert is rejected). Supabase adds: the tables exist in `agent_state` and not in `public`, RLS is enabled, and the round trip works as the app's DB role. DynamoDB adds: the conditional put rejects a duplicate key. Firestore adds: a large message round trip stays under the document limit. Replace path: write rows 0..n, then replace from seq k with different content and a shorter and a longer tail in one transaction; the reload equals the new list and no old row remains (Postgres: delete `seq >= k` then insert; DynamoDB: one transactional write; Firestore: one batched write).
  - Usage round trip (binding spike; pass test: a `RunUsage` with `requests` and `tool_calls` above zero survives the JSON round trip, and passing it as `usage=` makes the next run continue from those counts; failure path: binding defect (serializer): STOP and report (build-guide Step 4)).
  - Pending approval and stored shape (binding spike; pass test: a gated call ends the run with `DeferredToolRequests` whose `approvals` carry the call ids; a new worker process reads the `pending_approvals` row and resumes; failure path: binding defect: STOP and report (build-guide Step 4), not the sessions seam). It also RECORDS the shape of the history at the pause: does it end with the `ModelResponse` holding the calls, or with a `ModelRequest` of sibling returns (non-gated calls of the same response that already ran)? Record the answer in `build.md`; it settles the store rule (Caps, Persisting) and the notice-row rule (Caps, repair).
  - Resume (binding spike; pass tests under HITL gate, including the stored-rows check).

## HITL gate
- Recommended placement: ONE tier gate wrapped around the toolsets with `toolset.approval_required(fn)` (https://pydantic.dev/docs/ai/tools-toolsets/toolsets/index.md ), where `fn(ctx, tool_def, args)` looks up `tool_def.name` in the spec's tier table. It covers function toolsets and MCP toolsets in one place (the page says the method is available "on any toolset"; the MCP case is inference and the MCP spike confirms it). A tool missing from the tier table is treated as destructive (fail closed). Gated calls are not executed before approval: a `requires_approval` call is collected as deferred and not run (`_tool_execution.py`). Do not gate by raising `ApprovalRequired` inside a tool body: the body runs again on the resumed run and code before the raise would repeat (inference); keep the tier gate as the only gate.
- Tier mapping from the spec's tool contracts: destructive -> `fn` returns True every time, never cached, decisions approve or deny only (the worker rejects `edit` for a destructive tool); reversible -> per design policy (always True, or a predicate over `args`); safe -> False.
- Worker sequence:
  1. Dequeue the message for the session (ordering key = session key). If the ingress dedupe record of the message (keyed by the channel message id) has `processed_at` set, do not re-run it: re-send the stored reply if the send may not have happened, then ack (inference; ingress dedupe alone only catches channel retries, this closes queue redelivery after a worker crash).
  2. Read the `pending_approvals` row for the session (own repository; there is no framework state to inspect) and capture `prior` = its `resume_started` (G8).
  2a. If an approval is pending, check its expiry now: when it is older than the spec's TTL, the worker does not resume the run. It builds the denial notices for the pending calls (see Deny below, marker `EXPIRED:`) and commits them through `commit_turn` (notices, delete the row, turn status `hitl_expired`), records the outcome `hitl_expired`, sends the spec's expiry notice only if the spec defines one (no model reply from this step), then handles the dequeued message as a new turn (inference). The expiry commit does NOT set the dedupe record's `processed_at`; only the final post-run commit of the turn that handles the message sets it. The row's `requested_at` is the time the worker sent the approval prompt.
  3. If an approval is pending and not expired: parse the message (or the approver's reply) into a decision (results builder below) and RESUME; right before a resume that can run tools (approve, edit, deny-and-continue), commit `resume_started` = true on the `pending_approvals` row together with the turn status `running` (one write; a resume may run tools and then crash), and a deny-ends-turn path never sets it. Otherwise start a NEW turn: run the turn-start repair (see Caps), then write the turn status `running`. Both use ONE canonical call (parameters: https://pydantic.dev/docs/ai/api/pydantic-ai/agent/ ):
     ```python
     run_id = new_uuid()                       # fresh for every call
     token = CancellationToken()               # fresh for every call (single-use)
     remaining = WALL_CLOCK - elapsed_s        # new turn: elapsed_s = 0; resume: the row's elapsed_s
     timer = asyncio.get_running_loop().call_later(remaining, token.cancel)  # fresh timer for every call
     try:
         async with asyncio.timeout(remaining + GRACE):  # outer backstop (see Caps)
             with capture_run_messages() as captured:    # its own context for every call
                 result = await agent.run(
                     prompt,                           # new turn: the user text; resume: None
                     message_history=history,          # the stored history
                     deferred_tool_results=results,    # resume only; None for a new turn
                     usage=usage,                      # new turn: RunUsage(); resume: from the row
                     usage_limits=UsageLimits(request_limit=STEP_CAP),
                     deps=TurnState(tool_calls_requested=n, turn_id=turn_id, approval_id=aid),  # new turn: 0 and None; resume: the row's values
                     run_id=run_id,
                     cancellation_token=token,         # cancelled by the timer above
                 )
     finally:
         timer.cancel()
     ```
     The prompt is optional on a resume and the follow-up is a separate run with its own `run_id` (https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/ ); passing the stored `usage` and counter is what keeps both caps per turn across the pause.
  4. Post-run, in this order (commit order): (a) ONE transaction through `commit_turn`: store the run's messages (Caps, Persisting); write a NEW `pending_approvals` row (fresh UUID `approval_id`, `requested_at` = now, `elapsed_s`, `usage_json`, counter) when the run returned `DeferredToolRequests` and completed without an exception or timeout, and in every case delete the row the run started from, in the same transaction that stores the run's messages (a resume that ends in a new pause is thereby replaced by the new row); set the turn status to its outcome (`awaiting_approval` when the run ended in a pause); set `processed_at`, the outcome and the reply text on the ingress dedupe record of the dequeued message. (b) Send the approval prompt or the reply. (c) Ack the queue message. A crash between (a) and (b) redelivers the message: its dedupe record has `processed_at` set, so step 1 re-sends the stored reply (if the send may not have happened) and acks; without that record an approver's decision would be read as a new user message once the pending row is gone (inference).
- Decision value. The spec's three outcomes map to `DeferredToolResults.approvals[tool_call_id]` (https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/ ), one entry per call in `DeferredToolRequests.approvals`; the resume fails unless every deferred call has a result (`_tool_execution.py`):
  - approve -> `ToolApproved()` (or `True`)
  - deny -> see Deny below
  - edit -> `ToolApproved(override_args={...})`; keep edits conservative, because large changes may make the model re-plan.
  - Reply covering several gated calls (design choice, inference): one approve or deny reply applies to every pending approval, `edit` is accepted only when exactly one approval is pending, and the worker's single results builder produces the whole `DeferredToolResults`. The eval runner uses the same builder.
  - `DeferredToolRequests.calls` (external execution) must be empty: the binding uses neither `CallDeferred` nor external tools; a non-empty list is a defect, fail the turn.
- If a message for a pending session does not parse as a decision: keep the approval pending and reply with the spec's pending-approval prompt (or deny if the spec says so). Expiry is evaluated when the next message for that session is dequeued (step 2a; intended; a sweep is optional).
- Deny.
  - If the spec says a deny ends the turn: no further tool executes and no further model request is made. The construct that routes to the end is the worker itself: it does NOT resume the agent.
  - It appends one `ToolReturnPart(tool_name, content="DENIED: <reason>", tool_call_id, outcome="denied", metadata={"agent_notice": "denied"})` per tool call in the last model response that has no result yet (the pending approvals, and any sibling call that did not run), as a new `ModelRequest` row (when `prior` is set, an earlier resume may have run tools, so the content is "outcome unknown - do not retry without the user" with `outcome="interrupted"` and `metadata={"agent_notice": "interrupted"}` instead of the `DENIED:` or `EXPIRED:` text), and commits through `commit_turn` (notices, delete the `pending_approvals` row, turn status `hitl_denied`). Then it sends the spec's deny reply (step 4 order) and records the outcome `hitl_denied`. `ToolReturnPart.outcome` accepts `denied` and `interrupted` (`messages.py`).
  - If the spec lets the model continue after a deny: resume as in step 3 with `ToolDenied("DENIED: <reason>")` for each denied call; the model sees the denial and continues (the docs: the message is returned to the model). State which of the two applies in `build.md`.
  - A denied call still counts as a requested tool call for the tool cap (see Caps).
  - Deny spike (binding spike; failure path: binding defect: STOP and report (build-guide Step 4)): after a deny under deny-ends-turn, a recording tool shows zero further executions, the run is not resumed, and a follow-up turn on the same session succeeds against the real provider; an ordinary deny writes "was not run", and a deny or expiry after a crashed approve-resume (kill the worker mid-resume, then dequeue the next message) writes "outcome unknown - do not retry without the user".
- Idempotency: calls in the same model response that needed no approval run in the first run and are not re-run on the resume (calls without a supplied result are skipped, `_tool_execution.py`; resume spike confirms). A crash after an approved tool ran but before the history was stored redelivers the message and runs the tool again, so every destructive tool takes the key `<approval_id>:<tool_call_id>` as its idempotency key, read from `ctx.deps.approval_id` and `ctx.tool_call_id` (`tool_call_id` is stable, read from the stored history; `approval_id` is the fresh UUID of the row written at this pause, kept until the post-run transaction, so the key is stable across redelivery; a resume that pauses again writes a new row and a new id, so keys are never reused across pauses or turns; inference). Key spike: resume -> second pause -> second approval yields distinct keys and the second tool body runs.
- Approval is not an authorization boundary against an untrusted client: only an authenticated approver identity resolved by ingress may produce a decision, and each sensitive tool also checks authorization in its own body. Source: https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/
- Eval runner: the runner feeds the fixture's approvals to the worker's turn handler as incoming decision messages (see Eval runner mapping); it never calls `agent.run` itself.
- Resume spike (binding spike; failure path: binding defect: STOP and report (build-guide Step 4)). Pass tests: for one gated call, approve runs the tool body once, deny-and-continue runs it zero times and the model receives the denial, edit runs it once with the edited args; with two gated calls in one response, `[approve, deny]` runs exactly the first; a tool absent from the tier table pauses; a safe tool never pauses; a non-gated call from the same response ran once before the pause and is not run again after the resume. Stored-rows checks: after an approve-resume the stored rows deserialize to a list equal to `result.all_messages()`, each `tool_call_id` has exactly one result, and a follow-up turn on the same session succeeds against the real provider.

## Caps
- Step cap: native `UsageLimits(request_limit=<spec step cap>)`. The check runs before each model request and raises `UsageLimitExceeded` when `usage.requests >= request_limit` (`usage.py`), so a cap of N allows N requests. Unit conversion (inference): the spec's step is one model request, used 1:1; the final answer is also a request, so a turn that spends all N requests on tool use has no request left to answer and trips the cap; record this definition in `build.md`. Set no other `UsageLimits` field, so a `UsageLimitExceeded` always means the step cap.
- Per turn: the approval pause ends the run and the resume is a new run, so the counters restart unless the stored `RunUsage` is passed back as `usage=` (https://pydantic.dev/docs/ai/core-concepts/persistence/ , https://pydantic.dev/docs/ai/api/pydantic-ai/agent/ ). The run state holds the object passed in (`agent/__init__.py`: `usage = usage or RunUsage()`, then the graph state takes it), so the worker reads the counts from that object after the run. A NEW turn starts with a fresh `RunUsage()`; a resume reuses the row's. Do not pass `usage=` across turns: that would make the cap conversation-wide (the persistence page describes that use), not per turn.
- Tool-call cap: own counter, because the native `tool_calls_limit` is not the spec's unit (sources in the card's seam table). Verified in source: it counts successful executions (`RunUsage.tool_calls`), and its pre-check adds to that count only the calls of the current batch whose kind is function or unknown (`function_indices` in `_tool_execution.py`; approval-pending calls are a different kind and join the count only when a resume runs them), so failed calls, denied calls and calls awaiting approval are not counted as requested (`_tool_execution.py`, `usage.py`). The pipeline's cap counts each tool call requested, checked before execution. Implementation: in the `Hooks` capability register `hooks.on.after_model_request` (signature `(ctx, *, request_context, response) -> ModelResponse`); it adds `len(response.tool_calls)` (every `ToolCallPart` of the response; `messages.py`) to `ctx.deps.tool_calls_requested`, raises the binding's `ToolCapExceeded` when the total exceeds `<spec tool-call cap>`, and otherwise returns `response` unchanged. The hook runs when the response arrives, before any of its tools run, so parallel calls cannot overshoot; a raised exception aborts the run and propagates to the caller of `agent.run` (https://pydantic.dev/docs/ai/core-concepts/hooks/index.md ; the cap spike confirms it for this hook). Every `ToolCallPart` counts, because the tool-surface preflight asserts the agent has no output tools (if one is ever added, exclude its name). The counter lives in `TurnState` and is stored in `pending_approvals` across a pause. The native `tool_calls_limit` is left unset: it can only trip later than the own count, so it adds nothing (inference).
- Both exits map to the spec's single failure reply and a cap outcome: `UsageLimitExceeded` -> outcome `step_cap`, `ToolCapExceeded` -> `tool_call_cap`, wall-clock -> `wall_clock`. The exception text is never sent to the user.
- Wall-clock cap: the budget is per TURN, resume time included. The worker stores the turn's elapsed seconds in `pending_approvals.elapsed_s` at each pause and gives a resume the remainder (limit minus `elapsed_s`; the wait for the approver is not counted; inference); a new turn gets the full limit. Each agent invocation gets a fresh `CancellationToken` (single-use; https://pydantic.dev/docs/ai/api/pydantic-ai/agent/ ) passed as `cancellation_token=` and cancelled by a timer at the remaining budget; the run raises `RunCancelled` carrying the completed message history (https://pydantic.dev/docs/ai/core-concepts/agent/ ). Backstop: an outer `asyncio.timeout(<remaining> + <grace>)` around the call (`asyncio.timeout` needs Python 3.11 or later and the package supports 3.10, so on 3.10 use `asyncio.wait_for`; standard-library behavior, not from the Pydantic docs) (`<grace>` is a small constant recorded in `build.md`) catches a run that ignores the token, for example a blocked tool. Its expiry surfaces as `TimeoutError` or `CancelledError`, not `RunCancelled` (`exceptions.py`), and maps to the same outcome `wall_clock`, with the messages taken from the `capture_run_messages()` list. Tool bodies need their own timeouts, since whether a running synchronous tool stops on cancel is unverified. Expiry gives the single failure reply and the outcome `wall_clock`.
- Persisting a turn (ONE store rule for every outcome: new turn or resume, success or abort): every `agent.run` call (the first run and each resume) gets its own `capture_run_messages()` context (https://pydantic.dev/docs/ai/guides/testing/index.md ; the migration page says it also captures the partial request and response of an interrupted run). After the call, diff the captured list (for a success, `result.all_messages()`) against the stored rows by position, comparing the serialized messages: rows from the first difference on are replaced and the rest appended. For a new turn the captured list starts with the stored history, so only the tail differs; for a resume the library replaces the last model response with a copy and builds a request from the tool results (`_agent_graph.py`, `_handle_deferred_tool_results`), which the diff absorbs. If the library's in-memory cleaning of the history (merging adjacent requests, `messages.py`) makes the captured prefix differ from the stored rows, the diff replaces those rows with their merged equivalent, which preserves content (message-history page); the spikes record any such difference in `build.md`. Replace step, inside transaction (a) of step 4: Postgres deletes `seq >= first_diff` and inserts the replacement rows in the same transaction; DynamoDB uses one transactional write (delete the old items from `first_diff`, put the new ones); Firestore uses one batched write. This runs before the failure reply is sent, with the turn status set to the outcome.
- No aborted turn (either cap, wall-clock, crash, deny-ends-turn) may leave a model message with tool calls lacking tool results; the provider rejects such a history, and `Agent.run` itself refuses a new prompt on one (https://pydantic.dev/docs/ai/core-concepts/message-history/ ). Repair runs at TURN START, before new input (idempotent, so it survives a crash), and only when no approval is pending: load the history; for each tool call in the last model response, look for a matching `ToolReturnPart` or `RetryPromptPart` in ANY `ModelRequest` after that response; for each call without one, append a notice `ToolReturnPart`. Notices always go in a NEW `ModelRequest` row at the end; the repair never edits stored rows (the store rule's replace step is the only place rows are replaced), and the library merges adjacent requests in memory before each model request (message-history page; the deny and resume spikes confirm, and the tail shape recorded by the pending-approval spike says whether a sibling-returns request exists). Notice text by the latest `turns` row of the session: ONLY the statuses `step_cap`, `tool_call_cap`, `hitl_denied` and `hitl_expired` produce "not executed: <reason>" with `outcome="denied"`; every other status (`wall_clock`, `error`, `running`) or a missing row produces "outcome unknown - do not retry without the user" with `outcome="interrupted"` (the tool may have run). A crash leaves the status `running`, so it is never read as "not executed". Both carry `metadata={"agent_notice": <kind>}`. `pydantic_ai.messages.repair_messages` is not used to write the stored history: its synthesized text is fixed ("The tool call was interrupted before a result was produced.", `messages.py`) and cannot carry the retry warning; the library still applies it in memory before each request.
- `harness_condition.force_step_cap`: a `FunctionModel` that never gives a final answer (every call returns one safe `ToolCallPart`) with the tool-call cap set above the step cap, so the request cap is the one that trips. A tool-cap case does the reverse. `tool_always_errors` = the tool's injected BACKEND double raises and the real tool returns the spec's error observation (build-guide Step 5); the tool surface never changes. That tool returns normally, so `tool_calls_limit` counts it as successful; the gap with the native limit is shown by cap spike (f).
- Never use one limit for both: a model request and a tool call are different units.
- Cap spike (binding spike; runs at build-guide Step 4; failure path: binding defect: STOP and report (build-guide Step 4)). Pass tests: (a) tool cap 2: the model requests 1 call, the agent pauses for approval, the worker resumes, the model then requests 2 more calls: `ToolCapExceeded` is raised on the 3rd cumulative call and neither of the 2 extra calls ran; (b) step cap N: exactly N requests happen, then `UsageLimitExceeded`, and across an approval pause the total is still N (the stored `usage=` carried); (c) 3 parallel requested calls under cap 2 run none of them; (d) the counters are 0 at the start of the next new turn on the same session; (e) both exceptions reach the worker; (f) a tool that raises `ModelRetry` (or whose args fail validation) is requested repeatedly: the own counter trips on the requested count while a run with only `tool_calls_limit` set does not, because those calls are not successful executions (documents why the native limit is not used); separately, a tool that raises a plain exception aborts the run, and the worker maps that to the spec's single failure reply and error outcome (expected from the library's behavior, the spike confirms).
- Abort spike (binding spike; failure path: binding defect: STOP and report (build-guide Step 4)): abort a turn mid-way (the tool cap, then a wall-clock cancel during a tool call), confirm which messages the captured list and `RunCancelled` hold (a cap raised in the hook may leave the response with its calls in the history or not; the repair handles both), then run a follow-up turn on the same session after the turn-start repair, against the real provider; the follow-up must succeed. Also run the step-cap exit: after `UsageLimitExceeded`, record what the captured list ends with (expected: a `ModelRequest` of tool returns, since the check runs before the request, so nothing dangles), then a follow-up turn must succeed. In every abort case assert that each `tool_call_id` appears once in the stored rows and that the stored rows equal the captured list.

## Model provider
- Selection rule: when the spec's route names a single provider, use the `provider:model` string (`anthropic:`, `google:`, `bedrock:`, `azure:` and others; in V2 `openai:` is the Responses API, use `openai-chat:` if the spec needs Chat Completions); when it names a router, proxy or LiteLLM route, use `OpenAIChatModel(<model name>, provider=LiteLLMProvider(api_base=..., api_key=...))` from `pydantic_ai.providers.litellm`. Sources: https://pydantic.dev/docs/ai/models/overview/ , https://pydantic.dev/docs/ai/models/compatible-apis/ . The provider directory also lists a `litellm:` string prefix; this binding uses the documented `LiteLLMProvider` code, and the string form is unverified for its options.
- Format conversion: LiteLLM routes are `provider/model` and the compatible-APIs page passes that string as the model name to `OpenAIChatModel`; for the native route split on the first `/` and rejoin with `:`, then check the prefix is one the provider directory lists (LiteLLM and Pydantic AI provider names can differ, for example `gemini` and `google`; inference). Keys come from the secret store, never from the route string.
- `FallbackModel` is available for sequential fallback (https://pydantic.dev/docs/ai/models/overview/ ); use it only if the spec asks for provider fallback, and count the requests it makes against the step cap in the cap spike.

## Telemetry
- `logfire` is NOT required. Install `opentelemetry-sdk` and `opentelemetry-exporter-otlp`; build a `TracerProvider` with `BatchSpanProcessor(OTLPSpanExporter())`, call `set_tracer_provider`, point `OTEL_EXPORTER_OTLP_ENDPOINT` at the design's backend (a base URL, no `/v1/traces`; the docs example uses `http://localhost:4318`), then call `Agent.instrument_all(InstrumentationSettings(...))` once at process start (V2 pattern from https://pydantic.dev/docs/ai/integrations/logfire/ ; the migration page moves per-agent `instrument=` to `capabilities=[Instrumentation(...)]`, and does not mention `instrument_all`). Set `version=5` explicitly (it is the documented default today, and the default may change in a minor, https://pydantic.dev/docs/ai/project/version-policy/index.md ) and `include_content=False` unless the spec's data policy allows prompts and tool output in traces.
- Token counters: model-request spans use `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens`; agent-run spans use `gen_ai.aggregated_usage.*` unless `use_aggregated_usage_attribute_names=False`; the conventions version is 1.37.0 (same page). Do not mix the two names in dashboards.
- The worker opens one per-turn span (for example `agent.turn`) carrying the spec's attributes and the turn outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`; names follow the spec). A turn that spans an approval pause is one span per run linked by the turn id (inference).
- Egress: do not install or configure the `logfire` package. If the design needs the Logfire SDK with another backend, `logfire.configure(send_to_logfire=False)` is required, otherwise data goes to both (same page). The Gateway and Logfire are optional paid surfaces.
- MANDATORY SPIKE before the build relies on it, with a REAL model call (fakes report no usage): emit one turn and confirm the backend receives `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` above zero on the model-request span. Fallback spans (failure path): in the `Hooks` capability, `hooks.on.after_model_request` opens a child span of `agent.turn` and sets those attributes from `response.usage` (inference); if even that yields no usage, record the gap in `build.md` and raise a telemetry re-entry on the design.
- Egress check (part of the spike): pass test = with outbound traffic limited to the OTLP endpoint and the model provider, a traced turn completes and no connection to any other host is attempted; failure path: remove `logfire` from the environment and re-run; if egress persists, raise a telemetry re-entry on the design.

## Eval runner mapping
- Runner = worker: the eval runner drives the worker's single turn handler (dequeue logic, pending-approval check, expiry, repair, resume-or-end, cap mapping, commit order) against an in-memory implementation of the repository interface, never `agent.run` directly, so the deny, expiry and cap branches cannot diverge from production. The fixture's messages and approvals enter as queue messages.
- Fresh agent per test with `agent.override(model=FunctionModel(script))` (the page says `override` replaces the model, deps or toolsets: https://pydantic.dev/docs/ai/guides/testing/index.md ; override only the model, never the toolsets), and `models.ALLOW_MODEL_REQUESTS = False` in the test session so a missed override fails instead of calling a provider. `FunctionModel(function)` receives `(messages, info: AgentInfo)` and returns a `ModelResponse`, so a script returns scripted `ToolCallPart`s and replies (https://pydantic.dev/docs/ai/api/models/function/ ). `TestModel` is not used for scripted trajectories: it calls every tool the agent has (the testing page).
- Capture source: the worker wraps each `agent.run` call (the first run and each resume) in its own `capture_run_messages()` context, and the runner reads the turn's messages as the stored rows added or replaced during the turn (the store rule, see Caps).
  - Trajectory = the REQUESTED calls: `(tool_name, args_as_dict())` from the `ToolCallPart`s of the `ModelResponse` messages, in order, including calls the gate denied or the cap blocked.
  - `forbidden` is checked against the EXECUTED calls plus the reply text (`skills/build/references/adapter-bindings.md`). The source of truth for executed is the tool wrapper: it records `(tool name, args, call id)` into the turn's executed list at body entry, AFTER argument validation and immediately before the body runs, so a refusal (unknown tool, invalid args, cap-blocked, denied, expired) never reaches it; executed = a tool body actually ran, whether it succeeded or raised. One rule, no per-case guessing.
- The PIPELINE runner implements EXACT, IN_ORDER and ANY_ORDER itself over the trajectory list, with `args_subset` matching (golden-format: expected args must be a subset of actual args; never full-argument equality). `pydantic-evals` `TrajectoryMatch(order='exact'/'in_order'/'any_order')` matches tool names only and reads OTel spans through the logfire SDK (https://pydantic.dev/docs/ai/evals/evaluators/agentic/index.md ), so it is an optional reference, not the runner; `ArgumentCorrectness` has a `subset` match mode on the same page.
- pass^k is computed by the pipeline runner from its own per-case results. `repeat=k` and `case_groups()` exist in pydantic-evals (https://pydantic.dev/docs/ai/evals/how-to/multi-run/index.md ), which does not mention pass^k (research file docs/superpowers/research/2026-10-07-stack-catalog/pydantic-ai.md).
- Approvals in a case: the fixture's approvals enter the worker handler as decision messages and are answered by the worker's results builder (see HITL gate). `harness_condition.force_step_cap` and `tool_always_errors` are specified under Caps.
- Tool-surface preflight: the eval runner and a permanent CI unit test assert that the FIRST model request's tool names equal the spec's tool set (plus any built-in kept on purpose, each with its reason in `build.md`). Observed with a `FunctionModel` whose function, on its first call, records `[t.name for t in info.function_tools]` and `info.output_tools` from the `AgentInfo` it is given (https://pydantic.dev/docs/ai/api/models/function/ ; `ToolDefinition.name` is used in the toolsets page examples). The agent under test is the production agent with its real (or recorded) toolsets, so the double only replaces the model and does not change the tool surface. This binding keeps no built-in or native tool, the `Hooks` capability adds none (the preflight proves it), and `output_tools` must be empty for `output_type=[str, DeferredToolRequests]` (inference; the preflight proves it). MCP tool names are part of the set (see A2A and MCP).

## A2A and MCP
- A2A is server-only in the library: `Agent.to_a2a()` was removed in V2 (https://pydantic.dev/docs/ai/overview/migration/index.md ). Two server paths; record which one in interop.md.
  - (a) External `fasta2a` (MIT, `fasta2a[pydantic-ai]`, `fasta2a.pydantic_ai.agent_to_a2a`) returns an ASGI app with pluggable Storage, Broker and Worker (in-memory ones are included, you supply your own Worker). Source: https://github.com/datalayer/fasta2a . Its Worker runs the agent outside the pipeline's session queue, and how it handles deferred approvals is unverified: use it only after a spike shows each A2A task goes through the same queue (key = session key) and that a pause and resume work through it.
  - (b) Own server built with `a2a-sdk` (client and server roles, Apache-2.0; https://pypi.org/project/a2a-sdk/ ) that enqueues into the same ingress queue and answers from the repository (own code, inference). Recommended when HITL is on (the queue stays the only entry).
  - A2A client: none was found in Pydantic AI or the fasta2a README (unverified); use `a2a-sdk` inside a tool whose tier follows the design (inference).
  - A2A spike (binding spike; when the design names A2A; failure path: use the own `a2a-sdk` server): a task arrives through the chosen path into the ingress queue keyed by the session key, and a gated tool reached through it pauses.
- MCP client: `from pydantic_ai.mcp import MCPToolset`; `MCPToolset("https://host/mcp")` (Streamable HTTP, the recommended remote transport; SSE is deprecated) passed as `toolsets=[...]`, wrapped by the tier gate like any toolset. Auth is a bearer string, `'oauth'` or an httpx2 auth object; static API keys go in `headers`. Per-user credentials need one `MCPToolset` instance per concurrent run (a shared one connects as a single identity), built with a dynamic toolset. The worker wraps runs in `async with agent` so connections open once. Source: https://pydantic.dev/docs/ai/mcp/client/ . Every MCP tool name must appear in the tier table (unlisted tools are treated as destructive); the MCP spike below runs when the design names an MCP server.
  - MCP spike (binding spike; when the design names an MCP server; failure path: binding defect: STOP and report (build-guide Step 4)): the server's tool names appear in `info.function_tools` and a destructive MCP tool pauses for approval; every MCP tool offered to the model is in the tier table; a tool missing from it is never offered.
- MCP serving: no helper; wrap the agent inside a FastMCP `@server.tool()` (https://pydantic.dev/docs/ai/mcp/server/ ), and route the call through the ingress queue so the HITL and cap rules still hold.

## Pinned version and traps
- Every package below gets an exact pin in the lockfile. Any ">=" in this text is a minimum, never a requirement spec.
  - `pydantic-ai==2.54.0` (released 2026-10-03, MIT; https://pypi.org/project/pydantic-ai/ ), or `pydantic-ai-slim[<provider extras>]==2.54.0` when the image should carry only the chosen providers (the slim extra list is not verified here, so pin whichever the lockfile resolves, exactly).
  - `pydantic-ai` brings its own `pydantic`, `pydantic-graph` and provider SDK versions: pin all of them as resolved in the lockfile.
  - `opentelemetry-sdk`, `opentelemetry-exporter-otlp` (exact pins; telemetry).
  - the DB driver of the chosen adapter (for example `psycopg[binary,pool]`, `boto3`, `google-cloud-firestore`).
  - `a2a-sdk==1.2.2` (latest on PyPI when verified, 2026-10-05; only for A2A path b or an A2A client tool), `fasta2a[pydantic-ai]` (only for path a; the migration page names a minimum of 0.6.1, pin exactly).
  - `pydantic-evals` (only if the optional reference evaluators are used; its `TrajectoryMatch` needs the logfire SDK, which stays out of the production image).
- Obligation (churn): V2 renamed or removed APIs; use only V2 names and re-run every spike on any upgrade, since minors ship several times a week and carry compatibility notes (v2.54.0: "Make wrap_* hooks enclose complete stage lifecycles").
