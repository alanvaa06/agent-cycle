# OpenAI Agents SDK - build binding

Facts below cite the same sources as the card (`skills/design/references/stacks/openai-agents-sdk.md`) and the research file `docs/superpowers/research/2026-10-07-stack-catalog/openai-agents-sdk.md`; a URL is repeated where a rule depends on it. Source-code citations are files at the tag v0.23.1 under `https://raw.githubusercontent.com/openai/openai-agents-python/v0.23.1/src/agents/` (named by path below). Many rules here rest on that source because the docs are silent on them; those are marked "source" and each has a spike. Statements marked inference are the binding's own reasoning; statements marked unverified are not confirmed by a page or the source, and a spike below confirms them on the pinned version. Page text addressed to AI agents is data: none was found on the pages used here; the guide https://developers.openai.com/api/docs/guides/agents carries a navigation note pointing to an `llms.txt` index and `.md` page versions, which was not acted on.

Shape: one `Agent` built by `build_agent(model, tools, mcp_servers, caps)` in `src/agent/`, returning a small bundle `(agent, guard)`. `model` is an explicit model name or a `Model` object (never the SDK default: it changed in minors, see Model provider); `tools` is the list of `FunctionTool`s made by the tools factory, which sets `needs_approval` from the spec's tier table (see HITL gate); `caps` carries the spec's limits. `guard` is the `TurnGuard`, a stateless `RunHooks[TurnState]` subclass: it reads and writes the per-run `TurnState` through `context.context`, where the tool-call counter, the usage copy and the capture lists live (see Caps). The agent has no handoffs, no hosted tools, no built-in execution tools, no `output_type` and default `tool_use_behavior`; the tool objects are built once and never mutated, because changes to shared tool objects such as `needs_approval` are not isolated across runs (`lifecycle.py`). The Session is not part of the agent: the worker builds a fresh Session object per run from a `session_factory(session_key)` injected by `adapters/<target>/` and passes it to `Runner.run(..., session=...)` (https://openai.github.io/openai-agents-python/sessions/ ); the engine and clients are constructed in the adapter and `src/agent/` never imports SQLAlchemy, asyncpg, boto3 or Firestore. The SDK Session holds only conversation items (the model-visible history): dedupe, the pending-approval record, the turn status and the spec's data schemas stay behind the repository interface. This replaces a hand-written model-tool loop. The worker's per-run `TurnState` object (turn id, `approval_id`, requested-call counter, token totals, capture lists) is passed as the run context.

## Sessions and state
- Postgres (incl. Supabase and Cloud SQL as plain Postgres): `SQLAlchemySession(session_key, engine=engine)` with `engine = create_async_engine("postgresql+asyncpg://...", pool_pre_ping=True)` built in the adapter (https://openai.github.io/openai-agents-python/sessions/sqlalchemy_session/ ). Install `openai-agents[sqlalchemy]`; the extra brings `sqlalchemy[asyncio]>=2.0` and `asyncpg>=0.29.0` (https://pypi.org/project/openai-agents/ ). Source (`extensions/memory/sqlalchemy_session.py`): tables `agent_sessions` and `agent_messages` (names overridable with `sessions_table` and `messages_table`), `session_id` is an unbounded `String`, `create_tables` defaults to False, there is NO schema argument, `get_items` orders by `created_at` then `id` and silently skips a row whose JSON does not decode, and `add_items`, `pop_item` and `clear_session` take `SELECT ... FOR UPDATE` on the session row inside a transaction, so writers to one session serialize in the database. The docs give no guidance for concurrent runs on one session, so the guarantee stays the queue (ordering key = session key).
- Supabase connection: use the direct connection or the Supavisor session mode (port 5432); never the transaction pooler (port 6543), which does not support prepared statements (asyncpg prepares statements by default, inference). Source: https://supabase.com/docs/guides/database/connecting-to-postgres . Schema: put the SDK tables in a schema not exposed through the Data API (for example `agent_state`). Because the constructor has no schema argument, select it on the engine with `connect_args={"server_settings": {"search_path": "agent_state"}}` (the asyncpg wiring is unverified; spike 1 proves it) and enable RLS on the tables: https://supabase.com/docs/guides/database/postgres/row-level-security . The Free plan pauses projects after 1 week of inactivity, so it is not for production: https://supabase.com/pricing
- DynamoDB: no SDK session found for it (research file: no built-in DynamoDB session), so the AWS adapter writes a small custom Session class. The protocol is `session_id`, `session_settings`, `get_items(limit)`, `add_items`, `pop_item`, `clear_session`; no inheritance is required (`memory/session.py`, https://openai.github.io/openai-agents-python/sessions/ ). One item per history item, partition key `session_id`, sort key `seq`; `add_items` writes the whole batch in one transactional write, taking `seq` from the current tail plus one and failing on a duplicate key (inference; the queue means a second writer is a defect); `get_items(limit)` returns the latest N in chronological order (the protocol docstring); items are stored as JSON strings like the SQLAlchemy session. Item-size and transaction-size limits apply to a history item with a large tool output: check them against the target table in spike 1 (not verified here: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html is not read).
- Firestore: Cloud SQL Postgres through `SQLAlchemySession` is the documented SDK path on GCP. If the design's sessions seam names Firestore, write the custom Session class: `sessions/{session_key}/messages/{seq}`, one document per item, one batched write per `add_items` (inference); a document is limited to 1 MiB (https://firebase.google.com/docs/firestore/quotas ), so a very large tool result is trimmed before it is returned from the tool.
- Queue ordering key = the session key, so one turn per session holds even when an approver is a different sender. Ingress resolves an approver's reply to the pending session's key before enqueueing.
- Schema setup runs once as the named one-shot migration job `agent-migrate` (compose service / ECS task / Cloud Run job), never from the worker: the job builds `SQLAlchemySession("agent-migrate", engine=engine, create_tables=True)` and awaits `get_items()`, whose first step creates the tables (`_ensure_tables` is private, so calling the public read is an inference; spike 3). The worker builds every Session with `create_tables=False`.
- Record tables, all behind the repository interface:
  - `pending_approvals(approval_id, session_key, run_state_json, run_state_schema, sdk_version, calls, requested_at, elapsed_s, tool_calls_requested, turn_id, tokens_in, tokens_out, session_items_at_pause, resume_started)`: every pause writes a NEW record with a fresh UUID `approval_id` (never the session key; at most one live record per session key, enforced by a unique index). `run_state_json` is `RunState.to_json()` and never leaves the server (see HITL gate); `run_state_schema` is its `$schemaVersion` and `sdk_version` the pin, so a resume can refuse an unreadable snapshot; `calls` holds, per pending call, `(call_id, tool name, arguments)` read from `result.interruptions`. `session_items_at_pause` is `len(await session.get_items())`, read after the run and before transaction (b) (the Session is built without a `limit`); every resume first cuts the session back to it (see HITL gate). `resume_started` is set, in a committed write, before a resume runs (see HITL gate).
  - `turns(session_key, turn_id, status, started_at)`: `status` is `running` from turn start (written after the repair, before the run) and is overwritten with the outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`, `error`; names follow the spec) on every exit; a turn that ended in a pause is `awaiting_approval`, and the same value is the `outcome` on the dedupe record of the message that caused the pause.
- Crash marker (T2 decision): USED, as for an own-loop stack, although the SDK has a Session store. Reason (source, `run.py`): the SDK saves the user input at the start of the run, then saves a turn's items only after `run_single_turn` returned, which includes executing the turn's tools. A wall-clock cancel, a tool failure or a crash during tool execution therefore leaves no function call in the session, and a dangling-call scan cannot tell that tools may have run. The status row is the only record. The repair rule is under Caps.
- Post-run commit order (the SDK commits the session DURING the run, like a checkpointer stack): (a) the session has committed (user input first, each turn's items after its tools, the interrupted turn's items at the pause; `run.py` "Persist session items but skip approval placeholders"); (b) ONE repository transaction applies the lifecycle below: writes the new record (`requested_at` = now, taken just before sending) with `elapsed_s`, the counter and the token totals, deletes the record the run started from, sets the turn status, and sets `processed_at`, the `outcome` (`awaiting_approval` when the run ended in a pause) and the reply text on the ingress dedupe record of the dequeued message; (c) send the approval prompt or the reply; (d) ack the queue message. Unlike a checkpointer, the SDK does not persist the pause: the `RunState` exists only in the worker until (b). A crash between (a) and (b) loses the pause (the gated call never ran), leaves the status `running` and no record, and redelivers the message with `processed_at` unset: the next turn's repair answers the dangling gated call with "outcome unknown", the turn runs again, the user message appears twice in the session, and a model proposal that pauses again writes a fresh record (inference). There is no orphaned-interrupt recovery to run at step 2, because there is no stored interrupt to recover.
- Redelivery: the ingress dedupe record (keyed by the channel message id) carries `processed_at`, the `outcome` and the reply text. On dequeue, a message whose record has `processed_at` set is not re-run: re-send the stored reply if the send may not have happened, then ack. Ingress dedupe alone only catches channel retries; this closes queue redelivery after a worker crash. The step-2a expiry commit does NOT set `processed_at`: only the final post-run commit of the turn that handles the message sets it.
- Pending-record lifecycle: any run started from a record deletes it in the post-run transaction unless the run ended in a NEW pause, which writes a fresh record (new `approval_id`) in that same transaction; within the transaction, delete the old record before inserting the new one (the unique index is per session key). "Ended in a pause" = `result.interruptions` non-empty AND `Runner.run` returned without an exception or timeout; otherwise the pending calls are discarded, so a wall-clock abort with a gated call pending writes no record. The checkpointer note does not apply (no stored interrupt, see above).
- Spikes (each runs before build-guide Step 4; numbered once here and defined in the section named). A failed store spike (1, 2) STOPS and raises a re-entry on the design's sessions seam, never a silent store swap; the other spikes state their own failure path:

## HITL gate
- Why native: `needs_approval` pauses the run, `result.interruptions` lists the pending calls, `RunState` serializes and resumes the SAME run in another process (https://openai.github.io/openai-agents-python/human_in_the_loop/ ). Source (`run.py`): a resume reads `current_turn` from `run_state._current_turn` and overrides the `max_turns` argument with `run_state._max_turns`; the interrupted turn resolves its tools through `resolve_interrupted_turn` with no new model call; `RunState.to_json` writes `usage`, `current_turn` and `max_turns` (`run_state.py`). Snapshots are unauthenticated, so the stored state is server-side only: it is never sent to a client and no client-supplied state, call list or approval record is accepted (same page, "Keep approval state on the server").
- Recommended placement: ONE tier gate in the tools factory. `make_tool(fn, tier)` wraps every function tool with `function_tool(..., needs_approval=<from the spec tier table>, failure_error_function=None, timeout=<per-tool>)`; destructive tools also set `timeout_behavior="raise_exception"`, so a timeout fails the run instead of returning a retryable message to the model. The factory raises at build time for a tool with no tier (fail closed). MCP tools: pass `require_approval` as a CALLABLE `(run_context, agent, tool)` that returns the tier-table result and True for any name not in the table, plus `tool_filter=create_static_tool_filter(allowed_tool_names=[<spec names>])`; never the dict form, because a name missing from the dict is NOT gated (`mcp/server.py`: `policy.get(tool.name, False)`). Callable policies fail closed when the SDK cannot parse the arguments (the call pauses without the callable running; the docs page). Sticky decisions (`always_approve`, `always_reject`) are never used: per-call approvals are scoped to the call id, which is what "never cached" requires.
- Tier mapping from the spec's tool contracts: destructive -> `needs_approval=True` every time, never cached, decisions approve or deny only; reversible -> per design policy (True, or an async predicate `(ctx, params, call_id)`); safe -> False.
- Worker sequence:
  1. Dequeue the message for the session (ordering key = session key). If the ingress dedupe record of the message (keyed by the channel message id) has `processed_at` set, do not re-run it: re-send the stored reply if the send may not have happened, then ack (inference; ingress dedupe alone only catches channel retries, this closes queue redelivery after a worker crash).
  2. Read the `pending_approvals` record for the session key (own repository).
  2a. If an approval is pending, check its expiry now: when it is older than the spec's TTL, or its `sdk_version` differs from the running pin (a snapshot from before an upgrade; the upgrade rule drains these first), the worker does not resume. It appends the `EXPIRED:` outputs of the pending calls to the session in one batch (see Deny), commits (delete the record, turn status `hitl_expired`; the dedupe record's `processed_at` is NOT set here), sends the spec's expiry notice only if the spec defines one (no model reply from this step), then handles the dequeued message as a new turn (inference). The record's `requested_at` is the time the worker sent the approval prompt. Expiry is evaluated when the next message for the session is dequeued (intended; a sweep is optional).
  3. If an approval is pending and not expired: parse the message (or the approver's reply) into a decision (builder below), commit `resume_started` = true on the pending record (a resume may run tools and then crash), and RESUME. Otherwise start a NEW turn: run the turn-start repair (see Caps), then write the turn status `running`. Both use ONE canonical call:
     ```python
     turn_state = TurnState(turn_id=turn_id, approval_id=aid, tool_calls_requested=n)   # new turn: aid None, n 0; resume: the record's values
     remaining = WALL_CLOCK - elapsed_s            # new turn: elapsed_s = 0; resume: the record's elapsed_s
     session = session_factory(session_key)        # fresh Session object per run; same id, same store
     if resumed:
         # resume_started was committed on the record just before this block (G8)
         while len(await session.get_items()) > record.session_items_at_pause:
             await session.pop_item()              # drop items a crashed earlier resume already saved
         state = await RunState.from_json(agent, record.run_state_json, context_override=turn_state)
         for item in state.get_interruptions():    # server-owned items only
             decide(state, item)                   # state.approve(item) / state.reject(item, rejection_message=...)
         run_input, extra = state, {}
     else:
         run_input, extra = user_text, {"context": turn_state, "max_turns": STEP_CAP}
     try:
         async with asyncio.timeout(remaining):    # outer wall clock (see Caps)
             result = await Runner.run(agent, run_input, session=session, hooks=guard,
                                       run_config=RUN_CONFIG, **extra)
     except MaxTurnsExceeded: ...                  # outcome mapping under Caps
     ```
     Cutting the session back is what makes a crash-redelivered resume safe: a resume that ran its tools and saved its items, then died before transaction (b), is re-run from the same stored snapshot, and without the cut its items would be saved twice. It relies on the resume's model input coming from the snapshot and not from the session (source; spike 5(a) proves it). `from_json` is async and takes the starting agent, which the worker rebuilds with `build_agent` (a fresh agent object is fine; the pending-approval spike proves it in a new process). With `context_override` the restore builds the context wrapper around the given object and then sets the restored usage and rebuilds the approvals on it (`run_state.py`, `_build_run_state_from_json`), and `TurnState` is not serialized into the snapshot (a non-mapping context is omitted unless a `context_serializer` is given; `run_state.py`). If `from_json` raises (for example on a schema version it does not support), the worker takes the step 2a path with the marker `EXPIRED:`. `RUN_CONFIG` sets no `tracing_disabled` (see Telemetry). Do not pass a changed `max_turns` on a resume: it is ignored.
  4. Post-run, in this order (commit order): the transaction (b), then send (c), then ack (d), all under Sessions and state. On a pause the worker reads the pending calls from `result.interruptions` (call id from `raw_item.call_id`, whether the raw item is an object or a mapping), serializes `result.to_state().to_json()` into the new record, and replies with the approval prompt.
- Decision value. The spec's outcomes map to the SDK as follows:
  - approve -> `state.approve(item)`.
  - deny -> see Deny below.
  - edit -> not supported: `RunState.approve` takes no replacement arguments (`run_state.py`). If the spec requires an edit outcome, STOP and raise a re-entry on the design's hitl_gate seam (inference); a deny with an instruction that lets the model re-propose is a different outcome (it needs a new approval) and only fits a spec that lets the model continue after a deny.
  - One approve or deny reply applies to every pending call of the record (design choice, inference), built by the worker's single decision builder, which the eval runner uses too. Before applying anything, the builder checks that the set of `call_id`s in `state.get_interruptions()` equals the record's `calls`; a mismatch fails the turn (defect or tampering) and nothing is resumed. A resume that returns interruptions again for calls it was given decisions for is a defect: the docs say unresolved items pause the run again.
- If a message for a pending session does not parse as a decision: keep the approval pending and reply with the spec's pending-approval prompt (or deny if the spec says so).
- Deny.
  - If the spec says a deny ends the turn: no further tool executes and no model request is made. The construct that routes to the end is the worker itself: it does NOT resume. Resuming with `state.reject(...)` would not end the turn, because a rejection returns the rejection text to the model and the run loops to the next model call (docs: https://openai.github.io/openai-agents-python/human_in_the_loop/ for the text; the loop is source, `run.py`, and spike 6 proves it).
  - The worker writes one output item per pending call that has none yet, ALL in ONE `session.add_items([...])` batch, each `{"type": "function_call_output", "call_id": <id>, "output": "DENIED: <tool> was not run: <reason>"}` (or `EXPIRED:` from step 2a), taking the call ids from the record, not from the snapshot. When the record's `resume_started` is set, an earlier resume may have run the tool, so the output is "<DENIED: or EXPIRED:> <tool>: outcome unknown - do not retry without the user" instead of "was not run". The write is idempotent: before adding, it reads `get_items()` and keeps only the call ids that have no output item, and the single batch (one transaction in `SQLAlchemySession`) cannot be half written, so a redelivery repeats the step safely. Then it commits (delete the record, status `hitl_denied`, dedupe record with `processed_at`, the outcome and the deny reply), sends the spec's deny reply and acks. The snapshot is discarded unread.
  - If the spec lets the model continue after a deny: resume as in step 3 with `state.reject(item, rejection_message="DENIED: <reason>")` for each call; the SDK writes the rejection as the call's output and the model sees it. A denied call still counts as a requested tool call (it was counted when requested, see Caps). The post-run transaction deletes the record unless the run ends in a new pause. State which of the two applies in `build.md`.
- Idempotency key for a gated/destructive call: unique per APPROVED CALL, `"<approval_id>:<call_id>"`. The `call_id` is `ToolContext.tool_call_id` (`tool_context.py`), the model's own `call_id` of the function call: it is stored in the snapshot and in the session, so it is identical when a crashed resume is delivered again. The key is also unique across pauses because `approval_id` is the fresh UUID of the record written at that pause (and a provider that repeats short call ids across responses does not collide: inference); the tool reads `approval_id` from `ctx.context` (the restored `TurnState`). A resume that pauses again writes a new record with a new id, so keys are never reused across pauses or turns, and the key is stable across queue redelivery because the record is deleted only in the post-run transaction. A crash after an approved tool ran but before that transaction redelivers the message and runs the tool again, so every destructive tool passes the key to its backend as the idempotency key and refuses to run when `approval_id` is None. The SDK's own record of executed invocations lives in the restored snapshot and does not prevent this re-run (inference).
- Approval is not an authorization boundary against an untrusted client: only an authenticated approver identity resolved by ingress may produce a decision (the docs: do not take the reviewer's identity from the request body), and each sensitive tool also checks authorization in its own body. Replay: the record is consumed in the post-run transaction and the ingress dedupe record absorbs a repeated channel message, which is the "atomic consume" the docs ask for given one worker per session key (inference); a queue redelivery after a crash is a deliberate re-run covered by the idempotency key. If the approval id travels back through an untrusted channel (for example a button payload), ingress signs it (HMAC over `approval_id`, session key and expiry, key from the secret store) and verifies it before enqueueing; the stored record, not the token, authorizes the resume (inference; this refines the plan's "signed resume token", which the server-side-only rule makes optional).
- Eval runner: the fixture's approvals enter the worker's turn handler as decision messages (see Eval runner mapping); the runner never calls `Runner.run` itself.
- Pause spike (spike 4; binding spike; failure path: fix this binding). Pass tests: a destructive call ends the run with the tool body run zero times, `result.interruptions` holding its call id and tool name, and the model double called once; `RunState.to_json()` stored and loaded in a NEW process with a freshly built agent returns the same call ids from `get_interruptions()`; a response with one gated and one safe call runs the safe tool once and the gated tool zero times; a safe tool never pauses; a call whose arguments do not parse pauses without the policy callable running; record in `build.md` what the session ends with at the pause (expected: the user message, the function call items, outputs only for the non-gated siblings, no output for the gated call, no approval placeholder).
- Resume spike (spike 5; binding spike; failure path: fix this binding). Pass tests: (a) approve runs the body exactly once with the key `"<approval_id>:<call_id>"` and the model double is called exactly twice in total; each `call_id` has exactly one output item in the session; the user message appears once in the session; and `ScriptedModel.calls[1].input` has no duplicated items, which proves the resume's model input comes from the snapshot (the cut-back rule relies on this; failure path: STOP and raise a re-entry on the design's sessions seam, proposing own message tables written in transaction (b), the option where the SDK Session is not the history of record); (b) resume -> second pause -> second approval yields a new `approval_id`, keys distinct from the first, and the second tool body runs; (c) a non-gated call of the original response ran once before the pause and not again after the resume; (d) redelivery: run the same resume twice from the same stored record (simulating a crash after the tool ran and its items were saved, before transaction (b)): the body is invoked twice with the same key, the session holds exactly one output item per `call_id` and no dangling `function_call` after the second run, and the follow-up turn succeeds (failure path: the same STOP and sessions-seam re-entry as in (a)); (e) when the spec lets the model continue after a deny, deny-and-continue runs the body zero times and the model's next input contains the rejection text; (f) a follow-up turn on the same session succeeds against the real provider; (g) a snapshot whose `$schemaVersion` is edited to an unsupported value makes `from_json` raise, and the worker takes the step-2a path instead of raising out of the handler.
- Deny and expiry spike (spike 6; binding spike; failure path: fix this binding). Pass tests: after a deny under deny-ends-turn, and after a step-2a expiry, a recording tool shows zero executions, the model double's `calls` list is unchanged (no model request), each pending call has exactly one `DENIED:` or `EXPIRED:` output even when the step is run twice, the expiry commit leaves the dedupe record's `processed_at` unset, and a follow-up turn on the same session succeeds against the real provider.

## Caps
- Step cap: native `max_turns=<spec step cap>`, passed on every NEW turn. Per turn across a pause: a resume restores `current_turn` and `max_turns` from the snapshot (`run.py`, `run_state.py`), so the count continues and nothing needs to be carried by the worker; the docs are silent on this (https://openai.github.io/openai-agents-python/running_agents/ ), which is why spike 7 proves it. Unit conversion: the SDK defines a turn as one AI invocation including its tool calls (`run.py` docstring); the spec's step is one model call, used 1:1 (inference). The check is `current_turn += 1` then `current_turn > max_turns` before the model call, so a cap of N allows N model calls; the final answer is also a model call, so a turn that spends all N calls on tool use has no call left to answer and trips the cap; record this definition in `build.md`. Do not set `error_handlers={"max_turns": ...}`: it would turn the cap into a model-less final output stored in the session history, and the cap exit must instead reach the worker as `MaxTurnsExceeded` so it sends the spec's single failure reply. `ModelSettings.retry` stays unset (runner-managed retries are opt in, https://openai.github.io/openai-agents-python/models/ ). The OpenAI client has its own retries below the SDK (`models/openai_responses.py` only disables them when runner-managed retries are on), so the adapter builds the model as `OpenAIResponsesModel(<name>, openai_client=AsyncOpenAI(max_retries=<n>))` with `<n>` set explicitly; those retries happen inside one turn, are not counted as turns (inference), and count toward the wall clock and the cost.
- Tool-call cap: own counter, because the SDK has none (research file; the nearest knob found is `max_function_tool_concurrency`, which limits parallelism). Implementation: `TurnGuard.on_llm_end(context, agent, response)` reads every output item of `response.output` whose `type` is `function_call`, appends `(name, arguments)` to `TurnState.requested`, adds their number to `TurnState.tool_calls_requested`, and raises the binding's `ToolCapExceeded` (an `Exception`, not an `AgentsException`) when the total exceeds `<spec tool-call cap>`. Order (non-streamed `Runner.run`, the only form this binding uses), source (`run_internal/turn_resolution.py`, `get_single_step_result_from_response`): the response is processed, `after_invocation_validation` runs the `on_llm_end` hooks, and only then `execute_tools_and_side_effects` runs any tool, so the cap counts each tool call REQUESTED (denied, pending and blocked calls included) and parallel calls cannot overshoot. The hook is not run again when an interrupted turn resumes (`llm_end_hooks_started` defaults to True, `run_internal/run_steps.py`), so a resume does not count the same response twice. A tool input guardrail is NOT used: it runs inside each tool's own invocation (https://openai.github.io/openai-agents-python/guardrails/ ), where earlier parallel calls would already have run, and it does not cover hosted or built-in tools. The counter lives in `TurnState` and is stored in `pending_approvals.tool_calls_requested` across a pause. Every function call counts, because the tool-surface preflight asserts the agent has no handoffs, hosted tools or built-in tools (local MCP tools also arrive as function calls).
- Both caps are PER TURN: a new turn starts `TurnState` at 0 and a fresh run with `max_turns` set; a resume restores the step count from the snapshot and the tool counter from the record.
- Both exits map to the spec's single failure reply and a cap outcome: `MaxTurnsExceeded` -> `step_cap`, `ToolCapExceeded` -> `tool_call_cap`, wall clock -> `wall_clock`, any other exception -> `error` (also the failure reply). The exception text is never sent to the user. The cap exceptions abort `Runner.run`, which saves items per turn after its tools, so neither cap exit persists a function call without its output: the blocked response is never saved, and a step-cap abort happens before the next model call (source; spike 7 confirms).
- `harness_condition.force_step_cap`: a `ScriptedModel` with exactly `<step cap>` steps, each a single safe `function_call` and no final answer, and the tool-call cap set above the step cap, so `max_turns` is the one that trips; `assert_complete()` confirms every step was consumed. A tool-cap case does the reverse. `tool_always_errors` = the tool's injected BACKEND double raises and the real tool catches it and returns the spec's error observation (build-guide Step 5); the tool surface never changes. A tool that lets the exception escape fails the run (tools are built with `failure_error_function=None`, so the SDK does not feed the fixed "Please try again" text to the model, `tool.py`), and the worker maps it to the failure reply and the outcome `error`.
- Wall-clock cap: the budget is per TURN, resume time included. The worker stores `elapsed_s` in the record at each pause and gives a resume the remainder (limit minus `elapsed_s`; the wait for the approver is not counted; inference); a new turn gets the full limit. It wraps `Runner.run` in `asyncio.timeout(remaining)` (needs Python 3.11 or later and the package supports 3.10, so on 3.10 use `asyncio.wait_for`; standard-library behavior). The SDK has no whole-run timeout: `ModelSettings.timeout` bounds one model attempt and a tool's `timeout` one tool call, and neither bounds the run (https://openai.github.io/openai-agents-python/models/ ), so set both as secondary bounds, with `timeout_behavior="raise_exception"` on destructive tools so a timeout is not fed to the model as a retryable message (`tool.py`). Tools must be `async def`: a synchronous function tool runs in `asyncio.to_thread` (`tool.py`), which a cancel cannot stop. In-flight Session writes finish even when the caller is cancelled (`memory/session.py`, `_await_mutation`). How the SDK settles tool tasks on a cancel is unverified; spike 8 measures it. Expiry gives the single failure reply and the outcome `wall_clock`.
- Persisting a turn: nothing to diff. The SDK writes the session itself (Sessions and state); the worker writes only the record, the status and the dedupe record.
- Repair of aborted turns. For this SDK an abort leaves two different shapes, so the turn-start repair handles both. It runs at TURN START, before new input (idempotent, so it survives a crash), and only when no approval is pending:
  1. Dangling calls (a lost pause produces them, and so do a wall-clock abort, a tool error or a crash during a resume, which delete the record and leave the gated call unanswered; see Sessions and state): `get_items()`; for each `function_call` item whose `call_id` has no `function_call_output` item, add `{"type": "function_call_output", "call_id": <id>, "output": "outcome unknown - do not retry without the user"}`. The SDK itself drops such calls from the model input in memory (`run_internal/session_persistence.py`, `drop_orphan_function_calls`), so without this write the model never learns the call may have run.
  2. Interrupted turn (no call in the session): read the latest `turns` row. Status `ok`, `step_cap`, `tool_call_cap`, `hitl_denied`, `hitl_expired` or `awaiting_approval` -> nothing. Status `running`, `wall_clock` or `error`, or no row while the session is non-empty -> a crash or abort during tool execution: add one user-role item `{"role": "user", "content": "[agent-notice turn <turn_id>] The previous turn was interrupted; its tools may have run. Outcome unknown - do not retry without the user."}` unless the session tail already holds that notice for that turn id. The user role is used because it is accepted on every route (inference; spike 8 sends it to the real provider).
  3. Only then write the new status `running`. Every repaired call says "outcome unknown", never "not executed".
- Abort spike (spike 8; binding spike; failure path: fix this binding). Pass tests: (a) abort a turn with the wall-clock timeout during an `async` tool and record what the session ends with (expected: the user message and no function call); the next new turn, after the repair, succeeds against the real provider and the model's reply shows it was told the outcome is unknown; (b) a tool that raises: the worker maps it to the failure reply and the outcome `error`, and the repair adds the notice once; (c) kill the worker process during a tool, then run the repair twice: exactly one notice exists; (d) the lost-pause case (end the process after the SDK committed and before transaction (b)): the session holds a dangling gated call and no record, the repair writes the "outcome unknown" output, and the follow-up turn succeeds; (e) a wall-clock abort of a resume deletes the record it started from and sets the status `wall_clock`, the next repair answers the still-dangling gated call with "outcome unknown", and a run aborted with a gated call pending writes no record; (f) a synchronous tool is not stopped by the cancel (documents why tools are `async`). Also run the step-cap exit: after `MaxTurnsExceeded` a follow-up turn on the same session succeeds.
- Cap spike (spike 7; binding spike; runs before build-guide Step 4; failure path: fix this binding). Pass tests: (a) tool cap 2: the model requests 1 call, the turn pauses for approval, the worker resumes, the model then requests 2 more calls: `ToolCapExceeded` is raised on the 3rd cumulative call, neither extra call ran, and the session holds no function call from the blocked response; (b) step cap N: exactly N model calls happen, then `MaxTurnsExceeded`, and across an approval pause the total is still N (`len(model.calls)`); a larger `max_turns` passed on the resume changes nothing; (c) 3 parallel requested calls under cap 2 execute none of them; (d) both counters are 0 at the start of the next new turn on the same session; (e) both exceptions reach the worker unwrapped; (f) pause during turn N (the cap), approve: the approved tool runs and its output is saved, then `MaxTurnsExceeded`, and a follow-up turn succeeds.

## Model provider
- Selection rule: when the spec's route is an OpenAI model, pass the model name to `Agent(model=...)` (default OpenAI provider, Responses API path; https://openai.github.io/openai-agents-python/models/ ); for any other route install `openai-agents[litellm]` and pass `litellm/<provider>/<model>` (or build a `LitellmModel` directly). An OpenAI-compatible endpoint can also use `OpenAIChatCompletionsModel` with an `AsyncOpenAI(base_url=...)` client. Always set the model explicitly: the SDK's default model changed in 0.16 and 0.20 (research file citing https://openai.github.io/openai-agents-python/release/ ) and is `gpt-5.6-luna` on the models page today.
- Format conversion: LiteLLM routes are `provider/model`; the SDK form is the same string with the `litellm/` prefix added; for an OpenAI route use the bare model name (drop an `openai/` prefix; inference). Keys come from the secret store, never from the route string.
- `litellm` (installed by the extra, minimum 1.83.0 per the package metadata at https://pypi.org/project/openai-agents/ ): pin an exact version in the lockfile with hashes and never 1.82.7 or 1.82.8 (reported compromised on PyPI 2026-03-24 at https://adk.dev/agents/models/litellm/ ). ## Telemetry
- Tracing to OpenAI is ON by default with inputs and outputs, so the spec's security row requires switching it off or replacing it (https://openai.github.io/openai-agents-python/tracing/ ). Process start (`adapters/<target>/main.py`, BEFORE building any agent or running anything; the plan's "first line") does, in order: `set_tracing_disabled(True)` then `set_trace_processors([])`, both from `agents` (the page lists the first as the code switch and says `set_trace_processors()` replaces the default exporter; `add_trace_processor()` adds beside it and is never used). The deployment also sets `OPENAI_AGENTS_DISABLE_TRACING=1` in the process environment: the SDK reads it once, on first use of the provider, and a later `set_tracing_disabled` call overrides it (`tracing/provider.py`). The default provider and its processor are created lazily at the first tracing call, which the two functions above trigger and then disable (`tracing/setup.py`). `RUN_CONFIG` sets no `tracing_disabled`, so the permanent CI test (below) exercises the global switch.
- The exporter endpoint to watch for is `https://api.openai.com/v1/traces/ingest` (`tracing/processors.py`, `_OPENAI_TRACING_INGEST_ENDPOINT`). The docs name no endpoint URL.
- Own telemetry (the recommended route): the worker opens one per-turn span (for example `agent.turn`) with OpenTelemetry carrying the spec's attributes and the turn outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`, `error`; names follow the spec) and sets `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` from the run's usage (`RunContextWrapper.usage`: `requests`, `input_tokens`, `output_tokens`, `usage.py`). `TurnGuard.on_llm_end` copies the usage into `TurnState` on every response (from `context.usage`, or the sum of each `response.usage`), and the worker reads the totals from `TurnState` on EVERY exit, including `tool_call_cap`, `wall_clock` and `error`, where no `result` exists. Usage is cumulative across a pause because it travels in the snapshot, so a resume's span reports the difference from the totals stored in the record. A turn that spans a pause is one span per run linked by the turn id (inference). Install `opentelemetry-sdk` and `opentelemetry-exporter-otlp`; point `OTEL_EXPORTER_OTLP_ENDPOINT` at the design's backend.
- Optional SDK spans (only if the design wants them): replace the default exporter with an OTel bridge via `set_trace_processors([bridge])` and nothing else, set `RunConfig(trace_include_sensitive_data=False)` unless the spec's data policy allows content in traces, and do not call `set_tracing_disabled(True)` (it would stop the bridge too). The bridges are third-party and their behavior is unverified: `openinference-instrumentation-openai-agents` 2.5.2 (Apache-2.0, 2026-10-01), `openai-agents-opentelemetry` 0.4.1 (MIT, 2026-10-01), and the OpenTelemetry contrib `opentelemetry-instrumentation-openai-agents-v2` 0.1.0 (Apache-2.0, described on PyPI as barebones, last released 2025-10-15). Versions from PyPI on 2026-10-08. Each needs spike 10 on the exact version.
- MANDATORY SPIKE (spike 10) before the build relies on it, with a REAL model call (the `ScriptedModel` double reports a deterministic usage, so fakes prove nothing about usage). Pass tests: (a) emit one turn that includes a tool call and confirm the OTLP backend receives `agent.turn` with `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` above zero, and no prompt or response text unless the data policy allows it; (b) egress check: the process's outbound traffic goes through a TLS-intercepting proxy (for example mitmproxy, its CA trusted through `SSL_CERT_FILE`) whose log shows request paths; the turn completes and the log shows ZERO requests to the path `/v1/traces/ingest`. The proxy never forwards an ingest request upstream. A host-level check is enough only when the model route is not OpenAI; with an OpenAI route the model and the trace endpoint share the host `api.openai.com`, so only the path tells them apart; (c) negative control: the same turn in a throwaway process WITHOUT the process-start code and with a dummy `OPENAI_API_KEY` MUST show the ingest request in the proxy log (the proxy answers it locally), proving the probe can see it; (d) a `TracingProcessor` probe added after process start receives zero traces. ## Eval runner mapping
- Runner = worker: the eval runner drives the worker's single turn handler (dequeue logic, pending check, expiry, repair, resume-or-end, cap mapping, commit order) against an in-memory implementation of the repository interface and an in-memory Session per test: the eval `session_factory` returns ONE cached `SQLiteSession` per session key per test (`SQLiteSession(session_key)` with no path is in-memory: `memory/sqlite_session.py`, so each new object would be its own empty database and lose the history; a per-test temp file path is the alternative), never `Runner.run` directly, so the deny, expiry and cap branches cannot diverge from production. The fixture's messages and approvals enter as queue messages; the expiry clock is injected. The in-memory repository stores the real `RunState.to_json()` text and the handler rebuilds the agent with `build_agent` on each resume, so the serialization path and the cross-process resume are exercised; the same `ScriptedModel` instance is injected into both builds so the script continues across the resume.
- Model double: `agents.testing.ScriptedModel`, passed as `Agent(model=double)` through the factory's `model` argument. Steps are lists of output items built with `assistant_message(...)` and `function_call(name, args, call_id=...)` (unique `call_id` per call); it replaces only the model, never the tools, the hooks or the session, and `assert_complete()` ends every deterministic case (https://openai.github.io/openai-agents-python/testing/ ).
- Capture source: the `TurnState` lists filled by `TurnGuard`, read by the runner after each turn.
  - Trajectory = the REQUESTED calls: `TurnState.requested`, the `(name, arguments)` of every `function_call` in every model response as `on_llm_end` received it, in order, including calls the cap blocked and calls the gate paused.
  - `forbidden` is checked against the EXECUTED calls, `TurnState.executed` (`TurnGuard.on_tool_start` adds `(tool.name, context.tool_arguments)`; it runs after approval and just before the tool body, `run_internal/tool_execution.py`, so rejected and paused calls are not in it), plus the reply text (`skills/build/references/adapter-bindings.md`). One rule, no per-case guessing.
- The PIPELINE runner implements EXACT, IN_ORDER and ANY_ORDER itself over the trajectory list, with `args_subset` matching (golden-format: expected args must be a subset of actual args; never full-argument equality). The SDK has no trajectory API (research file; the testing page), so there is no framework evaluator to use.
- pass^k is computed by the pipeline runner from its own per-case results. OpenAI Evals and trace grading are not used: Evals goes read-only 2026-10-31 and shuts down 2026-11-30 (https://developers.openai.com/api/docs/deprecations ).
- Approvals in a case: the fixture's approvals enter the worker handler as decision messages and are answered by the worker's decision builder (see HITL gate). `harness_condition.force_step_cap` and `tool_always_errors` are specified under Caps.
- Tool-surface preflight: the eval runner and a permanent CI unit test assert that the FIRST model request's tool names equal the spec's tool set (plus any built-in kept on purpose, each with its reason in `build.md`; this binding keeps none). Capture source: `ScriptedModel.first_call.tools` (a `ModelCall` field, `testing/model.py`), reading `tool.name` for each; the same call's `handoffs` must be empty and its `output_schema` None. The double replaces only the model, so it does not change the surface (local MCP tools reach the request as function tools: inference, spike 13 confirms). Negative control (the surface is filtered by `create_static_tool_filter`): a fake MCP server exposes one extra tool outside the spec; with the filter the preflight passes, and a second run of the same test with the filter removed MUST fail on that extra name, proving the preflight can see a filtered tool.
- Eval double spike (spike 11; binding spike; failure path: fix this binding): the scripted double drives a full pause, resume and finish through the worker handler on the in-memory Session and on the real Session class with the same trajectory.
