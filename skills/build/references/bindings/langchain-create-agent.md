# LangChain create_agent - build binding

Facts below cite the same sources as the card (`skills/design/references/stacks/langchain-create-agent.md`) and the research file `docs/superpowers/research/2026-10-07-stack-catalog/langchain-family.md`; a URL is repeated where a rule depends on it. This file is self-contained: the shared LangGraph facts are restated in full. Statements marked inference are the binding's own reasoning; statements marked unverified are not confirmed by a page or the library source, and a spike below confirms them on the pinned version.

Shape: one compiled agent from `create_agent`, built by `build_agent(model, checkpointer, tools, caps)` in `src/agent/`. The `middleware` list is, in this order, `HumanInTheLoopMiddleware`, the binding's own `TurnCaps` middleware (counters, both caps and the deny jump; see Caps) and the optional telemetry fallback middleware; `checkpointer=` takes the injected saver and `caps` carries the spec's two per-turn limits into `TurnCaps`. The list order matters: after-model hooks run last to first and before-model hooks first to last (https://docs.langchain.com/oss/python/langchain/middleware/custom ), so `TurnCaps.after_model` runs before the HITL pause and an over-cap request never reaches the approver. This replaces a hand-written model-tool loop and `langgraph.prebuilt.create_react_agent` (the v1 guide now recommends `create_agent`; it does not call the old function deprecated). The adapter constructs `PostgresSaver` / `AsyncPostgresSaver` (or the DynamoDB saver) in `adapters/<target>/` and injects it; `src/agent/` never imports psycopg or the saver packages. The checkpointer holds only conversation/graph state. Dedupe and the spec's data schemas live in repository tables behind the repository interface, not in agent state. Sources: https://docs.langchain.com/oss/python/langchain/agents and https://docs.langchain.com/oss/python/migrate/langchain-v1.md

## Sessions and state
- `create_agent(..., checkpointer=<saver>)` plus `{"configurable": {"thread_id": <session key>}}` in the config is how the agent gets persistence. Source: https://docs.langchain.com/oss/python/langchain/short-term-memory
- Postgres: `PostgresSaver` / `AsyncPostgresSaver` from `langgraph-checkpoint-postgres`. Source: https://docs.langchain.com/oss/python/langgraph/checkpointers.md
- Saver kind follows the worker: an async worker uses `AsyncPostgresSaver` and `ainvoke` / `astream`; a sync worker uses `PostgresSaver` and `invoke` / `stream` (inference; the persistence page names both savers: https://docs.langchain.com/oss/python/langgraph/persistence ).
- A connection you create yourself must use `autocommit=True` and `row_factory=dict_row` (autocommit makes `.setup()` persist the tables; the saver reads columns by name). Source: https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md
- `.setup()` runs once, as a named one-shot migration job (`agent-migrate`: compose service / ECS task / Cloud Run job), never from the worker and never per request. The short-term-memory page shows `checkpointer.setup()` inline next to `create_agent`; do not copy that into the worker. Source for the call: https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md
- Durability: pass `durability="sync"` on every agent call (persists changes before the next step starts; default is "async"). The parameter is documented on the LangGraph `invoke`: https://reference.langchain.com/python/langgraph/pregel/main/Pregel/invoke ; that `create_agent`'s compiled graph accepts it on `stream`, `ainvoke` and `astream` is unverified (inference: it is a compiled LangGraph graph), so confirm it in the first spike. The modes are described at https://docs.langchain.com/oss/python/langgraph/checkpointers.md
- `thread_id` = the spec's session key; keep it under 255 characters on Postgres. Source: https://docs.langchain.com/oss/python/langgraph/persistence
- Queue ordering key = `thread_id` (the session key), so one turn per thread holds even when the approver is a different sender. Ingress resolves an approver's reply to the pending session's key before enqueueing. The OSS library has no per-thread locking and double-texting is not available there. Source: https://docs.langchain.com/langsmith/double-texting.md
- The built-in call-limit middlewares are not used: their run counters restart on a HITL resume and `thread_limit` spans the whole thread, so neither is a per-turn cap (see Caps).
- Supabase connection: use the direct connection or the Supavisor session mode (port 5432); never the transaction pooler (port 6543), which does not support prepared statements (psycopg3 uses them by default, inference). Source: https://supabase.com/docs/guides/database/connecting-to-postgres
- Supabase schema: put the checkpoint tables in a schema not exposed through the Data API (for example `agent_state`, selected via the connection's search_path; the wiring is unverified) and enable RLS on them. Source: https://supabase.com/docs/guides/database/postgres/row-level-security
- Supabase Free plan: projects are paused after 1 week of inactivity, so it is not for production. Source: https://supabase.com/pricing
- DynamoDB: `langgraph-checkpoint-aws` provides the checkpointer (the class is named DynamoDBSaver in the research file; the docs page lists only the package). The same page also lists a separate community package, `langgraph-dynamodb-checkpoint` (agentstate); prefer the AWS package. Source: https://docs.langchain.com/oss/python/integrations/checkpointers/index.md
- Firestore: no official checkpointer (a community package is listed, unverified for production). Source: https://docs.langchain.com/oss/python/integrations/checkpointers/index.md . If the design names Firestore, STOP and raise a re-entry on the design's sessions seam; do not swap the store silently.
- Spikes (each runs before build-guide Step 4). A failed store spike STOPS and raises a re-entry on the design's sessions seam, never a silent store swap; the other spikes state their own failure path:
  - Supabase (store spike): after `.setup()` with the chosen search_path the tables exist in `agent_state` and not in `public`; then `ENABLE ROW LEVEL SECURITY` on them; a put/get round trip works as the saver's DB role.
  - DynamoDB (store spike): the pinned package imports the named saver class and a put/get round trip works against the target table.
  - Durability (binding spike, not a store spike): `durability="sync"` is accepted by the exact call the worker uses (`invoke`, `ainvoke`, `stream` or `astream`) on the compiled `create_agent` graph; failure path: fix this binding (use the call or parameter the pinned version accepts), not a sessions-seam re-entry.
  - Pending interrupt (binding spike; pass test: after a gated tool call pauses the agent, `agent.get_state(config)` exposes the pending interrupt via `state.tasks[*].interrupts` and the payload carries `action_requests`; failure path: fix this binding and the worker's check, not a sessions-seam re-entry). The call that raises the interrupt also reports it in its own result (`__interrupt__` key, or `.interrupts` with `version="v2"`), but the worker needs the check on a later dequeue.
  - Resume payload (binding spike; pass tests: for one gated call, `Command(resume={"decisions": [{"type": "approve"}]})` runs the tool once; a reject decision runs it zero times and the agent receives the rejection; an edit decision runs the tool with the edited args. Multi-action: with two gated calls in one model message, the decisions `[approve, reject]` run exactly the first and not the second, and the interrupt payload shows one interrupt with two `action_requests`; if the spike instead shows one interrupt per action, resume with the interrupt-id map described under HITL gate. Failure path: fix this binding).
  - Deny (binding spike) and cap/abort spikes are specified under HITL gate and Caps.
- Worker post-run order: the checkpointer has committed during the run; then one repository transaction writes a NEW pending-approval record when the turn ended in a pause (fresh UUID `approval_id`, `requested_at` = now, taken just before sending), deletes the record the run started from unless the run ended in a NEW pause ("ended in a pause" = an interrupt is pending AND the run completed without an exception or timeout; a wall-clock abort with a gated call pending writes no record), and writes the dedupe record's `processed_at` and reply text; then send the prompt or reply; then ack the queue message. If step 2 finds a pending interrupt with no record (a crash between the checkpoint commit and the post-run transaction, or a timeout after the interrupt was checkpointed), write a fresh record (new UUID `approval_id`, `requested_at` = now) before prompting or resuming. A dequeued message whose dedupe record has `processed_at` set is not re-run: re-send the stored reply if the send may not have happened, then ack.

## HITL gate
- Recommended placement: `HumanInTheLoopMiddleware` first in the `middleware` list, configured from the spec's tool tiers (below). It pauses the agent after the model proposes a gated tool call and before the tool executes, and needs a durable checkpointer plus a `thread_id`. Source: https://docs.langchain.com/oss/python/langchain/human-in-the-loop
- Worker sequence:
  1. Dequeue the message for the session (ordering key `thread_id`).
  2. Read `agent.get_state(config)` for that `thread_id` and check for a pending interrupt (inference, unverified for `create_agent`: pending interrupts appear on the snapshot as `state.tasks[*].interrupts`; the pending-interrupt spike confirms it).
  2a. If an approval is pending, check its expiry now: when it is older than the spec's TTL, resume it with reject decisions whose message starts with the marker `EXPIRED:` (the `TurnCaps` deny jump ends the turn on that marker whatever the spec's deny policy is), record the outcome `hitl_expired`, produce no model reply from this resume (the final message is a tool message; send the spec's expiry notice only if the spec defines one), then handle the dequeued message as a new turn (inference). The worker records the time it sent the approval prompt in the repository for this check. Its repository commit deletes the pending record but does NOT set the dedupe record's `processed_at`; only the final post-run commit of the turn that handles the message sets it.
  3. If an approval is pending and not expired: parse the message (or the approver's reply) into a decision and resume with `Command(resume={"decisions": [...]})` on the same `thread_id`. A resume carries no new input, so the `TurnCaps` counters persist across the pause. Otherwise start a new turn: run the turn-start repair (see Caps), then invoke with fresh input and both counters set to 0.
- Decision value. The spec's three outcomes map to the documented payloads, one entry per `action_requests` item, in the same order as the interrupt lists them. Source: https://docs.langchain.com/oss/python/langchain/human-in-the-loop
  - approve -> `{"type": "approve"}`
  - deny -> `{"type": "reject", "message": "DENIED: <reason>"}` (`message` is optional in the docs; the binding always sets it, with the marker, see Deny below)
  - edit -> `{"type": "edit", "edited_action": {"name": "<tool>", "args": {...}}}`; keep edits conservative, because large changes may make the model re-plan.
  - The documented `respond` type returns a human reply as a successful tool result and the page says not to use it to deny side-effecting tools: the binding never uses it.
  - Reply covering several gated calls (design choice, inference): one approve or deny reply applies to every pending action, `edit` is accepted only when exactly one action is pending, and the worker's single decisions-list builder makes the list length equal the number of `action_requests`. The eval runner uses the same builder. Only if the resume-payload spike shows several interrupts pending (one per action) instead of one interrupt with N actions, the resume value is a map from interrupt id to its answer: https://docs.langchain.com/oss/python/langgraph/interrupts , https://docs.langchain.com/oss/python/langchain/streaming .
- If a message for a pending session does not parse as a decision: keep the interrupt pending and reply with the spec's pending-approval prompt (or deny if the spec says so). Expiry is evaluated when the next message for that session is dequeued (step 2a; intended; a sweep is optional).
- Deny. The worker always starts the reject message with a marker, `DENIED:` (or `EXPIRED:` from step 2a), so `TurnCaps` can recognize a rejection among the tool messages. Match rule: a tool message counts as a rejection only when its content STARTS WITH the marker AND its `tool_call_id` belongs to the tool calls of the last AI message. Untrusted tool output is wrapped in the spec's envelope, so it cannot start with the marker (inference; the envelope is the spec's untrusted-content wrapper). In `before_model` the deny/expiry jump is checked BEFORE the step cap. That the reject message reaches the tool message content is unverified; the deny spike confirms it.
  - If the spec says a deny ends the turn: no further tool may execute after the reject. `TurnCaps.before_model` finds a tool message carrying the marker after the last AI message and returns `{"jump_to": "end"}` (valid targets are end, tools and model; declared with `@hook_config(can_jump_to=["end"])`). Source: https://docs.langchain.com/oss/python/langchain/middleware/custom . The reply is the spec's deny reply and the outcome is `hitl_denied`; the tool message is the last message, so no tool call is left without a result.
  - If the spec lets the model continue after a deny: the jump is disabled for `DENIED:` (it stays on for `EXPIRED:`), the model sees the rejection and continues. State which of the two applies in `build.md`.
  - A denied call still counts as a requested tool call for the tool cap (see Caps).
  - Deny spike (binding spike; failure path: fix this binding): after a reject under deny-ends-turn, zero further tool calls execute and a follow-up turn on the same `thread_id` works.
- Tier mapping, built from the spec's tool contracts into `interrupt_on`: destructive -> `{"allowed_decisions": ["approve", "reject"]}` every time, never cached (no edit, no respond); reversible -> per design policy (`["approve", "edit", "reject"]`, or a `when` predicate on the tool call request, which needs `langchain>=1.3.3` and is satisfied by the pin); safe -> `False`. List every tool explicitly; do not rely on unlisted tools defaulting to auto-approve (the page does not state the default for an unlisted tool; unverified). Source: https://docs.langchain.com/oss/python/langchain/human-in-the-loop
- Idempotency: the interrupted node restarts from its beginning on resume, so any code before the interrupt in that node runs again; keep it idempotent (the HITL middleware's own pre-interrupt work only inspects the model's message, inference). Gated tools run only after approval, so a destructive tool body never runs before the pause. Interrupts are matched to resume values by position: never reorder them. Do not wrap interrupt-raising code in a bare try/except. Idempotency key for a destructive tool: `<approval_id>:<tool_call_id>`, where `approval_id` is the fresh UUID of the pending record written at this pause; a resume that pauses again writes a new record with a new id, so keys are never reused across pauses or turns. The worker passes `approval_id` to the run in `config["configurable"]` and the tool reads it (inference; the key spike confirms how the tool sees it). The key is stable across queue redelivery because the record is deleted only in the post-run transaction. Key spike (binding spike; failure path: fix this binding): resume -> second pause -> second approval yields distinct keys and the second tool body runs. Source: https://docs.langchain.com/oss/python/langgraph/interrupts
- Eval runner: the fixture's approvals enter the worker handler as decision messages; the handler resumes with `Command(resume={"decisions": <list from the worker's builder>})` on the same `thread_id`, until the agent finishes or the fixture runs out.

## Caps
- One small custom middleware, `TurnCaps` (a subclass of `AgentMiddleware`), owns both caps; the built-in `ModelCallLimitMiddleware` and `ToolCallLimitMiddleware` are not used. Reason: their run counters are private untracked state (`UntrackedValue`, library source on master), so they are not saved in checkpoints and a `Command(resume=...)` invocation starts them at zero (inference from the annotation; the docs say `run_limit` is "per single invocation"). A spec turn that pauses for approval and resumes would then get a second budget. A global `ToolCallLimitMiddleware` also cannot use `exit_behavior="end"` (single tool only). Sources: https://docs.langchain.com/oss/python/langchain/middleware/built-in , https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/tool_call_limit.py , https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/model_call_limit.py
- State: a custom `AgentState` subclass assigned as the middleware's `state_schema` with two `NotRequired[int]` fields, `model_calls` and `tool_calls_requested`, and NO reducer, so an input value overwrites. Custom fields are passed in the invoke input next to `messages`. Source: https://docs.langchain.com/oss/python/langchain/middleware/custom
- Per turn: the worker puts `model_calls: 0` and `tool_calls_requested: 0` in the input of every NEW turn. A resume after approval is `Command(resume=...)` and carries no input, so the counters keep their checkpointed values across the pause (inference from the reducer-less state; the cap spike proves it).
- `before_model`: if `model_calls >= <spec step cap>` raise the binding's `StepCapExceeded`; otherwise return `{"model_calls": model_calls + 1}`. The check runs before each model call, so a cap of N allows N model calls. This hook also holds the deny jump (see HITL gate).
- `after_model`: read the last AI message, set `tool_calls_requested += len(ai_message.tool_calls)` and, if the total exceeds `<spec tool-call cap>`, raise `ToolCapExceeded`. The hook runs before the tool node and before the HITL pause (list order, see Shape), so the cap counts each tool call REQUESTED, not each tool-execution step, and parallel calls cannot overshoot; denied and blocked calls count as requested. The hook order is documented at https://docs.langchain.com/oss/python/langchain/middleware/custom ; raising from a hook is not documented on that page, though the built-in limit middlewares raise from their hooks (library source above): the cap spike confirms the exception reaches the worker.
- Both exits map to the spec's single failure reply and a cap outcome: `StepCapExceeded` -> outcome `step_cap`, `ToolCapExceeded` -> outcome `tool_call_cap`, wall-clock expiry -> outcome `wall_clock`. The exception text is never sent to the user.
- Unit conversion (inference): the spec's step is one model call (one pass of model -> tools); `<spec step cap>` is used 1:1. The final answer is also a model call, so a turn that spends all N calls on tool use has no call left to answer and trips the cap; record this definition in `build.md`. LangGraph's `recursion_limit` counts super-steps, not model calls, so it is not the step cap: leave the default (1000) unless the cap spike's measured super-steps per model call, multiplied by the step cap, exceeds it; and catch `GraphRecursionError` as a backstop mapped to the same reply and the outcome `step_cap`. Source for `recursion_limit` and the error: https://docs.langchain.com/oss/python/langgraph/graph-api
- Wall-clock cap: the worker bounds each turn, including the time spent on a resume, with the spec's wall-clock limit (timeout around the agent call); expiry produces the same failure reply and the outcome `wall_clock`.
- No aborted turn (either cap, wall-clock, crash, deny-ends-turn) may leave an AI message with tool calls lacking tool results; most providers reject such a history (https://docs.langchain.com/oss/python/langchain/short-term-memory ). A cap raised in `after_model` leaves exactly that, and so can a timeout or crash during a tool call. Repair runs at TURN START, before new input (idempotent, so it survives a crash), and only when no approval is pending: read `agent.get_state(config)`; if the last AI message has tool calls without matching tool messages, append one notice per dangling call with `agent.update_state(config, {"messages": [...]}, as_node="tools")` (`tools` is the tool node's name in the streaming examples, https://docs.langchain.com/oss/python/langchain/streaming ; confirm the name in the abort spike). Notice text: for cap and deny exits, "not executed: <reason>"; for a wall-clock abort or crash, "outcome unknown - do not retry without the user" (the tool may have run).
- `harness_condition.force_step_cap`: use a fake model that never gives a final answer (a cycling `GenericFakeChatModel` iterator emitting one safe tool call per message, inference) and set the tool-call cap above the step cap, so the model-call cap is the one that trips. A tool-cap case, if the suite defines one, does the reverse.
- Never use one limit for both: a model call, a tool call and a super-step are different units.
- Cap spike (binding spike; runs before build-guide Step 4; failure path: fix this binding). Pass tests: (a) tool cap 2: the model requests 1 call, the agent pauses for approval, the worker resumes, the model then requests 2 more calls: `ToolCapExceeded` is raised on the 3rd cumulative call and neither of the 2 extra calls executed; (b) step cap N: exactly N model calls happen, then `StepCapExceeded`; (c) 3 parallel requested calls under cap 2 execute none of them; (d) the counters are 0 at the start of the next new turn on the same `thread_id`; (e) the exception reaches the worker from both hooks.
- Abort spike (binding spike; failure path: fix this binding): abort a turn mid-way (the tool cap, then a wall-clock timeout during a tool call), then run a follow-up turn on the same `thread_id` after the turn-start repair, against the real provider; the follow-up must succeed.

## Model provider
- Selection rule: when the spec's route names a single provider, use `init_chat_model("provider:model")` (or pass the same string as `model=` to `create_agent`); when it names a router, proxy or LiteLLM route, use `ChatLiteLLM(model=<spec route>)` from `langchain-litellm` (the models page recommends the dedicated LiteLLM integration over `init_chat_model` for LiteLLM, because router and proxy fields may be dropped; maintainer unverified). Source: https://docs.langchain.com/oss/python/langchain/models
- Format conversion: LiteLLM routes are `provider/model`, `init_chat_model` takes `provider:model`; split on the first `/` and rejoin with `:`, then check the provider id is one `init_chat_model` knows (LiteLLM and LangChain provider names can differ; some providers need `model_provider=` as a separate argument, per the models page; inference for the mapping).

## Telemetry
- Install `langsmith[otel]`, set `LANGSMITH_OTEL_ENABLED=true` and `LANGSMITH_OTEL_ONLY=true`, and point `OTEL_EXPORTER_OTLP_*` at the design's backend. `OTEL_EXPORTER_OTLP_ENDPOINT` is a base URL (no `/v1/traces`). Source: https://docs.langchain.com/langsmith/trace-with-opentelemetry.md
- The worker opens one per-turn span (for example `agent.turn`) carrying the spec's attributes and the turn outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`; names follow the spec). A turn that spans a HITL pause is one span per invocation linked by the turn id (inference).
- MANDATORY SPIKE before the build relies on it, with a REAL model call (fakes report no usage): emit one turn and confirm the backend receives `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` with values above zero. The docs show how LangSmith reads those attributes on ingest but do not state what the SDK emits (unverified). If they do not arrive, add fallback spans: a small custom `AgentMiddleware` whose `after_model` hook (https://docs.langchain.com/oss/python/langchain/middleware/custom ) opens a child span of `agent.turn` and sets those attributes from `AIMessage.usage_metadata` of the last message (inference). Failure path: the fallback middleware; if even that yields no usage, record the gap in `build.md` and raise it as a telemetry re-entry on the design.
- Set `LANGSMITH_TRACING=true` only together with `LANGSMITH_OTEL_ONLY=true` when the design's telemetry backend is not LangSmith. The page's LangChain setup sets `LANGSMITH_OTEL_ENABLED` and `LANGSMITH_TRACING` together, calls the default hybrid tracing and says `LANGSMITH_OTEL_ONLY` sends traces "only" to your OTEL endpoint; it does not say whether `LANGSMITH_TRACING` is required for OTel export, and that OTEL_ONLY stops all LangSmith traffic is inference from "only". Source: https://docs.langchain.com/langsmith/trace-with-opentelemetry.md
- Egress check (part of the telemetry spike): pass test = no request reaches api.smith.langchain.com (or its regional hosts) while a turn is traced; failure path: unset `LANGSMITH_TRACING` and re-run; if egress persists, raise a telemetry re-entry on the design.

## Eval runner mapping
- Fresh agent and a fresh `InMemorySaver` per test, passed as `checkpointer=` (inference: the testing page uses `InMemorySaver` in tests; per-test isolation is the binding's own rule). Source: https://docs.langchain.com/oss/python/langchain/test/unit-testing.md
- Model double: `GenericFakeChatModel` scripted with `AIMessage` objects carrying `tool_calls` (name, args, id) and replies; each model call consumes the next item. Source: https://docs.langchain.com/oss/python/langchain/test/unit-testing.md
- Capture source: run the agent with `stream_mode="updates"` and `version="v2"` (needs LangGraph 1.1 or later; each chunk has `type`, `ns` and `data`, and `data` maps the node name to that node's update). Source: https://docs.langchain.com/oss/python/langchain/streaming
  - Trajectory = the REQUESTED calls: `(tool name, args)` from the `tool_calls` of the AI messages in the `model` node's updates, in order. This includes calls the HITL gate rejected or the cap blocked.
  - `forbidden` is checked against the EXECUTED calls (the tool messages from the `tools` node's updates) plus the reply text (`skills/build/references/adapter-bindings.md`). One rule, no per-case guessing.
- The PIPELINE runner implements EXACT, IN_ORDER and ANY_ORDER itself over the trajectory list, with `args_subset` matching (the golden-format: expected args must be a subset of actual args; never full-argument equality). The agentevals evaluators (`create_trajectory_match_evaluator`: strict, unordered, subset, superset; no in-order-with-extras mode; default argument matching is exact) are optional references only. Source: https://docs.langchain.com/oss/python/langchain/test/evals.md
- Approvals in a case: the fixture's approvals enter the worker handler as decision messages, answered by the worker's decisions-list builder (see HITL gate).
- `harness_condition.force_step_cap` = a fake model that never gives a final answer (see Caps); `tool_always_errors` = the tool's injected BACKEND double raises and the real tool returns the spec's error observation (build-guide Step 5); the tool surface never changes (inference). The runner drives the worker's single turn handler (dequeue logic, expiry, repair, resume-or-end, cap mapping) against the in-memory saver and an in-memory repository, never the compiled graph's run call directly, so the deny, expiry and cap branches match production (inference).
- Tool-surface preflight: the eval runner and a permanent CI unit test assert that the first model request's tool names equal the spec's tool set (plus any built-in kept on purpose, each with its reason in `build.md`); the fake model must not change the tool surface. Observed with a recording `wrap_model_call` middleware that calls through to the handler (https://docs.langchain.com/oss/python/langchain/middleware/custom ; that the request exposes tool names is confirmed in the first spike).
- pass^k is computed by the pipeline runner; it is not native to the stack (research file `docs/superpowers/research/2026-10-07-stack-catalog/langchain-family.md`).

## A2A and MCP
- Two A2A paths; record which one in interop.md.
  - (a) Licensed LangSmith Agent Server `/a2a/{assistant_id}`: A2A v1.0 JSON-RPC, push notifications not supported, the graph state must include a `messages` key (the `create_agent` state includes a sequence of messages, https://docs.langchain.com/oss/python/langchain/agents ). Source: https://docs.langchain.com/langsmith/server-a2a.md ; a standalone server needs `LANGGRAPH_CLOUD_LICENSE_KEY` and reaches beacon.langchain.com for license verification and usage reporting (unless air-gapped). Source: https://docs.langchain.com/langsmith/deploy-standalone-server.md
  - (b) Own server built with `a2a-sdk` that wraps the agent and persists interrupted state through the checkpointer (own code, inference; a build option only when a license is acceptable or A2A is not a hard filter). Source for the licensed alternative: https://docs.langchain.com/langsmith/server-a2a.md
- MCP client: `langchain[mcp]` with a minimum of 1.4.0 (the pin satisfies it), `from langchain.mcp import MCPAdapter`; use `async with MCPAdapter(url) as adapter: tools = await adapter.list_tools()` and pass `tools` to `create_agent`. ## Pinned version and traps
- Every package below gets an exact pin in the lockfile. Any ">=" in this text is a minimum, never a requirement spec.
  - `langchain==1.4.3` (released 2026-09-28; https://pypi.org/project/langchain/ ). Its declared dependencies are `langgraph>=1.2.11,<1.3.0` and `langchain-core>=1.6.3,<2.0.0` (https://pypi.org/pypi/langchain/1.4.3/json ): pin both exactly in the lockfile.
  - `langgraph==1.2.14` (the latest release when verified, 2026-10-06; https://pypi.org/project/langgraph/ )
  - `langchain-core` (exact pin inside the range above)
  - `langgraph-checkpoint-postgres`, `psycopg[pool]` (the install command in https://docs.langchain.com/oss/python/langgraph/add-memory is `psycopg[binary,pool]`; choose per the base image)
  - `langchain-litellm` (only for the LiteLLM route), `langsmith[otel]` (docs: minimum 0.3.18, recommended 0.4.25 or later), one provider package such as `langchain-anthropic` or `langchain-openai` for the chosen provider
  - `fastmcp` (only with the `langchain[mcp]` extra; the extra declares `>=4.0.1,<5.0.0`)
  - `langgraph-checkpoint-aws` (only when DynamoDB is chosen), `a2a-sdk` (only for A2A path b)
- Obligation (ops): the interrupted node re-runs on resume, so code before the interrupt is idempotent. Source: https://docs.langchain.com/oss/python/langgraph/interrupts
- Obligation (ops): the built-in call-limit run counters are per invocation and restart on a HITL resume, so both caps live in the binding's `TurnCaps` middleware, and the worker maps its two exceptions to the spec's single failure reply. Sources: https://docs.langchain.com/oss/python/langchain/middleware/built-in , https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/tool_call_limit.py
- Obligation (ops): the OSS library has no per-thread locking and double-texting is not available there; the adapter queue (key = `thread_id`) serializes turns. Source: https://docs.langchain.com/langsmith/double-texting.md
- Obligation (data): set `LANGSMITH_TRACING=true` only together with `LANGSMITH_OTEL_ONLY=true` when LangSmith is not the chosen backend, and prove no request reaches api.smith.langchain.com in the telemetry spike. Source: https://docs.langchain.com/langsmith/trace-with-opentelemetry.md
