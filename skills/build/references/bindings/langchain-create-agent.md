# LangChain create_agent - build binding

Facts below cite the same sources as the card (`skills/design/references/stacks/langchain-create-agent.md`) and the research file `docs/superpowers/research/2026-10-07-stack-catalog/langchain-family.md`; a URL is repeated where a rule depends on it. This file is self-contained: the shared LangGraph facts are restated in full. Statements marked inference are the binding's own reasoning; statements marked unverified are not confirmed by a page or the library source, and a spike below confirms them on the pinned version.

Shape: one compiled agent from `create_agent`, built by `build_agent(model, checkpointer, tools, caps)` in `src/agent/`. The `middleware` list is `HumanInTheLoopMiddleware`, `ModelCallLimitMiddleware` and `ToolCallLimitMiddleware` (plus the optional telemetry fallback middleware); `checkpointer=` takes the injected saver. `caps` carries the two per-turn limits so the worker can rebuild the agent with a smaller remaining budget (see Caps). This replaces a hand-written model-tool loop and `langgraph.prebuilt.create_react_agent` (the v1 guide now recommends `create_agent`; it does not call the old function deprecated). The adapter constructs `PostgresSaver` / `AsyncPostgresSaver` (or the DynamoDB saver) in `adapters/<target>/` and injects it; `src/agent/` never imports psycopg or the saver packages. The checkpointer holds only conversation/graph state. Dedupe and the spec's data schemas live in repository tables behind the repository interface, not in agent state. Sources: https://docs.langchain.com/oss/python/langchain/agents and https://docs.langchain.com/oss/python/migrate/langchain-v1.md

## Sessions and state
- `create_agent(..., checkpointer=<saver>)` plus `{"configurable": {"thread_id": <session key>}}` in the config is how the agent gets persistence. Source: https://docs.langchain.com/oss/python/langchain/short-term-memory
- Postgres: `PostgresSaver` / `AsyncPostgresSaver` from `langgraph-checkpoint-postgres`. Source: https://docs.langchain.com/oss/python/langgraph/checkpointers.md
- Saver kind follows the worker: an async worker uses `AsyncPostgresSaver` and `ainvoke` / `astream`; a sync worker uses `PostgresSaver` and `invoke` / `stream` (inference; the persistence page names both savers: https://docs.langchain.com/oss/python/langgraph/persistence ).
- A connection you create yourself must use `autocommit=True` and `row_factory=dict_row` (autocommit makes `.setup()` persist the tables; the saver reads columns by name). Source: https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md
- `.setup()` runs once, as a named one-shot migration job (`agent-migrate`: compose service / ECS task / Cloud Run job), never from the worker and never per request. The short-term-memory page shows `checkpointer.setup()` inline next to `create_agent`; do not copy that into the worker. Source for the call: https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md
- Durability: pass `durability="sync"` on every agent call (persists changes before the next step starts; default is "async"). The parameter is documented on the LangGraph `invoke`: https://reference.langchain.com/python/langgraph/pregel/main/Pregel/invoke ; that `create_agent`'s compiled graph accepts it on `stream`, `ainvoke` and `astream` is unverified (inference: it is a compiled LangGraph graph), so confirm it in the first spike. The modes are described at https://docs.langchain.com/oss/python/langgraph/checkpointers.md
- `thread_id` = the spec's session key; keep it under 255 characters on Postgres. Source: https://docs.langchain.com/oss/python/langgraph/persistence
- Queue ordering key = `thread_id` (the session key), so one turn per thread holds even when the approver is a different sender. Ingress resolves an approver's reply to the pending session's key before enqueueing. The OSS library has no per-thread locking and double-texting is not available there. Source: https://docs.langchain.com/langsmith/double-texting.md
- Do not use `thread_limit` on either call-limit middleware: it persists across turns of a thread, so it is not a per-turn cap (see Caps).
- Supabase connection: use the direct connection or the Supavisor session mode (port 5432); never the transaction pooler (port 6543), which does not support prepared statements (psycopg3 uses them by default, inference). Source: https://supabase.com/docs/guides/database/connecting-to-postgres
- Supabase schema: put the checkpoint tables in a schema not exposed through the Data API (for example `agent_state`, selected via the connection's search_path; the wiring is unverified) and enable RLS on them. Source: https://supabase.com/docs/guides/database/postgres/row-level-security
- Supabase Free plan: projects are paused after 1 week of inactivity, so it is not for production. Source: https://supabase.com/pricing
- DynamoDB: `langgraph-checkpoint-aws` provides the checkpointer (the class is named DynamoDBSaver in the research file; the docs page lists only the package). The same page also lists a separate community package, `langgraph-dynamodb-checkpoint` (agentstate); prefer the AWS package. Source: https://docs.langchain.com/oss/python/integrations/checkpointers/index.md
- Firestore: no official checkpointer (a community package is listed, unverified for production). Source: https://docs.langchain.com/oss/python/integrations/checkpointers/index.md . If the design names Firestore, STOP and raise a re-entry on the design's sessions seam; do not swap the store silently.
- Spikes (each runs before build-guide Step 4). A failed store spike STOPS and raises a re-entry on the design's sessions seam, never a silent store swap; the other spikes state their own failure path:
  - Supabase (store spike): after `.setup()` with the chosen search_path the tables exist in `agent_state` and not in `public`; then `ENABLE ROW LEVEL SECURITY` on them; a put/get round trip works as the saver's DB role.
  - DynamoDB (store spike): the pinned package imports the named saver class and a put/get round trip works against the target table.
  - Durability (store spike): `durability="sync"` is accepted by the exact call the worker uses (`invoke`, `ainvoke`, `stream` or `astream`) on the compiled `create_agent` graph.
  - Pending interrupt (pass test: after a gated tool call pauses the agent, `agent.get_state(config)` exposes the pending interrupt via `state.tasks[*].interrupts` and the payload carries `action_requests`; failure path: fix this binding and the worker's check, not a sessions-seam re-entry). The call that raises the interrupt also reports it in its own result (`__interrupt__` key, or `.interrupts` with `version="v2"`), but the worker needs the check on a later dequeue.
  - Resume payload (pass test: for one gated call, `Command(resume={"decisions": [{"type": "approve"}]})` runs the tool once; a reject decision runs it zero times and the agent receives the rejection; an edit decision runs the tool with the edited args; failure path: fix this binding).

## HITL gate
- Recommended placement: `HumanInTheLoopMiddleware` in the `middleware` list, configured from the spec's tool tiers (below). It pauses the agent after the model proposes a gated tool call and before the tool executes, and needs a durable checkpointer plus a `thread_id`. Source: https://docs.langchain.com/oss/python/langchain/human-in-the-loop
- Worker sequence:
  1. Dequeue the message for the session (ordering key `thread_id`).
  2. Read `agent.get_state(config)` for that `thread_id` and check for a pending interrupt (inference, unverified for `create_agent`: pending interrupts appear on the snapshot as `state.tasks[*].interrupts`; the pending-interrupt spike confirms it).
  3. If an approval is pending: parse the message (or the approver's reply) into a decision and resume with `Command(resume={"decisions": [...]})` on the same `thread_id`. Otherwise start a new turn with fresh input.
- Decision value. The spec's three outcomes map to the documented payloads, one entry per `action_requests` item, in the same order as the interrupt lists them. Source: https://docs.langchain.com/oss/python/langchain/human-in-the-loop
  - approve -> `{"type": "approve"}`
  - deny -> `{"type": "reject", "message": "<reason>"}` (`message` is optional; a default is used if omitted)
  - edit -> `{"type": "edit", "edited_action": {"name": "<tool>", "args": {...}}}`; keep edits conservative, because large changes may make the model re-plan.
  - The documented `respond` type returns a human reply as a successful tool result and the page says not to use it to deny side-effecting tools: the binding never uses it.
  - Reply covering several gated calls (design choice, inference): one approve or deny reply applies to every pending action, `edit` is accepted only when exactly one action is pending, and the worker builds the list so its length equals the number of `action_requests`. If several interrupts are pending at once (parallel branches), the resume value is a map from interrupt id to its answer: https://docs.langchain.com/oss/python/langgraph/interrupts ; the streaming page shows the same id-keyed form for HITL (https://docs.langchain.com/oss/python/langchain/streaming ); confirm which form applies in the resume-payload spike.
- Deny: the model receives the rejection for that call and continues; if the spec says a deny ends the turn with a fixed reply, the worker replaces the final reply with the spec's deny reply and records the outcome `hitl_denied`. A denied call still counts as a requested tool call for the tool cap (it was requested; see Caps).
- If a message for a pending session does not parse as a decision: keep the interrupt pending and reply with the spec's pending-approval prompt (or deny if the spec says so). Expiry is evaluated when the next message for that session is dequeued (intended; a sweep is optional).
- Expiry: the worker records the time it sent the approval prompt in the repository; when the next message for the session is dequeued and the approval is older than the spec's TTL, the worker resumes it with reject decisions (message "approval expired"), records the outcome `hitl_expired`, then handles the new message as a new turn (inference).
- Tier mapping, built from the spec's tool contracts into `interrupt_on`: destructive -> `{"allowed_decisions": ["approve", "reject"]}` every time, never cached (no edit, no respond); reversible -> per design policy (`["approve", "edit", "reject"]`, or a `when` predicate on the tool call request, which needs `langchain>=1.3.3` and is satisfied by the pin); safe -> `False`. List every tool explicitly; do not rely on unlisted tools defaulting to auto-approve (the page does not state the default for an unlisted tool; unverified). Source: https://docs.langchain.com/oss/python/langchain/human-in-the-loop
- Idempotency: the interrupted node restarts from its beginning on resume, so any code before the interrupt in that node runs again; keep it idempotent (the HITL middleware's own pre-interrupt work only inspects the model's message, inference). Gated tools run only after approval, so a destructive tool body never runs before the pause. Interrupts are matched to resume values by position: never reorder them. Do not wrap interrupt-raising code in a bare try/except. Source: https://docs.langchain.com/oss/python/langgraph/interrupts
- Eval runner: when the run returns an interrupt (`__interrupt__` key in the result or stream, or `.interrupts`), the runner resolves it by calling `Command(resume={"decisions": [<next approval in the case fixture, mapped as above>]})` on the same `thread_id`, until the agent finishes or the fixture runs out.

## Caps
- The two caps are two middlewares with two limits, always counted separately: `ModelCallLimitMiddleware(run_limit=<spec step cap>, exit_behavior="error")` and `ToolCallLimitMiddleware(run_limit=<spec tool-call cap>, exit_behavior="error")` (global, no `tool_name`). Source: https://docs.langchain.com/oss/python/langchain/middleware/built-in
- Why `error` and not `end`: `ToolCallLimitMiddleware` with `exit_behavior="end"` works only when limiting a single tool and raises NotImplementedError if other tools have pending calls, so it cannot be a global cap; `continue` lets the model keep going. `ModelCallLimitMiddleware` has only `end` and `error`; its `end` emits an AI message that starts with "Model call limits exceeded:" (read in the library source on master) that the worker would have to detect by text, so `error` is used there too and the worker maps the exceptions. Sources: https://docs.langchain.com/oss/python/langchain/middleware/built-in , https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/model_call_limit.py
- Both caps are PER TURN, reset at turn start: `run_limit` is per single invocation ("one user message -> response cycle", it resets with each new user message). The run counters are private untracked state, so a new invocation starts at zero (library source on master; the docs say "per single invocation"). Sources: https://docs.langchain.com/oss/python/langchain/middleware/built-in , https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/tool_call_limit.py
- HITL resume caveat (inference): a resume after approval is a second invocation of the same spec turn, so the run counters may restart at zero. The worker therefore keeps a per-turn tally of model calls and requested tool calls (from the captured stream; see Eval runner mapping) in the repository, and on resume builds the agent with `caps` = spec cap minus the tally already used. If the cap spike shows the counters do not restart on resume, drop this rebuild and pass the full caps.
- Tool-call cap counting: the library source on master counts in the `after_model` hook from the last AI message's requested calls (parallel calls in one message are checked in order against the limit), i.e. each tool call requested, before any tool executes, so parallel calls cannot overshoot; blocked calls still count toward the run total. The docs page does not state this timing: treat it as unverified until the cap spike confirms it on `langchain==1.4.3`. Source: https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/tool_call_limit.py
- Step cap: `ModelCallLimitMiddleware` checks `count >= run_limit` in `before_model`, before each model call, so `run_limit=N` allows N model calls and trips before call N+1 (library source on master). Source: https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/model_call_limit.py
- Unit conversion (inference): define the spec's step as one model call (one pass of model -> tools); `run_limit` = spec step cap, 1:1. The final answer is also a model call, so a turn that uses all N calls on tools has no call left to answer and trips the cap; record this definition in `build.md`. LangGraph's `recursion_limit` counts super-steps, not model calls, so it is not the step cap here: set it above the middleware limits (each loop iteration costs several super-steps once middleware nodes are counted, factor unverified; measure it in the cap spike) so the middleware trips first, and catch `GraphRecursionError` as a backstop mapped to the same reply and the outcome `step_cap`. Source for `recursion_limit` and the error: https://docs.langchain.com/oss/python/langgraph/graph-api
- Exits: the worker catches `ModelCallLimitExceededError` -> outcome `step_cap`, `ToolCallLimitExceededError` -> outcome `tool_call_cap`, and wall-clock expiry -> outcome `wall_clock`. All three produce the spec's single failure reply; the middleware's own message text is never sent to the user.
- Thread repair after an aborted turn (inference): `ToolCallLimitExceededError` is raised in `after_model`, after the model's message with tool calls was committed, so the thread can end on an AI message whose tool calls have no tool results (a wall-clock abort can do the same). Most providers reject such a history (https://docs.langchain.com/oss/python/langchain/short-term-memory ). Before the thread is reused the worker appends one `ToolMessage` per dangling tool call (content: the cap or timeout notice) with `agent.update_state(config, {"messages": [...]})`. The cap spike proves a follow-up turn works.
- Wall-clock cap: the worker bounds each turn, including the time spent on resume, with the spec's wall-clock limit (timeout around the agent call); expiry produces the same failure reply and the outcome `wall_clock`.
- `harness_condition.force_step_cap`: use a fake model that never gives a final answer (a cycling `GenericFakeChatModel` iterator emitting one safe tool call per message, inference) and set the tool-call cap above the step cap, so the model-call cap is the one that trips. A matching `force_tool_cap` case does the reverse.
- Never use one limit for both: a model call, a tool call and a super-step are different units.
- Cap spike (runs before build-guide Step 4; failure path: fix this binding, not a sessions-seam re-entry). Pass tests: (a) a fake model emitting 3 parallel tool calls under `run_limit=2` executes none of them and raises `ToolCallLimitExceededError` (confirms counting before execution; if it executes some, switch to the binding's own counter in a custom middleware and record it); (b) the model cap raises `ModelCallLimitExceededError` after exactly N calls; (c) after each exit and after the thread repair, a follow-up turn on the same `thread_id` succeeds; (d) the counters across a HITL pause and resume behave as the caveat above assumes; (e) the middleware order that passes (a)-(d) together with the HITL middleware is the order recorded in `build.md` (the order of after-model hooks across middleware is unverified).

## Model provider
- Selection rule: when the spec's route names a single provider, use `init_chat_model("provider:model")` (or pass the same string as `model=` to `create_agent`); when it names a router, proxy or LiteLLM route, use `ChatLiteLLM(model=<spec route>)` from `langchain-litellm` (the models page recommends the dedicated LiteLLM integration over `init_chat_model` for LiteLLM, because router and proxy fields may be dropped; maintainer unverified). Source: https://docs.langchain.com/oss/python/langchain/models
- Format conversion: LiteLLM routes are `provider/model`, `init_chat_model` takes `provider:model`; split on the first `/` and rejoin with `:`, then check the provider id is one `init_chat_model` knows (LiteLLM and LangChain provider names can differ; some providers need `model_provider=` as a separate argument, per the models page; inference for the mapping).

## Telemetry
- Install `langsmith[otel]`, set `LANGSMITH_OTEL_ENABLED=true` and `LANGSMITH_OTEL_ONLY=true`, and point `OTEL_EXPORTER_OTLP_*` at the design's backend. `OTEL_EXPORTER_OTLP_ENDPOINT` is a base URL (no `/v1/traces`). Source: https://docs.langchain.com/langsmith/trace-with-opentelemetry.md
- The worker opens one per-turn span (for example `agent.turn`) carrying the spec's attributes and the turn outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`; names follow the spec). A turn that spans a HITL pause is one span per invocation linked by the turn id (inference).
- MANDATORY SPIKE before the build relies on it, with a REAL model call (fakes report no usage): emit one turn and confirm the backend receives `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` with values above zero. The docs show how LangSmith reads those attributes on ingest but do not state what the SDK emits (unverified). If they do not arrive, add fallback spans: a small custom `AgentMiddleware` whose `after_model` hook (the v1 guide documents `before_model` / `after_model`: https://docs.langchain.com/oss/python/migrate/langchain-v1.md ) opens a child span of `agent.turn` and sets those attributes from `AIMessage.usage_metadata` of the last message (inference). Failure path: the fallback middleware; if even that yields no usage, record the gap in `build.md` and raise it as a telemetry re-entry on the design.
- Never set `LANGSMITH_TRACING` unless the design's telemetry backend is LangSmith (the docs examples pair it with the LangSmith endpoint). Source: https://docs.langchain.com/langsmith/trace-with-opentelemetry.md

## Eval runner mapping
- Fresh agent and a fresh `InMemorySaver` per test, passed as `checkpointer=`. Source: https://docs.langchain.com/oss/python/langchain/test/unit-testing.md
- Model double: `GenericFakeChatModel` scripted with `AIMessage` objects carrying `tool_calls` (name, args, id) and replies; each model call consumes the next item. Source: https://docs.langchain.com/oss/python/langchain/test/unit-testing.md
- Capture source: run the agent with `stream_mode="updates"` and `version="v2"` (needs LangGraph 1.1 or later; each chunk has `type`, `ns` and `data`, and `data` maps the node name to that node's update). Collect `(tool name, args)` from the `tool_calls` of the AI messages in the `model` node's updates, in order. These are the REQUESTED calls, including calls the HITL gate rejected or the cap blocked; if a golden case means executed calls only, keep only the calls that have a matching `ToolMessage` from the `tools` node (inference). Source: https://docs.langchain.com/oss/python/langchain/streaming
- The PIPELINE runner implements EXACT, IN_ORDER and ANY_ORDER itself over that captured list, with `args_subset` matching (the golden-format: expected args must be a subset of actual args; never full-argument equality). The agentevals evaluators (`create_trajectory_match_evaluator`: strict, unordered, subset, superset; no in-order-with-extras mode; default argument matching is exact) are optional references only. Source: https://docs.langchain.com/oss/python/langchain/test/evals.md
- `harness_condition.force_step_cap` = a fake model that never gives a final answer (see Caps); `tool_always_errors` = a tool that always raises or returns an error message (inference).
- pass^k is computed by the pipeline runner; it is not native to the stack (research file `docs/superpowers/research/2026-10-07-stack-catalog/langchain-family.md`).

## A2A and MCP
- Two A2A paths; record which one in interop.md.
  - (a) Licensed LangSmith Agent Server `/a2a/{assistant_id}`: A2A v1.0 JSON-RPC, push notifications not supported, the graph state must include a `messages` key (the `create_agent` state includes a sequence of messages, https://docs.langchain.com/oss/python/langchain/agents ). Source: https://docs.langchain.com/langsmith/server-a2a.md ; a standalone server needs `LANGGRAPH_CLOUD_LICENSE_KEY` and reaches beacon.langchain.com for license verification and usage reporting (unless air-gapped). Source: https://docs.langchain.com/langsmith/deploy-standalone-server.md
  - (b) Own server built with `a2a-sdk` that wraps the agent and persists interrupted state through the checkpointer (own code, inference; a build option only when a license is acceptable or A2A is not a hard filter). Source for the licensed alternative: https://docs.langchain.com/langsmith/server-a2a.md
- MCP client: `langchain[mcp]` with a minimum of 1.4.0 (the pin satisfies it), `from langchain.mcp import MCPAdapter`; use `async with MCPAdapter(url) as adapter: tools = await adapter.list_tools()` and pass `tools` to `create_agent`. The namespace is beta (import raises a beta warning, the API may change) and succeeds langchain-mcp-adapters. The extra pulls `fastmcp`. Sources: https://docs.langchain.com/oss/python/langchain/mcp , https://pypi.org/pypi/langchain/1.4.3/json
- Serving MCP (`/mcp`) is documented on Agent Server; no OSS-library endpoint is documented. Source: https://docs.langchain.com/langsmith/server-mcp.md

## Pinned version and traps
- Every package below gets an exact pin in the lockfile. Any ">=" in this text is a minimum, never a requirement spec.
  - `langchain==1.4.3` (released 2026-09-28; https://pypi.org/project/langchain/ ). Its declared dependencies are `langgraph>=1.2.11,<1.3.0` and `langchain-core>=1.6.3,<2.0.0` (https://pypi.org/pypi/langchain/1.4.3/json ): pin both exactly in the lockfile.
  - `langgraph==1.2.14` (the latest release when verified, 2026-10-06; https://pypi.org/project/langgraph/ )
  - `langchain-core` (exact pin inside the range above)
  - `langgraph-checkpoint-postgres`, `psycopg[pool]` (the install command in https://docs.langchain.com/oss/python/langgraph/add-memory is `psycopg[binary,pool]`; choose per the base image)
  - `langchain-litellm` (only for the LiteLLM route), `langsmith[otel]` (docs: minimum 0.3.18, recommended 0.4.25 or later), one provider package such as `langchain-anthropic` or `langchain-openai` for the chosen provider
  - `fastmcp` (only with the `langchain[mcp]` extra; the extra declares `>=4.0.1,<5.0.0`)
  - `langgraph-checkpoint-aws` (only when DynamoDB is chosen), `a2a-sdk` (only for A2A path b)
- Obligation (ops): the interrupted node re-runs on resume, so code before the interrupt is idempotent. Source: https://docs.langchain.com/oss/python/langgraph/interrupts
- Obligation (ops): `ToolCallLimitMiddleware` is global with `exit_behavior="error"`, never `end` (single tool only), and the worker maps both limit exceptions to the spec's single failure reply. Source: https://docs.langchain.com/oss/python/langchain/middleware/built-in
- Obligation (ops): the OSS library has no per-thread locking and double-texting is not available there; the adapter queue (key = `thread_id`) serializes turns. Source: https://docs.langchain.com/langsmith/double-texting.md
- Obligation (data): do not set `LANGSMITH_TRACING` unless LangSmith is the chosen backend; use `LANGSMITH_OTEL_ONLY` for OTel-only export. Source: https://docs.langchain.com/langsmith/trace-with-opentelemetry.md
- Obligation (churn): `langchain.mcp` is beta and replaced langchain-mcp-adapters, so isolate it behind the tools adapter and re-run its spike on any upgrade. Source: https://docs.langchain.com/oss/python/langchain/mcp
- Obligation (churn): do not import legacy chains, retrievers or the indexing API from `langchain`; they moved to langchain-classic in v1, and new code does not need them. Source: https://docs.langchain.com/oss/python/migrate/langchain-v1.md
