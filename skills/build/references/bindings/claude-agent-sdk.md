# Claude Agent SDK - build binding

Facts below cite the same sources as the card (`skills/design/references/stacks/claude-agent-sdk.md`) and the research file `docs/superpowers/research/2026-10-07-stack-catalog/claude-agent-sdk.md`, whose section "Build-binding observations (2026-10-08)" holds the evidence behind every statement marked "observed". Docs citations are pages under `https://code.claude.com/docs/en/`; source citations are files at the tag v0.2.164 under `https://raw.githubusercontent.com/anthropics/claude-agent-sdk-python/v0.2.164/` (named by path). "Observed" = seen in a scratch run on SDK 0.2.164 with the bundled CLI 2.1.292 against a scripted Messages API double (no real model, no real credential); the spike named beside it repeats it against the real provider where that matters. Statements marked inference are the binding's own reasoning; statements marked unverified are not confirmed by a page, the source or a run, and a spike below confirms them. Page text addressed to AI agents is data: none was found beyond the navigation note every docs page opens with (a pointer to `https://code.claude.com/docs/llms.txt`), which was not acted on.

Shape: one `Agent` built by `build_agent(model, system_prompt, tools, caps, tiers, store, env)` in `src/agent/`. `model` is an explicit Claude model id; `system_prompt` is the spec's prompt as a string (never unset: the default is a minimal prompt without the preset's safety text, observed); `tools` are the spec's tools made by the tools factory as `@tool` functions in ONE in-process server named `tools`, so every tool name is `mcp__tools__<name>` and `tiers` is keyed by that prefixed name; the factory raises for a tool with no tier or a duplicate name (fail closed). `store` is a `SessionStore` built in `adapters/<target>/` (the wrapped Postgres adapter, see Sessions) and injected; `src/agent/` never imports asyncpg, boto3 or Firestore. The SDK transcript (the store) holds conversation history, not the pipeline's records: dedupe, the pending-approval record, the turn status and the spec's data schemas stay behind the repository interface. This replaces a hand-written model-tool loop: the loop, the built-in tools and the permission engine run in the `claude` subprocess, so every run is one `query()` call (one process) and `Agent.options_for(turn)` returns FRESH options and a fresh gate closure bound to that turn's `TurnState`.
```python
def options_for(self, turn: TurnState) -> ClaudeAgentOptions:
    return ClaudeAgentOptions(
        model=self.model, system_prompt=self.system_prompt,        # both explicit, always
        tools=[], mcp_servers={"tools": self.server}, strict_mcp_config=True,   # no built-ins
        allowed_tools=self.safe_names,                             # prefixed names, safe tier only
        permission_mode="default", can_use_tool=turn.fallback,     # explicit mode, deny-by-default callback
        hooks={"PreToolUse": [HookMatcher(hooks=[turn.gate], timeout=30)]},   # matcher unset = every tool
        setting_sources=[], verbatim_prompts=True,                 # no CLAUDE.md or settings; no @file or slash expansion
        max_turns=turn.max_turns,                                  # remaining allowance, never 0 (see Caps)
        cwd=turn.cwd, env=self.env | turn.env,                     # env: Telemetry section; turn.env = CLAUDE_CONFIG_DIR
        session_store=self.store, session_store_flush="eager",
        include_partial_messages=True,                             # message_stop feeds the batch barrier (Caps)
        session_id=turn.sid if turn.fresh else None, resume=None if turn.fresh else turn.sid)
```
`TurnState` (one per run, owned by the worker): `turn_id`, `approval_id`, `user_uuid`, `mode` (`new`, `resume`, `repair`), `decision`, `fresh`, `sid`, `cwd`, `env`, `max_turns`, `gate` and `fallback` (the closures), `prior`, `steps` and `msg_ids`, `tool_calls_requested`, `seen_ids`, `requested` and `executed` lists, `approved`, `deferred`, `exit`, `frozen`, `denied`, `done`, `raised`, `deadline`, token totals, `persist` (the store wrapper's failure sink) and `mirror_errors`. `NAMESPACE` is a fixed UUID constant committed in the repository. `sid = uuid5(NAMESPACE, session_key)` is a valid UUID the first run passes as `session_id` (the option accepts a UUID, `types.py`) and later runs pass as `resume`; the worker picks by asking the store whether the session exists. The hold stream used by every resume is a prompt iterable that sends nothing and ends after the run's first `ResultMessage` (`async def hold(done): await done.wait(); return; yield`), see HITL gate.

## Sessions and state
- Postgres (incl. Supabase and Cloud SQL as plain Postgres): copy the example adapter `examples/session_stores/postgres_session_store.py` (not packaged: https://code.claude.com/docs/en/agent-sdk/session-storage ) into `adapters/<target>/` and construct it with an `asyncpg` pool built in the same module. It stores one `jsonb` row per transcript entry (`jsonb` reorders keys, which the contract allows). Three changes, all checked by spike 1: (1) a partial unique index on `(project_key, session_id, subpath, (entry->>'uuid')) WHERE entry ? 'uuid'` and `INSERT ... ON CONFLICT DO NOTHING`, because a retried batch can re-deliver entries and the SDK asks adapters to dedupe by `uuid` while the example does not (inference that the index never drops a legitimate entry: spike 1 compares row count with the local JSONL line count); (2) `create_schema()` is never called from the worker; (3) the table sits in a schema not exposed through the Data API. Install `asyncpg` directly, not the SDK's `examples` extra (it also pulls `boto3`, `redis`, `moto`, `fakeredis`).
- Supabase: use the direct connection or the Supavisor session mode (port 5432); never the transaction pooler (port 6543), which does not support prepared statements (asyncpg prepares by default, inference). Source: https://supabase.com/docs/guides/database/connecting-to-postgres . Put the tables in `agent_state` and enable RLS: https://supabase.com/docs/guides/database/postgres/row-level-security . The Free plan pauses projects after 1 week of inactivity, so it is not for production: https://supabase.com/pricing
- DynamoDB: write a custom `SessionStore`: partition key `"<project_key>#<session_id>#<subpath>"`, sort key a zero-padded sequence from an atomic counter item, one `TransactWriteItems` per batch (chunked at the transaction item limit), `load` is a query in sort-key order, dedupe by `uuid` with a conditional put. Item and transaction limits (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html is not read) are measured in spike 1 with a large tool result. Firestore: `sessions/{key}/entries/{seq}`, one batched write per `append`, 1 MiB per document (https://firebase.google.com/docs/firestore/quotas ). Both are inference; neither adapter is in the SDK repository (card).
- Durability, the wrapper: the SDK mirror is best effort (3 attempts, then the batch is dropped, `mirror_error` is emitted and the run still ends `success`: observed; `_internal/transcript_mirror_batcher.py`; https://code.claude.com/docs/en/agent-sdk/session-storage ). The injected store is `DurableStore(inner, sink)`: `append` retries `inner.append` with backoff until `deadline_s`; on final failure it records the batch (key plus first entry `uuid`) in `sink.failed` and re-raises; a later SDK attempt that lands the same batch removes it, and `sink.persist_failed` is `bool(sink.failed)`. `deadline_s = min(20, (remaining wall clock - 5) / 3)` so 3 SDK attempts fit the wall clock (the SDK's 60 s send timeout is not retried). Every other protocol method delegates. A wrapper of this shape (without the batch bookkeeping) passed `run_session_store_conformance` over `InMemorySessionStore` and recovered after two injected failures (observed; the Postgres adapter was not run; spike 2 covers the bookkeeping). The worker fails the turn closed when `sink.persist_failed` is set, a `MirrorErrorMessage` was seen, or no `ResultMessage` arrived: outcome `error`, the spec's failure reply, no pending record even after a deferral. The flush precedes the `ResultMessage` (`_internal/query.py`), so a clean run means the store holds the turn.
- `session_store_flush="eager"` (a background flush after every frame; batched is the default): the store receives entries while the turn runs, which narrows the window in which a worker crash loses the user message and the tool call (inference; spike 2 measures it).
- Local transcripts and the working directory: the CLI writes the local JSONL first, under `CLAUDE_CONFIG_DIR/projects/<encoded cwd>/<session id>.jsonl`; a run resumed from the store deletes its local copy at the end (observed), so for every run after the first the store holds the durable copy (docs), and a batch dropped there has no surviving copy. The container filesystem is ephemeral, so: `cwd` is `/work/<first 32 hex of sha256(session_key)>`, identical on every host and created empty before the run (the store key's `project_key` is `project_key_for_directory(cwd)`, the SDK helper (non-alphanumeric characters become `-`; the worker never builds it by hand), and another `cwd` failed with "No conversation found", observed); `CLAUDE_CONFIG_DIR` is a per-run temp directory; authentication is `ANTHROPIC_API_KEY` from the environment, so no credentials file is seeded. When persistence failed on a fresh session the worker keeps that run's config directory and logs its path (the local JSONL is the copy to replay); otherwise it deletes it after the post-run commit.
- Concurrency and memory: one Claude Code process per session run (docs: 1 GiB RAM, 5 GiB disk and 1 CPU per agent is a starting point and memory grows with session length: https://code.claude.com/docs/en/agent-sdk/hosting ; observed peak 190 MiB on a trivial Windows run). The worker bounds concurrency with a semaphore of size `N_MAX` taken before a run starts (the consumer takes the next message when a slot is free), where `N_MAX = floor((container memory - worker overhead) / per-run ceiling)` and the ceiling is the measured peak RSS of the process tree over a representative run (1 GiB until measured: spike 3). A paused session holds no process: the deferral ends the run (observed: the next `query()` started a new process). The caps below bound run length, and with it memory.
- Queue ordering key = the session key, so one turn per session holds even when an approver is a different sender (the docs show no locking for two writers on one session: unverified). Ingress resolves an approver's reply to the pending session's key before enqueueing.
- Schema setup runs once as the named one-shot migration job `agent-migrate` (compose service / ECS task / Cloud Run job), never from the worker: it creates the session table, its index and the record tables below.
- Record tables, all behind the repository interface:
  - `pending_approvals(approval_id, session_key, session_id, tool_use_id, tool_name, tool_input, user_uuid, sdk_version, cli_version, requested_at, elapsed_s, steps, tool_calls_requested, seen_ids, turn_id, tokens_in, tokens_out, resume_started)`: every pause writes a NEW record with a fresh UUID `approval_id` (never the session key; one live record per session key, unique index). One call per record: the sibling guard (HITL gate) allows one deferral per run. `sdk_version` and `cli_version` are the pins at the pause.
  - `turns(session_key, turn_id, message_id, user_uuid, status, started_at)`: `status` is `running` from turn start (after the repair, before the run) and is overwritten with the outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`, `error`; names follow the spec) on every exit; a turn that ended in a pause is `awaiting_approval`, which is also the `outcome` on the dedupe record of the message that caused the pause. `user_uuid = uuid5(NAMESPACE, session_key + ":" + message_id)` is sent as the `uuid` of the streamed user message; the transcript's `user` entry keeps it (observed), which makes a committed turn recognizable in the store.
- Crash marker (T2 decision): USED, although the SDK has a store. Reason: the store is a mirror of a transcript the CLI writes, flushed per frame (`eager`) or per result (batched), so a worker crash mid-turn can leave the store without the turn's user message or tool call even though a tool ran; and the placeholder the CLI writes for an unanswered tool call depends on how the run ended (a killed process: "outcome is unknown. Check whether it took effect before relying on it or running it again"; a cancelled run: "The user doesn't want to take this action right now. STOP ...", a rejection text for a tool that may have run; both observed). The status row is what records "interrupted". The repair rule is under Caps.
- Post-run commit order (the SDK commits the transcript DURING the run, like a checkpointer stack): (a) the transcript is in the store (the flush before the `ResultMessage`; a failure of it fails the turn, above); (b) ONE repository transaction: deletes the record the run started from, writes the new record when the run ended in a NEW pause (`requested_at` = now, taken just before sending), sets the turn status, and sets `processed_at`, the `outcome` (`awaiting_approval` when the run ended in a pause) and the reply text on the ingress dedupe record of the dequeued message; (c) send the approval prompt or the reply; (d) ack the queue message. A crash between (a) and (b) leaves status `running`, `processed_at` unset and the record (if any) in place: step 1b and step 2c of the worker sequence recognize what the transcript already holds.
- Redelivery: the ingress dedupe record (keyed by the channel message id) carries `processed_at`, the `outcome` and the reply text. On dequeue, a message whose record has `processed_at` set is not re-run: re-send the stored reply if the send may not have happened, then ack. Ingress dedupe alone catches channel retries but not redelivery; this closes queue redelivery after a worker crash. The step-2a expiry commit does NOT set `processed_at`: only the final post-run commit of the turn that handles the message sets it.
- Pending-record lifecycle: any run started from a record deletes it in the post-run transaction unless the run ended in a NEW pause, which writes a fresh record (new `approval_id`) in that same transaction; delete the old record before inserting the new one (the unique index is per session key). "Ended in a pause" = the `ResultMessage` has `stop_reason="tool_deferred"` with a `deferred_tool_use` equal to `turn.deferred` AND the run completed without an exception, timeout, `tool_call_cap`, `mirror_error` or persist failure; otherwise the deferral is discarded. A deferral in the transcript with no record (a crash between the deferral and transaction (b), or a failed persist) is the lost-pause case: a gated `tool_use` with no `tool_result` and no record; the turn-start repair answers it with "outcome unknown - do not retry without the user" (Caps, repair), never "not executed". This deviates from the template's fresh record for an orphaned interrupt on purpose: the approval prompt was never sent and the original message is redelivered (`processed_at` unset), so the redelivered turn re-proposes the call and pauses afresh; a fresh record would send a second prompt, and after a failed persist the deferral cannot be trusted (inference).
- Spikes (each runs before build-guide Step 4; numbered once here and defined in the section named). A failed store spike (1, 2) STOPS and raises a re-entry on the design's sessions seam, never a silent store swap; the other spikes state their own failure path:

## HITL gate
- Why native, and the shape: a PreToolUse hook that returns `defer` ends the run with `stop_reason="tool_deferred"` and a `deferred_tool_use` (id, name, input), the process exits, and a later `query(resume=<session id>)` fires the hook again for the same call, where `allow` runs it (https://code.claude.com/docs/en/hooks , "Defer a tool call for later"; observed). No timeout applies to the pause; local session files are swept after 30 days by default (the store keeps the transcript independent of that sweep: inference). A pause holds no process. The gate is ONE PreToolUse hook (`turn.gate`) plus a `can_use_tool` fallback and a hold-stream resume; the docs say a hook decision is evaluated before every permission rule and a hook `deny` holds in every mode (https://code.claude.com/docs/en/agent-sdk/permissions ).
- Gated tools are NOT in `allowed_tools`, and the mode is `default`: anything the hook does not release reaches `can_use_tool`, which denies it (observed: with no hook decision the call reached the callback). `can_use_tool` is a fallback and the interrupt channel of the deny path, never the primary gate, because calls approved by `allowed_tools` never reach it (docs). The init `SystemMessage` reports `permissionMode`, `tools` and `claude_code_version`; the worker aborts the run when they differ from the spec (mode `default`, the spec's tool names, CLI 2.1.292). The docs say an unset mode can start in `auto` (it reported `default` in the observed isolated run), so the explicit value and the assertion stay.
- Fail closed. Every hook body is wrapped: any exception becomes `deny`; a tool missing from the tier table is destructive; the matcher is unset so every tool is seen; `timeout=30` on the matcher, because a PreToolUse callback that times out blocks the tool and the model is told the hook did not respond (docs, hook timeout). The spike proves a hook made to raise blocks the call.
- Multi-call turns (the design decision the docs leave open): the docs say `defer` works only for a single tool call and is otherwise ignored; on CLI 2.1.292 a gated call beside safe calls was deferred (the safe calls ran, all ids paired after the resume) and when TWO calls returned `defer` the result reported only the last while the earlier `tool_use` vanished from the history without a result (observed). The rule, enforced in the gate: per run the FIRST gated call returns `defer` and is recorded in `turn.deferred`; any LATER gated call in the same run returns `deny` with "Gated tool <name> must be called alone in its own turn; call it again by itself after the pending one is resolved." (observed: the second got that text as an error `tool_result`, both ids were paired after the resume). A safe sibling is allowed to run. The system prompt also tells the model to call gated tools alone; that sentence is advice, not the control. Rejected (inference): denying every gated call that has a sibling, because each denial costs a model request. Side effects (record in `build.md`): (a) the denied call counts as requested and its retry counts again, so one gated action can use 2 cap units and at least 1 extra step; (b) the requested-call trajectory lists the retried call twice, so EXACT goldens recorded on stacks without this guard fail here while IN_ORDER passes (cross-stack note for the evals phase); (c) gated actions are approved one at a time, N actions = N prompts; (d) when the fixture's approvals run out while a pause is pending, the runner fails the case with an explicit error, never waits.
- Tier mapping from the spec's tool contracts: destructive -> gated EVERY time, never cached (no `updated_permissions`, no "always allow", no settings sources); reversible -> per design policy (gated, or in `allowed_tools` with a safe-tier gate result); safe -> in `allowed_tools`, the gate returns `{}`. MCP tools follow the same table under their prefixed names.
- Worker sequence:
  1. Dequeue the message for the session (ordering key = session key). If its dedupe record has `processed_at` set, do not re-run it: re-send the stored reply if the send may not have happened, then ack.
  1b. Crash-window check: if the latest `turns` row has status `running` and `message_id` equal to the dequeued message's id, load the transcript (`store.load`) and apply the committed-turn predicate (observed on store entries): an entry of type `user` has `uuid` equal to that turn's `user_uuid`; every `tool_use` id in `assistant` entries after it has a `tool_result` in a `user` entry; and the last `assistant` entry after it has `message.stop_reason == "end_turn"`. When it holds, the turn committed before the crash: run nothing, finish transaction (b) with outcome `ok` and that entry's text blocks as the reply, send, ack. Otherwise continue (the repair handles the partial turn; the redelivered message is a new turn and the duplicate user text in the history is accepted).
  2. Read the `pending_approvals` record for the session key and capture `prior` = its `resume_started` (G8). Load the transcript and compute the probe of the record's `tool_use_id`: unanswered, answered with a later final assistant entry, or answered with no final entry. An answered call goes to 2c; an unanswered one continues with 2a.
  2a. If an approval is pending, check expiry now: when it is older than the spec's TTL, or its `sdk_version` or `cli_version` differs from the running pins (the upgrade rule drains these first), no decision is applied. The worker runs the denial primitive below with the `EXPIRED:` text (under a different `cli_version` the primitive may fail to resume the transcript; then the same commit goes through the repository alone, the turn status is `error`, and the next repair adds the notice), commits (delete the record, status `hitl_expired`; the dedupe record's `processed_at` is NOT set here), sends the spec's expiry notice only if the spec defines one (no model reply from this step), then handles the dequeued message as a new turn (inference). `requested_at` is the time the worker sent the approval prompt. Expiry is evaluated when the next message for the session is dequeued (intended; a sweep is optional).
  2c. Resume already applied (a crash between the CLI finishing the continuation and transaction (b)): when the call is answered and the committed-turn predicate holds for the record's `user_uuid` (the call's `tool_result` exists and the last `assistant` entry after it has `stop_reason="end_turn"`), finish transaction (b) with outcome `ok` and that text as the reply, delete the record, send, ack; no resume is started (re-running a deferral that no longer exists is unverified). When it is answered with no final entry, delete the record and handle the dequeued message as a new turn whose user text carries the notice "[agent-notice turn <turn_id>] The approved call <name> completed (result above); the reply was not sent." (inference).
  3. If an approval is pending, unanswered and not expired: parse the message (or the approver's reply) into a decision (builder below) and RESUME. Right before a resume that can run tools (approve, edit, deny-and-continue), commit `resume_started` = true and status `running` on the record in one write (a resume may run tools and then crash); a deny-ends-turn resume never sets the flag. Otherwise start a NEW turn: turn-start repair (Caps), then status `running`. Both use ONE canonical call:
     ```python
     remaining = WALL_CLOCK - elapsed_s               # new turn: elapsed_s = 0; resume: the record's elapsed_s
     turn = TurnState(turn_id=..., approval_id=aid, prior=prior, mode=mode, steps=n_steps, tool_calls_requested=n_calls,
                      seen_ids=ids, tokens_in=ti, tokens_out=to, deadline=time.monotonic() + remaining, ...)   # new turn: aid None, zeros
     opts = agent.options_for(turn)                   # max_turns = max(1, STEP_CAP - n_steps); frozen when STEP_CAP - n_steps <= 0
     prompt = user_stream(text_with_notice, uuid=turn.user_uuid) if mode == "new" else hold(turn.done)
     try:
         async with asyncio.timeout(remaining + GRACE):          # outer wall clock (see Caps)
             async for m in query(prompt=prompt, options=opts):
                 turn.observe(m)                      # requested calls, step count, init assertions, mirror_error, usage; sets turn.done on a ResultMessage
     except (ResultError, ProcessError) as e:         # raised AFTER an error result (error_max_turns, interrupt, error_during_execution)
         turn.raised = e
     except TimeoutError:
         turn.exit = "wall_clock"
     except Exception as e:                           # anything else: outcome error, the post-run commit still runs
         turn.raised = e
         turn.exit = turn.exit or "error"
     finally:
         turn.done.set()
     ```
     `query()` raises after yielding an error result (docs), so the worker classifies by the turn's flags and the last `ResultMessage` before the exception (Caps, exit mapping). `user_stream` yields one `{"type": "user", "uuid": turn.user_uuid, "message": {...}}` message. The hold stream is the prompt of every resume: any prompt message sent with a resume starts a second turn and a second model request, an empty prompt stream closes stdin at once and fails with `tool_deferred_unavailable`, while the hold stream gave exactly the continuation of the deferred call (all observed). `asyncio.timeout` needs Python 3.11 or later, which this binding requires (the package allows 3.10). After a resume the worker checks that the gate saw the stored `tool_use_id` again; if the hook never re-fired (nothing was released), the outcome is `error`, the failure reply goes out and the record is KEPT (not deleted in (b)), so the approval can be answered again.
  4. Post-run, in this order (commit order): the transaction (b), send (c), ack (d), under Sessions and state. On a pause the worker builds the approval prompt from the record's stored call, never from model text.
- Decision value, built by the worker's single decision builder (the eval runner uses it too). approve -> the gate releases the stored call (below); deny -> the denial primitive or the hook deny (Deny); edit -> the gate releases the call with `updatedInput` set to the edited arguments, accepted only when they validate against that tool's input schema and only when the spec has an edit outcome (observed: the body ran with the edited arguments; the history keeps the model's original `tool_use` input, so the tool result must state the arguments actually used); expire -> issued only by step 2a. One approve or deny reply applies to the single pending call (design choice, inference). A message that does not parse as a decision keeps the approval pending: no run is started and the worker replies with the spec's pending-approval prompt (or denies, if the spec says so); interpreting free text is the builder's job.
- Gate behavior on a resume, by `turn.mode` and `turn.decision`: the hook fires again for the deferred `tool_use_id` (observed). Approve or edit: `turn.approved[tool_use_id] = key`, the hook returns `allow` with `updatedInput` = the arguments plus `idempotency_key` (observed: `updatedInput` overwrote a model-supplied value and reached the in-process tool body). Deny-and-continue (only when the spec lets the model continue): the hook returns `deny` with the reason; the model is called once more (observed). Deny-ends-turn and expire: the hook returns `{}` for that call and `can_use_tool` returns `PermissionResultDeny(message=<text>, interrupt=True)` after setting `turn.denied`. After the deferred call is released, the gate behaves as in a new turn for every later call of that run (counter, sibling guard, tiers).
- Deny.
  - If the spec says a deny ends the turn: no further tool executes and NO model request is made. The construct is `can_use_tool` returning `PermissionResultDeny(interrupt=True)` for the deferred call on the resume (`types.py`, `PermissionResultDeny.interrupt`): observed zero model requests, the denial text saved as the call's `tool_result`, result `error_during_execution` with `terminal_reason="aborted_streaming"` and `query()` raising `ProcessError`; the worker treats that outcome as expected when `turn.denied` is set (any other `ProcessError` is `error`). `continue_: False` with a hook deny did NOT stop the run for the re-fired deferred call on the resume (observed; it DID stop later calls, see Caps), so the hook is not used for this path. The text is "DENIED: <tool> was not run: <reason>"; when `prior` is set, an earlier resume may have run the tool, so it is "DENIED: <tool>: outcome unknown - do not retry without the user" (and `EXPIRED:` for step 2a). The saved `tool_result` keeps the session history valid for the next turn (observed). The user-visible deny reply is the spec's text, sent by the worker (outcome `hitl_denied`). The same primitive serves expiry and the lost-pause repair.
  - If the spec lets the model continue after a deny: resume as in step 3 with the hook returning `deny` and the reason "DENIED: <reason>" (or the outcome-unknown text when `prior` is set); the resume sets `resume_started` like an approve and the model sees "PreToolUse:<tool> hook error: <reason>" as the tool result (observed). A denied call still counts as a requested call. State which of the two applies in `build.md`.
- Idempotency key for a gated/destructive call: unique per APPROVED CALL, `"<approval_id>:<tool_use_id>"`. `approval_id` is the fresh UUID of the record written at that pause; `tool_use_id` is the model's own call id stored in the record. A resume that pauses again writes a new record with a new id, so keys are never reused across pauses or turns, and the key is stable across queue redelivery because the record is deleted in the post-run transaction, not before. Every destructive tool takes an optional `idempotency_key` argument in its schema, passes the value to its backend as the idempotency key and refuses to run when it is missing; the gate always overwrites whatever the model supplied. A crash after the approved tool ran but before it was recorded redelivers the message, the transcript still shows the call unanswered (step 2), the resume runs again and the tool runs again with the same key.
- Resume-started marker (G8): `prior` is captured at step 2 and picks the deny/expiry text ("outcome unknown - do not retry without the user" when set, never "was not run"); the flag is committed right before a resume that can run tools, at no other time, and deleted with the record.
- Approval is not an authorization boundary against an untrusted client: an authenticated approver identity resolved by ingress is required for a decision, and each sensitive tool checks authorization in its own body. The record is consumed in the post-run transaction and the dedupe record absorbs a repeated channel message (inference); a redelivery after a crash is a deliberate re-run covered by the idempotency key. An approval id that travels through an untrusted channel is signed by ingress (HMAC over `approval_id`, session key and expiry); the stored record authorizes the resume (inference).
- Eval runner: the fixture's approvals enter the worker's turn handler as decision messages (Eval runner mapping); the runner never calls `query` itself.
- Gate and pause spike (spike 4; binding spike; failure path: fix this binding). Pass tests: (a) one gated call: the result has `stop_reason="tool_deferred"`, the tool body ran zero times, one model request, the record holds the call; (b) one safe and one gated call in a response: the safe body once, the gated zero; a gated call listed first behaves the same; (c) two gated calls: the first deferred, the second answered with the "alone" text, after the approval the history holds both ids paired and the second is never executed; (d) fault injection: a gate body made to raise blocks the call, an unknown tool name is treated as destructive, a gate that sleeps past `timeout` blocks the call; (e) a gated tool absent from the hook decision reaches `can_use_tool` and is denied; (f) the model supplies `idempotency_key` itself: the body receives the gate's value; (g) a user message containing `@<file in cwd>` and a slash command: the file content never appears in the model request (`verbatim_prompts`; observed without it the content did); (h) permission mode, tool names and CLI version in the init message are asserted and a changed value aborts the run; (i) the call is not re-counted when the hook fires again on the resume.

## Caps
- Step cap: native `max_turns`, with a carried allowance. Observed: `max_turns=N` allows exactly N model requests (each with its tool executions), then ends `error_max_turns` (`terminal_reason="max_turns"`) before request N+1; the final text answer is also a request, so a turn that spends all N on tool use trips the cap (record this definition in `build.md`). The spec's step is one model request, 1:1 with `max_turns` (inference); `ResultMessage.num_turns` is not the step count and is never used. The count restarts on every `query()` (observed: `max_turns=1` ran a deferral and its resume), so `steps` (distinct `message_id`s of `AssistantMessage`s without `parent_tool_use_id`; observed one per model response) is stored in the record and a resume gets `max_turns = STEP_CAP - steps`. `max_turns=0` or `None` means NO cap (`src/claude_agent_sdk/_internal/transport/subprocess_cli.py`: `if self._options.max_turns:`), so the factory raises below 1. When the allowance is already 0 (the call that paused was request `STEP_CAP`) the resume still has to run the approved tool: it runs with `max_turns=1` and `turn.frozen`, which makes the gate deny every call but the stored one (observed: the approved body ran, one model request followed, its new `tool_use` was denied, the run ended `error_max_turns`). A PostToolUse hook returning `continue_: False` for the approved id did not prevent that request (observed), so the overshoot of one request stays; its reply is discarded and the outcome is `step_cap`. Record in `build.md` that the discarded reply can be a legitimate `end_turn` answer, so the user gets the failure reply although the approved action ran. `max_budget_usd` may be a backstop (a client-side estimate: https://code.claude.com/docs/en/agent-sdk/cost-tracking ), not a spec cap.
- Tool-call cap: own counter (the SDK has none: card) with a batch barrier, because no Python hook sees the whole batch (`PostToolBatch` is TypeScript only). Observed: the SDK yields one `AssistantMessage` per content block and the first PreToolUse hook entered before the later blocks reached the consumer, so a per-message count is too late. With `include_partial_messages=True`, `observe()` collects the `tool_use` ids per `message_id` (taken from `message_start`); at `message_stop` it adds every id not in `seen_ids` to `turn.tool_calls_requested` and `turn.requested`, sets `turn.exit = "tool_call_cap"` if the total exceeds `<spec tool-call cap>`, and sets a per-id `asyncio.Event`. The gate awaits its id's event (5 s, below the 30 s hook timeout; a timeout denies) and, when `turn.exit` is set, returns `deny` with `continue_: False` and a `stopReason` (it stops later calls of a run, a resumed run included, but not the re-fired deferred call: observed), gated calls included, so nothing is deferred. Ids already in `seen_ids` (the re-fired deferred call, repair runs) skip the barrier. Observed: cap 2 and a batch of 3 ran no body and made no further model request (`terminal_reason="hook_stopped"`, subtype `success`), with and without `readOnlyHint` (parallel hooks); cap 3 ran all 3; a barrier never released timed out and ran no body. Fallback: the hook input carries `transcript_path` (key observed, not exercised) to count the response's `tool_use` blocks. Only if both are disproven against the real provider (spike 7) does the binding count each call in the hook (calls up to the cap run, the rest are denied), recorded in `build.md` as a deviation with the evidence and the eval consequence (partial execution of an over-cap batch). `continue_: False` from a later call did NOT cancel a deferral already issued in the same run (observed: result `tool_deferred`), so `tool_call_cap` beats the pause in the exit mapping and no record is written. Denied, gated and unknown-tool calls count; the same list is the trajectory.
- Both caps are PER TURN: a new turn starts `TurnState` at zero; a resume restores `steps`, `tool_calls_requested`, `seen_ids`, `elapsed_s` and the token totals from the record.
- Both exits map to the spec's single failure reply and a cap outcome. Exit mapping, evaluated in this order after the run: `turn.exit == "wall_clock"` -> `wall_clock`; `turn.exit == "tool_call_cap"` -> `tool_call_cap` (the result subtype is `success`, so the flag decides); a `ResultMessage` with `subtype="error_max_turns"` or `turn.frozen` -> `step_cap`; `turn.denied` with `ProcessError` and the last `ResultMessage` carrying `terminal_reason="aborted_streaming"` -> `hitl_denied` or `hitl_expired`; `stop_reason="tool_deferred"` with a clean run -> pause; `subtype="success"`, `stop_reason="end_turn"` -> `ok`, reply = `ResultMessage.result`; anything else, including a persist failure -> `error`. The failure reply never carries exception text or partial model text.
- `harness_condition.force_step_cap`: the double scripts exactly `<step cap>` responses, each a single safe `tool_use` and no final answer, the tool-call cap set above the step cap; the test asserts `error_max_turns` and `len(double.calls) == <step cap>`. A tool-cap case does the reverse. `tool_always_errors` = the tool's injected BACKEND double raises and the real tool catches it and returns `{"content": [...], "is_error": True}` with the spec's error observation (build-guide Step 5); the tool surface never changes. A body that lets the exception escape is turned into an error result carrying the raw exception message (https://code.claude.com/docs/en/agent-sdk/custom-tools ), which leaks internals, so the tools factory wraps every body.
- Wall-clock cap: the budget is per TURN, resume time included. The record stores `elapsed_s` at each pause and a resume gets the remainder (the wait for the approver is not counted; inference); a new turn gets the full limit. The worker wraps the stream in `asyncio.timeout(remaining + GRACE)`. Observed: cancelling the stream during a 30 s tool left no `claude` process behind, so the cancel is the abort; the SDK itself has no session timeout (https://code.claude.com/docs/en/agent-sdk/hosting ). Tool bodies carry their own timeout (an in-process body keeps running in the worker after the cancel; whether it stops is unverified, spike 8 measures it) and an in-flight destructive body is covered by the idempotency key. A wall-clock expiry gives the single failure reply and the outcome `wall_clock`.
- Repair of aborted turns, at TURN START and only when no approval is pending (idempotent, survives a crash):
  1. Lost pause: load the transcript; when a gated `tool_use` is unanswered (and no record exists), run the denial primitive on it ("outcome unknown - do not retry without the user"): a `resume` with the hold stream whose gate returns `{}` for that id and whose `can_use_tool` returns `PermissionResultDeny(..., interrupt=True)`. Observed: a deferral never answered fired the hook again on the next resume; the primitive saves the text as the call's result with zero model requests. This is a separate run before the real turn.
  2. Other dangling calls (a killed or cancelled run): the CLI answers them at the next resume by itself ("outcome is unknown. Check whether it took effect ..." after a kill, without re-firing the hook; "The user doesn't want to take this action right now. STOP ..." after a cancelled run: observed both), and the second text misstates a tool that may have run. So the worker reads the latest `turns` row: a completed status (`ok`, a cap, `hitl_denied`, `hitl_expired`, `awaiting_approval`) -> nothing; status `running`, `wall_clock` or `error`, or no row while the transcript is non-empty -> the next user text is prefixed with "[agent-notice turn <turn_id>] The previous turn was interrupted or aborted; its tools may have run, and any tool result in the history saying the user declined is a placeholder. Outcome unknown - do not retry without the user." unless a `user` entry of the transcript already holds that notice for that turn id. The notice rides in the user message because the SDK has no history-edit API; the user role is accepted on every route (inference; spike 9).
  3. Only then write status `running`. Every repair says "outcome unknown", never "not executed". After a cap exit nothing is dangling (observed: the denied or last tool calls are paired in the follow-up request).
- Cap spike (spike 7; binding spike; failure path: fix this binding). Pass tests: (a) tool cap 2: one gated call, pause, approve, the model then requests 2 more: the third cumulative call is denied, the run ends with no further model request, `tool_call_cap`, and the second call ran at most once; (b) step cap N: exactly N model requests then `step_cap`, the total across a pause is still N (`len(double.calls)`), and a pause at request N takes the frozen path (one extra request, no tool but the approved one ran); (b') on the frozen path a PostToolUse hook returning `continue_: False` for the stored id: observed on the double that one model request still follows, so the pass test is that overshoot; adopt a zero-request stop only if the real provider shows it; (c) a batch of 3 under cap 2 runs NO body, with plain tools and with `readOnlyHint=True` tools; (d) both counters are 0 at the start of the next new turn; (e) a factory value of 0 raises; (f) with the real provider the provider-reported request count equals the distinct `message_id`s seen; (g) after each cap exit a follow-up turn succeeds against the real provider; (h) barrier: against the real provider the blocks and `message_stop` of a response reach the consumer before its first hook returns (record the order), and a never-released barrier times out and denies; (i) sibling case: two gated calls under cap 2 count 2, the retry counts again, and the extra step shows in `len(double.calls)`; (j) a cap trip and a deferral in the same run (barrier disabled in the test): outcome `tool_call_cap`, no record, and the next repair answers the deferred call with "outcome unknown - do not retry without the user".
- Abort spike (spike 8; binding spike; failure path: fix this binding). Pass tests: (a) a wall-clock abort during a slow tool: failure reply, outcome `wall_clock`, no `claude` process left, the next turn carries the notice once and succeeds against the real provider, its reply shows the model was told the outcome is unknown and not that the user declined; record whether the in-process body kept running; (b) a tool that raises its backend error returns the spec's error observation and the turn ends normally; (c) kill the worker during a tool, run the repair twice: exactly one notice; (d) the lost-pause case (end the process after the CLI deferred, before transaction (b)): the denial primitive answers the call, no record is written, the follow-up turn succeeds; (e) a wall-clock abort of a resume deletes the record it started from and sets `wall_clock`; the next repair writes the "outcome unknown" result for the still-unanswered deferral (assert the transcript text) and no record; (f) after every exit above the next turn succeeds with every `tool_use` paired; (g) kill the worker after the `ResultMessage` and before transaction (b) on a NEW turn: the redelivery takes step 1b, finishes (b) with the transcript's reply and makes no model request; (h) a resume whose hook never re-fires ends `error` with the record kept.

## Model provider
- Selection rule: this stack runs Claude models only; the design filter guarantees the spec did not require provider portability (card: vendor-only), and this binding offers no LiteLLM or other-provider route (Anthropic does not support non-Claude models behind a gateway: https://code.claude.com/docs/en/llm-gateway ). The spec's route names a provider and a model id of that provider, and the worker sets that provider's environment: Anthropic API -> `ANTHROPIC_API_KEY`; Amazon Bedrock -> `CLAUDE_CODE_USE_BEDROCK=1` plus AWS credentials and region; Google Cloud's Agent Platform -> `CLAUDE_CODE_USE_VERTEX=1`; Microsoft Foundry -> `CLAUDE_CODE_USE_FOUNDRY=1`; Claude Platform on AWS -> `CLAUDE_CODE_USE_ANTHROPIC_AWS=1` plus `ANTHROPIC_AWS_WORKSPACE_ID` and AWS credentials (https://code.claude.com/docs/en/agent-sdk/quickstart ; the `USE_*` names also appear in the provider table at https://code.claude.com/docs/en/data-usage ). `model=` is always set to the provider's own id; `fallback_model` stays unset (a silent model change). A gateway in front of Claude models is allowed through `ANTHROPIC_BASE_URL` (inference; this binding writes no LiteLLM route string and the spec route stays a provider plus model id).
- Format conversion: the route is a provider plus the model id as that provider names it; the SDK converts nothing, and ids, regions and keys come from the spec's route and the secret store, never from a route string. Metrics default off on Bedrock, Vertex, Foundry and Claude Platform on AWS (data-usage table); the kill switches below are set on every route anyway.
- Model route spike (spike 9; binding spike; failure path: fix this binding or the route): one turn with a tool call through the chosen route against the real provider returns the call with its arguments; a turn after a repair notice and after a `DENIED:` tool result succeeds; the provider reports usage; the init message names the expected model.

## Eval runner mapping
- Runner = worker: the eval runner drives the worker's single turn handler (dequeue logic, pending check, expiry, repair, resume-or-end, cap mapping, commit order) against an in-memory implementation of the repository interface and `InMemorySessionStore` (shipped by the SDK, wrapped in `DurableStore`), never `query` directly, so the deny, expiry and cap branches cannot diverge from production. Fixture messages and approvals enter as queue messages; the expiry clock is injected. Each case gets its own `cwd` and `CLAUDE_CONFIG_DIR`. Every run is a real `claude` process pointed at the double; run cases in parallel up to `N_MAX`.
- Model double: there is no official fake model (card). The double is a scripted Messages API server (own code, standard library) behind `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>` with a dummy `ANTHROPIC_API_KEY`: it answers `POST /v1/messages` (any query string; observed `?beta=true`) with the next scripted step as an SSE stream (`message_start`, then `content_block_start`, delta and `content_block_stop` per block, `message_delta` with `stop_reason` `tool_use` or `end_turn`, `message_stop`) or as JSON when `stream` is false, answers other paths with a small JSON body, records every request, and has `assert_complete()`. A step is a list of text or `tool_use` blocks (`id` unique per call, `name` the prefixed tool name) and a fixed usage. Observed with the kill switches set: the CLI sent only `POST /v1/messages?beta=true`, one per model request, so the request count is the step count; without them it also contacted `api.anthropic.com`, so a hermetic eval sets every switch of the Telemetry section. The Python `Transport` ABC (https://code.claude.com/docs/en/agent-sdk/python ) is a low-level internal API and is not used. The script fixes the trajectory; a recorded fixture is turned into steps by the fixture loader.
- Capture source: `TurnState`, filled by `observe()` and the gate, read by the runner after each run; a turn with a pause has several runs and the runner joins their lists in order.
  - Trajectory = the REQUESTED calls: `(name, input)` of every `ToolUseBlock` of an `AssistantMessage` in the stream, in order, deduped by block id, including cap-denied and gate-deferred calls.
  - `forbidden` is checked against the EXECUTED calls, `TurnState.executed` (the gate appends `(name, input)` only for a call it released, with `{}` or `allow`; denied, deferred and interrupt-denied calls are not in it), plus the reply text (`skills/build/references/adapter-bindings.md`). A released call can still fail before its body, which errs on the side of `forbidden` (inference). One rule, no per-case guessing.
- The PIPELINE runner implements EXACT, IN_ORDER and ANY_ORDER itself over the trajectory list, with `args_subset` matching (golden-format: expected args must be a subset of actual args; never full-argument equality). The SDK ships no eval tooling (card), so there is no framework evaluator to use. pass^k is computed by the pipeline runner from its own per-case results.
- Approvals in a case: the fixture's approvals enter the worker handler as decision messages and are answered by the worker's decision builder; when they run out while a pause is pending the runner fails the case explicitly. The trajectory lists a retried gated call twice (HITL gate, sibling guard), so EXACT cases recorded elsewhere fail and IN_ORDER passes. `harness_condition.force_step_cap` and `tool_always_errors` are under Caps.
- Tool-surface preflight: the eval runner and a permanent CI unit test assert that the FIRST model request's tool names equal the spec's tool set (plus any built-in kept on purpose, each with its reason in `build.md`; this binding keeps none). Capture source: `double.calls[0]["tools"]` (the `name` of each entry of the request body's `tools` list), cross-checked in production by the init `SystemMessage`'s `tools` (observed to list the same names). The double replaces only the model, but the CLI's tool search is on by default on a first-party host and off for a non-first-party `ANTHROPIC_BASE_URL` (https://code.claude.com/docs/en/agent-sdk/tool-search ), so a double could hide the production surface: `ENABLE_TOOL_SEARCH=false` is set in production and in evals, and the preflight also runs against the real provider in spike 11. Negative controls (both observed): (1) remove `tools=[]` from the options: the request lists 26 built-ins and the preflight MUST fail on them (`allowed_tools` alone does not restrict); (2) set `ENABLE_TOOL_SEARCH=true`: the list gains a `DeferredToolPlaceholder` entry and the preflight MUST fail on it. A stale tier table (a renamed tool) must fail the factory.
- Eval double spike (spike 11; binding spike; failure path: fix this binding): the double drives a full pause, resume and finish through the worker handler on the in-memory store and on the Postgres store with the same trajectory; the preflight and both negative controls pass; the preflight against the real provider shows the same names as against the double.

## A2A and MCP
- A2A: none native (card). Own server built with `a2a-sdk` (Apache-2.0; 1.2.2 was the latest on PyPI on 2026-10-08, https://pypi.org/project/a2a-sdk/ ) that enqueues into the same ingress queue (key = session key) and answers from the repository, so the gate, the caps and the repair apply (own code, inference). A2A client: a tool wrapping the `a2a-sdk` client, with the tier the design gives it (inference). Record the path in interop.md.
  - A2A spike (spike 12, when the design names A2A; binding spike; failure path: fix this binding): a task through the server appears in the ingress queue with the session key as ordering key, and a gated tool reached through it pauses.
- MCP client: custom tools are in-process SDK servers (`@tool`, `create_sdk_mcp_server`; the server runs inside the worker: https://code.claude.com/docs/en/agent-sdk/custom-tools ). Annotations are metadata: `readOnlyHint=True` lets read-only tools run in parallel and is set only on tools that are read-only, while `destructiveHint` is informational only, so the tier table, not annotations, is the policy. The Python `@tool` forwards only `content` and `is_error` (no `structuredContent`). External servers: `mcp_servers={"<name>": {"type": "http", "url": ..., "headers": ...}}` with `strict_mcp_config=True` (ignores ambient MCP configuration: `types.py`), an explicit `allowed_tools` entry per safe tool (never the wildcard `mcp__<name>__*`, which would pre-approve tools the server adds later), the tier table keyed by the prefixed names (unknown = destructive), and `ENABLE_TOOL_SEARCH=false` so every schema is loaded and visible to the preflight. Every external MCP tool name must appear in the tier table.
  - MCP spike (spike 13, when the design names an external MCP server; binding spike; failure path: fix this binding): the server's filtered tool names appear in the first model request, a destructive MCP tool is deferred by the gate (the hook sees `mcp__<name>__<tool>`: documented, unverified for external servers), the pause serializes, and the resume in a new process runs it once with the key; a tool missing from the table is deferred, not run.
- MCP serving: not part of this binding unless the design asks for it, and then routed through the ingress queue so gate and caps still hold (inference).

## Pinned version and traps
- Every package below gets an exact pin in the lockfile. Any ">=" in this text is a minimum, never a requirement spec.
  - `claude-agent-sdk==0.2.164` (released 2026-10-06; the package allows Python 3.10, this binding requires 3.11 or later for `asyncio.timeout`; latest on PyPI on 2026-10-08; https://pypi.org/project/claude-agent-sdk/ ). The platform wheel bundles the native CLI 2.1.292 (`claude_agent_sdk/_cli_version.py`, the changelog at the tag): record both versions in `build.md`, pin the wheel with its hash (the binary is part of the supply chain), assert `claude_code_version == "2.1.292"` in the init message, and never let the CLI update itself (`DISABLE_AUTOUPDATER=1`). Resolved on 2026-10-08 in a scratch environment (the lockfile is the authority): `mcp` 2.3.0 (the package allows `>=1.23.0,<3`), `anyio` 4.15.1, `jsonschema` 4.26.0, `pydantic` 2.14.0.
  - `asyncpg==0.32.0` (Apache-2.0; 2026-10-06) or the driver of the chosen adapter (`boto3` for DynamoDB, `google-cloud-firestore` for Firestore).
  - `opentelemetry-api`, `opentelemetry-sdk`, `opentelemetry-exporter-otlp-proto-http` (1.45.1 on 2026-10-08; exact pins; the SDK reads the active span through `opentelemetry-api`).
  - `a2a-sdk==1.2.2` (only for A2A).
- Obligation (security): `tools=[]`, an explicit permission mode, an explicit system prompt and `verbatim_prompts=True` are set on every run and asserted by the preflight and the init check; gated tools are never in `allowed_tools`; never `bypassPermissions` or `auto`; the gate is fail closed (wrapped body, unknown tool = destructive, hook timeout blocks, sibling guard, deny-by-default callback) and each sensitive tool re-checks authorization. Sources: https://code.claude.com/docs/en/agent-sdk/permissions , https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts , https://code.claude.com/docs/en/hooks
- Obligation (data): the kill-switch variables are in `.env.example` and the deploy recipe, `main.py` asserts them, and spike 10 (proxy log plus negative control) passes before any client data flows; the CLI writes plaintext transcripts to the local config directory, which the worker deletes after the commit. Sources: https://code.claude.com/docs/en/data-usage , https://code.claude.com/docs/en/agent-sdk/session-storage
- Obligation (data): persistence is guaranteed or the turn fails closed (`DurableStore`, the `mirror_error` and persist-failed checks, eager flush, deterministic `cwd`). Source: https://code.claude.com/docs/en/agent-sdk/session-storage
- Obligation (ops): one process per run and `N_MAX` bounds concurrency; the step cap is `max_turns = STEP_CAP - steps` and never 0; the tool-call cap is the gate counter; the turn-start repair (lost pause plus notice) runs before every new turn; wall clock is a cancel with a notice. Sources: https://code.claude.com/docs/en/agent-sdk/hosting , https://raw.githubusercontent.com/anthropics/claude-agent-sdk-python/v0.2.164/src/claude_agent_sdk/_internal/transport/subprocess_cli.py
- Obligation (ops): re-run every spike on any upgrade, because each release bundles a different CLI (`CHANGELOG.md` at the tag); before changing the pin, drain pending approvals (answer or expire them), because `pending_approvals.cli_version` is compared at step 2a and the deferred call lives in a transcript the new CLI must be able to resume. Sources: https://github.com/anthropics/claude-agent-sdk-python/blob/v0.2.164/CHANGELOG.md , https://code.claude.com/docs/en/agent-sdk/hosting
