# Deep Agents - build binding

Facts below cite the same sources as the card (`skills/design/references/stacks/deep-agents.md`) and the research file `docs/superpowers/research/2026-10-07-stack-catalog/langchain-family.md`; a URL is repeated where a rule depends on it. This file is self-contained: the shared LangGraph and `create_agent` facts are restated in full. Statements marked inference are the binding's own reasoning; statements marked unverified are not confirmed by a page or the library source, and a spike below confirms them on the pinned version. Library source was read on `main` (https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/graph.py ), not on the 0.7.23 tag; the spikes confirm every placement rule that depends on it.

Shape: one compiled agent from `create_deep_agent`, built by `build_agent(model, checkpointer, tools, caps, backend)` in `src/agent/`, plus a helper `build_profile(spec_tool_names, has_subagents, has_sandbox)` that builds and registers the harness profile (see Least privilege). The call passes, explicitly: `model=` (always; omitting it is deprecated and falls back to a default Anthropic model, which is hidden egress and a hidden provider choice), `tools=` (the spec's tools that are NOT mapped to a Deep Agents built-in; a kept built-in is not passed), `system_prompt=`, `checkpointer=` (the injected saver), `backend=` (StateBackend or a sandbox backend, see Pinned version and traps), `permissions=` (see Least privilege below), `interrupt_on=` (from the spec tiers, see HITL gate), `subagents=` (the spec's declared subagents, or nothing) and `middleware=[TurnCaps(caps), <optional telemetry fallback middleware>]`. Anything not listed here (`memory=`, `skills=`, `store=`, `response_format=` and the like) is not passed unless the design names it. The harness profile (`excluded_tools`, general-purpose subagent disabled) is registered before the call by the same factory. The factory replaces a hand-written model-tool loop. `src/agent/` never imports psycopg, saver packages or sandbox SDKs: the adapter constructs the checkpointer (`PostgresSaver` / `AsyncPostgresSaver` or the DynamoDB saver) and the sandbox backend in `adapters/<target>/` and injects them. The checkpointer holds only conversation/graph state, which includes the StateBackend virtual files; dedupe and the spec's data schemas live in repository tables behind the repository interface, never in agent state or agent files. Sources: https://docs.langchain.com/oss/python/deepagents/customization and https://docs.langchain.com/oss/python/deepagents/backends

Least privilege (mandatory, applies to every section below). Deep Agents "trusts the LLM" and the boundary is the tool or sandbox (https://github.com/langchain-ai/deepagents ), so the build closes the implicit surface. The obligations and their pass test (the Least-privilege spike) are:
- Kept set and `excluded_tools`. The built-in tool names on the pinned version are `ls`, `read_file`, `write_file`, `edit_file`, `delete`, `glob`, `grep` (filesystem), `execute` (sandbox backends only), `task` (subagents), `write_todos` (only with `TodoListMiddleware`; not default since 0.7), `eval` (only with an interpreter) and `compact_conversation` (only with the optional summarization tool middleware; listed here unconditionally). Sources: https://docs.langchain.com/oss/python/deepagents/harness , https://docs.langchain.com/oss/python/deepagents/context-engineering . This list is hand-maintained in `build_profile`: nothing in the library computes it, and the computed `excluded_tools` cannot catch a built-in added in a later 0.x release; the permanent tool-surface test below is what catches it on an upgrade. Kept set K = (the spec tool names the spec maps to a Deep Agents built-in) plus `task` if the spec declares subagents, plus `execute` if the spec declares a sandbox, plus `read_file` when the eviction rule below applies. `excluded_tools` = (built-in names) minus K. A kept built-in is NOT passed in `tools=`, and the spec must accept that built-in's schema and description (record each kept built-in and its reason in `build.md`). Every other spec tool name must not collide with a built-in name (`build_profile` asserts it), because `excluded_tools` is a post-injection filter that also drops user-supplied tools. The Filesystem, SubAgent and permission middleware cannot be removed (listing them in `excluded_middleware` raises ValueError); only their tools are hidden.
- Profile registration. Declare `HarnessProfile(excluded_tools=frozenset({...}))` and `register_harness_profile(<key>, profile)` BEFORE `create_deep_agent`. The key is a provider name (applies to every model of that provider) or `provider:model`; only the first colon separates the two; re-registering merges onto the existing profile; model-level values override provider-level ones. Build the agent with the PRODUCTION model string so the key resolves; register one profile per distinct model key in use (the main agent's, and each declared subagent's own model, because each subagent re-runs profile resolution against its own model). Source: https://docs.langchain.com/oss/python/deepagents/profiles . The profiles page imports `GeneralPurposeSubagentProfile`, `HarnessProfile` and `register_harness_profile` from `deepagents`, and the permissions page imports `FilesystemPermission` and `create_deep_agent` from `deepagents`: the pages import these names from `deepagents`, and spike test (e) confirms they resolve on the pin. The registry is process-global (inference: profiles are registered by key before agent creation); tests reset it between tests if the pin exposes a way to do so (unverified), otherwise the registry-touching tests run in separate processes and `build.md` says so.
- General-purpose subagent disabled: `general_purpose_subagent=GeneralPurposeSubagentProfile(enabled=False)` in the same profile, and pass no synchronous subagents, unless the spec declares subagents. With both done, `SubAgentMiddleware` and the `task` tool are not attached. Do not use `excluded_middleware` for this. Source: https://docs.langchain.com/oss/python/deepagents/subagents . If the spec declares subagents, they are passed explicitly in `subagents=`, each with its own `tools`, `interrupt_on`, `permissions` and caps (below), and `task` is in K. A declared subagent whose gates or caps are missing from the spec is a STOP: raise a re-entry on the spec, never a default.
- Catch-all `deny /**` FilesystemPermission (applies when the backend is StateBackend; with a sandbox backend, permissions do not apply, the sandbox is the boundary, and spike test (b) is replaced by "no ambient secrets or credentials are present in the sandbox"): `permissions=[<allow rules for the spec's paths, narrower first>, <the eviction allow rule below, when it applies>, FilesystemPermission(operations=["read", "write"], paths=["/**"], mode="deny")]`. Rules are checked in declaration order and the first match decides; with no match the operation is allowed, so the deny must be last. `operations="read"` covers `ls`, `read_file`, `glob`, `grep`; `"write"` covers `write_file`, `edit_file`, `delete`. Permissions do NOT cover `execute`, custom tools or MCP tools, and do not apply to sandbox backends; with a CompositeBackend whose default is a sandbox, every permission path must fall under a route prefix and `/**` raises NotImplementedError. A subagent inherits the parent's permissions unless its spec sets `permissions`, which replaces them entirely, so every subagent spec either inherits or carries its own deny-last list. Source: https://docs.langchain.com/oss/python/deepagents/permissions
- Eviction rule (StateBackend). Deep Agents writes tool results over the offload threshold (20,000 tokens by default) to the backend and replaces them with a path and a 10-line preview that the agent re-reads with `read_file` (and summarization writes a text rendering of the old messages to the filesystem). Source: https://docs.langchain.com/oss/python/deepagents/context-engineering . If the eviction spike shows that excluding `read_file` breaks that re-read, keep `read_file` in K and add a read-only allow rule `FilesystemPermission(operations=["read"], paths=["<eviction prefix>/**"], mode="allow")` BEFORE the catch-all deny, for the eviction prefix only (the pages do not name the prefix: read it from the pinned version); add `read_file` to the tool-surface expected set with that reason in `build.md`. Whether permissions apply to middleware-internal writes (eviction and the summarization offload) is unverified: the eviction spike proves eviction still works under the `/**` write deny. If spike (f) shows the `/**` write deny blocks the eviction or summarization offload writes, add a write-allow rule for those prefixes only, placed before the deny.
- Backend: StateBackend (default) or a sandbox backend only. `FilesystemBackend` and `LocalShellBackend` are forbidden in deployed agents (host access; LocalShellBackend runs unrestricted shell commands; `virtual_mode=True` gives no protection for the latter). `ContextHubBackend` needs `LANGSMITH_API_KEY` and is not used (egress). `StoreBackend` is used only if the design needs cross-thread memory, with a per-user namespace factory (without one, users of the same assistant share storage); that is a sessions/store decision, so STOP and raise a re-entry on the design's sessions seam rather than adding it silently. Sources: https://docs.langchain.com/oss/python/deepagents/backends , https://docs.langchain.com/oss/python/deepagents/going-to-production
- Sandbox backend (only if the spec declares code execution): `execute` is destructive-tier (HITL every time) and permissions do not guard it, so the sandbox is the boundary: no ambient secrets (the production page says to use the sandbox auth proxy so keys never enter the sandbox and not to pass secrets through environment variables or file uploads), a TTL or cleanup for assistant-scoped sandboxes, thread-scoped sandboxes by default. Source: https://docs.langchain.com/oss/python/deepagents/going-to-production . Sandbox providers are third-party services (egress): record the choice in `build.md`.
- Tool-surface probe (test-only). A test-only middleware `ToolSurfaceProbe` is passed in `middleware=` in test builds. Its `wrap_model_call(request, handler)` hook (https://docs.langchain.com/oss/python/langchain/middleware/custom ) records the tool names of the request and returns the next scripted `AIMessage` WITHOUT calling `handler`, so no model call and no network happens and the agent is built with the PRODUCTION model string (so the profile key resolves and the tool surface is the production one). Construction of the production model may need a placeholder API key in the test environment; the tests block sockets. That a `wrap_model_call` hook can short-circuit this way on the pin, and that the request exposes tool names, are unverified: spike test (d) proves them. In test builds `build_agent` also appends the probe, each with its own script slot, to every declared subagent's `middleware`, and the runner's fixture scripts responses per subagent. The eval runner drives its scripted responses through the same middleware (see Eval runner mapping).
- Least-privilege spike (binding spike; runs at build-guide Step 4; failure path: binding defect: STOP and report (build-guide Step 4); never widen the spec). Pass tests: (a) the FIRST model request's tool names equal the expected set: the spec's tool names (those passed in `tools=` plus the kept built-ins of K, each kept built-in with its reason in `build.md`); an extra or missing name fails. The same assertion is a permanent CI unit test and also runs in the eval runner. The test also records whether the system prompt still describes the excluded tools (a prompt that names a hidden tool invites a hallucinated call; record the answer in `build.md`). Negative control: a built-in not in K (for example `glob`) must be absent from the recorded names; if it is present, the probe sits outside the exclusion filter (the filter is appended last in the stack, so an earlier middleware may see the unfiltered list; unverified) and the test is invalid, so observe at the model boundary instead: keep passing the production model string and, in tests, monkeypatch the production chat-model class's `_generate` / `_agenerate` at class level (record the bound tools from the call kwargs, return scripted messages, no network) so `init_chat_model` builds the patched class and the profile key still resolves (unverified). The eval runner switches to the same mechanism whenever this negative control fails. (b) with StateBackend: a `write_file` to a path outside the allowed paths is denied (the tool result says so and the file does not appear in `state.values["files"]`); with a sandbox backend this test is replaced by: no ambient secrets or credentials are present in the sandbox. (c) with the general-purpose subagent disabled and no declared subagents, `task` is absent from the tool list. (d) the short-circuit works: with `ToolSurfaceProbe` returning an `AIMessage` that carries a safe tool call, the tool runs, the next scripted message ends the turn, and no socket was opened. (e) the four names the pages import from `deepagents` (`register_harness_profile`, `HarnessProfile`, `GeneralPurposeSubagentProfile`, `FilesystemPermission`) resolve on the pinned version. (f) eviction: a tool result over the threshold is still evicted and the agent can still read it back under the `/**` write deny (with the eviction allow rule if the spike showed it is needed); summarization offload is checked the same way. (g) per declared subagent: the subagent's first model request lists exactly that subagent's declared tools (the subagent's model key has its own profile; the page does not say whether `excluded_tools` filters a subagent's tool set, so this is proved, not assumed).

## Sessions and state
- `create_deep_agent(..., checkpointer=<saver>)` plus `{"configurable": {"thread_id": <session key>}}` in the config is how the agent gets persistence; HITL needs a checkpointer. StateBackend files live in graph state for the thread and persist across turns through the checkpointer; they are not shared across threads (the page: they persist across turns on the same thread through checkpoints), and since they live in checkpointed state, large files make every checkpoint bigger (inference), so do not write large files into them. Sources: https://docs.langchain.com/oss/python/deepagents/backends , https://docs.langchain.com/oss/python/deepagents/going-to-production
- Postgres: `PostgresSaver` / `AsyncPostgresSaver` from `langgraph-checkpoint-postgres`. Source: https://docs.langchain.com/oss/python/langgraph/checkpointers.md
- Saver kind follows the worker: an async worker uses `AsyncPostgresSaver` and `ainvoke` / `astream`; a sync worker uses `PostgresSaver` and `invoke` / `stream` (inference; the persistence page names both savers: https://docs.langchain.com/oss/python/langgraph/persistence ).
- A connection you create yourself must use `autocommit=True` and `row_factory=dict_row` (autocommit makes `.setup()` persist the tables; the saver reads columns by name). Source: https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md
- `.setup()` runs once, as a named one-shot migration job (`agent-migrate`: compose service / ECS task / Cloud Run job), never from the worker and never per request. Source for the call: https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md
- Durability: pass `durability="sync"` on every agent call (persists changes before the next step starts; default is "async"). The parameter is documented on the LangGraph `invoke`: https://reference.langchain.com/python/langgraph/pregel/main/Pregel/invoke ; that the compiled Deep Agent graph accepts it on `stream`, `ainvoke` and `astream` is unverified (inference: `create_deep_agent` returns a compiled LangGraph graph), so confirm it in the first spike. The modes are described at https://docs.langchain.com/oss/python/langgraph/checkpointers.md
- `thread_id` = the spec's session key; keep it under 255 characters on Postgres. Source: https://docs.langchain.com/oss/python/langgraph/persistence
- Queue ordering key = `thread_id` (the session key), so one turn per thread holds even when the approver is a different sender. Ingress resolves an approver's reply to the pending session's key before enqueueing. The OSS library has no per-thread locking and double-texting is not available there. Source: https://docs.langchain.com/langsmith/double-texting.md
- Pass per-run data such as a user id as `context` (with `context_schema`), not through `thread_id`; it is independent of the thread. Source: https://docs.langchain.com/oss/python/deepagents/going-to-production
- The built-in call-limit middlewares are not used (see Caps).
- Supabase connection: use the direct connection or the Supavisor session mode (port 5432); never the transaction pooler (port 6543), which does not support prepared statements (psycopg3 uses them by default, inference). Source: https://supabase.com/docs/guides/database/connecting-to-postgres
- Supabase schema: put the checkpoint tables in a schema not exposed through the Data API (for example `agent_state`, selected via the connection's search_path; the wiring is unverified) and enable RLS on them. Source: https://supabase.com/docs/guides/database/postgres/row-level-security
- Supabase Free plan: projects are paused after 1 week of inactivity, so it is not for production. Source: https://supabase.com/pricing
- DynamoDB: `langgraph-checkpoint-aws` provides the checkpointer (the class is named DynamoDBSaver in the research file; the docs page lists only the package). The same page also lists a separate community package, `langgraph-dynamodb-checkpoint` (agentstate); prefer the AWS package. Source: https://docs.langchain.com/oss/python/integrations/checkpointers/index.md
- Firestore: no official checkpointer (a community package is listed, unverified for production). Source: https://docs.langchain.com/oss/python/integrations/checkpointers/index.md . If the design names Firestore, STOP and raise a re-entry on the design's sessions seam; do not swap the store silently.
- Any one-time schema setup (the checkpointer tables) runs as the named one-shot migration job above, never from the worker.
- Spikes (each runs at build-guide Step 4). A failed store spike STOPS and raises a re-entry on the design's sessions seam, never a silent store swap; the other spikes state their own failure path:
  - Supabase (store spike): after `.setup()` with the chosen search_path the tables exist in `agent_state` and not in `public`; then `ENABLE ROW LEVEL SECURITY` on them; a put/get round trip works as the saver's DB role.
  - DynamoDB (store spike): the pinned package imports the named saver class and a put/get round trip works against the target table.
  - Durability (binding spike, not a store spike): `durability="sync"` is accepted by the exact call the worker uses (`invoke`, `ainvoke`, `stream` or `astream`) on the compiled `create_deep_agent` graph; failure path: binding defect (the call or parameter named does not work on the pinned version): STOP and report (build-guide Step 4), not a sessions-seam re-entry.
  - Pending interrupt (binding spike; pass test: after a gated tool call pauses the agent, `agent.get_state(config)` exposes the pending interrupt via `state.tasks[*].interrupts` and the payload carries `action_requests`; failure path: binding defect: STOP and report (build-guide Step 4), not a sessions-seam re-entry). The call that raises the interrupt also reports it in its own result (`__interrupt__` key); the worker needs the check on a later dequeue. With declared subagents, the same test is repeated for a gated call made inside a subagent: the docs say a subagent interrupt surfaces as `__interrupt__` in the parent's `updates` stream, and how it appears on the parent's `get_state` snapshot is unverified. The spike also asserts that the worker can tell the two sources apart from `state.tasks[*]` (the task name or namespace: the main agent's HITL after-model node versus the parent's `tools` node, where a subagent interrupt surfaces); the pre-prompt guard needs this distinction. Failure path: binding defect: STOP and report (build-guide Step 4) and the worker's check.
  - Resume payload and PatchToolCalls (binding spike; pass tests: for one gated call, `Command(resume={"decisions": [{"type": "approve"}]})` runs the tool once and no "cancelled" tool message from `PatchToolCallsMiddleware` precedes it (that middleware repairs dangling tool calls and must not fire on a resume; unverified); a reject decision runs it zero times and the agent receives the rejection; an edit decision runs the tool with the edited args. Multi-action: with two gated calls in one model message, the decisions `[approve, reject]` run exactly the first and not the second, and the interrupt payload shows one interrupt with two `action_requests`; if the spike instead shows one interrupt per action, resume with the interrupt-id map described under HITL gate. Failure path: binding defect: STOP and report (build-guide Step 4)).
  - Deny, expiry, cap, abort and least-privilege spikes are specified under HITL gate, Caps and Least privilege.
- Worker post-run order: the checkpointer has committed during the run; then one repository transaction writes a NEW pending-approval record when the turn ended in a pause (fresh UUID `approval_id`, `requested_at` = now, taken just before sending), deletes the record the run started from unless the run ended in a NEW pause ("ended in a pause" = an interrupt is pending AND the run completed without an exception or timeout; a wall-clock abort with a gated call pending writes no record), and writes the dedupe record's `processed_at`, `outcome` (`awaiting_approval` when the turn ended in a pause) and reply text; then send the prompt or reply; then ack the queue message. If step 2 finds a pending interrupt with no record (a crash between the checkpoint commit and the post-run transaction, or a timeout after the interrupt was checkpointed), write a fresh record (new UUID `approval_id`, `requested_at` = now) before prompting or resuming. A dequeued message whose dedupe record has `processed_at` set is not re-run: re-send the stored reply if the send may not have happened, then ack.

## HITL gate
- Recommended placement: pass the tiers as `interrupt_on=` to `create_deep_agent`; Deep Agents appends its `HumanInTheLoopMiddleware` after the user `middleware=` entries. It pauses the agent after the model proposes a gated tool call and before the tool executes, and needs a durable checkpointer plus a `thread_id`. Sources: https://docs.langchain.com/oss/python/deepagents/human-in-the-loop , https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/graph.py
- Worker sequence:
  1. Dequeue the message for the session (ordering key `thread_id`).
  2. Capture `prior` = the pending record's `resume_started` (G8), then read `agent.get_state(config)` for that `thread_id` and check for a pending interrupt (inference, unverified for `create_deep_agent`: pending interrupts appear on the snapshot as `state.tasks[*].interrupts`; the pending-interrupt spike confirms it).
  2a. If an approval is pending, check its expiry now: when it is older than the spec's TTL, resume it with reject decisions whose message starts with the marker `EXPIRED:` (the `TurnCaps` deny jump ends the turn on that marker whatever the spec's deny policy is), record the outcome `hitl_expired`, produce no model reply from this resume (the final message is a tool message; send the spec's expiry notice only if the spec defines one), then handle the dequeued message as a new turn (inference). The worker records the time it sent the approval prompt in the repository for this check. A pending approval has already passed the pre-prompt guard of step 4 and the counters do not change while it is pending, so this expiry resume cannot trip the tool cap: its outcome is `hitl_expired`. Its repository commit deletes the pending record but does NOT set the dedupe record's `processed_at`; only the final post-run commit of the turn that handles the message sets it.
  3. If an approval is pending and not expired: parse the message (or the approver's reply) into a decision, commit `resume_started` = true on the pending record ONLY right before a resume that can run tools (approve, edit, or a deny when the spec lets the model continue; a deny-ends-turn or `EXPIRED:` reject never sets it; a resume may run tools and then crash), and resume with `Command(resume={"decisions": [...]})` on the same `thread_id`. A resume carries no new input, so the `TurnCaps` counters persist across the pause. Otherwise start a new turn: run the turn-start repair (see Caps), then invoke with fresh input and both counters set to 0.
  4. Pre-prompt guard (every call that returns an interrupt, new turn or resume, before ANY approval prompt is sent): read `values["tool_calls_requested"]` from the snapshot and count the tool calls in the last AI message; if the sum exceeds the spec's tool-call cap, do NOT prompt. The guard applies ONLY when the pending interrupt comes from the main agent's HITL after-model node, not from the parent's `tools` node where subagent interrupts surface (the worker tells them apart from `state.tasks[*]`, see the pending-interrupt spike). Resume immediately with one reject decision per action request, each with the message `DENIED: tool-call cap`, so `TurnCaps.after_model` raises `ToolCapExceeded` (outcome `tool_call_cap`, the spec's single failure reply) before any tool runs. At the pause the pending message is not yet counted, because HITL's after_model runs before `TurnCaps.after_model` (inference from the hook order); cap spike test (f) proves it. The guard is one function shared by the worker and the eval runner. It does not cover interrupts raised inside a subagent; the subagent's own caps handle those.
- Detecting the pause in a call result: `result.get("__interrupt__")`, then `value["action_requests"]` and `value["review_configs"]` (each review config has an `action_name` and `allowed_decisions`). Source: https://docs.langchain.com/oss/python/deepagents/human-in-the-loop
- Decision value. The spec's three outcomes map to the documented payloads, one entry per `action_requests` item, in the same order as the interrupt lists them. Source: https://docs.langchain.com/oss/python/deepagents/human-in-the-loop
  - approve -> `{"type": "approve"}`
  - deny -> `{"type": "reject", "message": "DENIED: <reason>"}` (`message` is optional in the docs, and omitting it gives a default "not executed, do not retry" text; the binding always sets it, with the marker, see Deny below)
  - edit -> `{"type": "edit", "edited_action": {"name": "<tool>", "args": {...}}}`; the name must be included and edits stay conservative, because large changes may make the model re-plan.
  - The documented `respond` type returns a human reply as a successful tool result and the page says not to use it to deny side-effecting tools: the binding never uses it, and never lists it in `allowed_decisions`.
  - Reply covering several gated calls (design choice, inference): one approve or deny reply applies to every pending action, `edit` is accepted only when exactly one action is pending, and the worker's single decisions-list builder makes the list length equal the number of `action_requests`. The eval runner uses the same builder. Only if the resume-payload spike shows several interrupts pending (one per action) instead of one interrupt with N actions, the resume value is a map from interrupt id to its answer: https://docs.langchain.com/oss/python/langgraph/interrupts , https://docs.langchain.com/oss/python/langchain/streaming .
- If a message for a pending session does not parse as a decision: keep the interrupt pending and reply with the spec's pending-approval prompt (or deny if the spec says so). Expiry is evaluated when the next message for that session is dequeued (step 2a; intended; a sweep is optional).
- Deny. The worker always starts the reject message with a marker, `DENIED:` (or `EXPIRED:` from step 2a), so `TurnCaps` can recognize a rejection among the tool messages. When `prior` (the record's `resume_started`, captured at step 2) is set (an earlier resume may have run tools before it crashed), the text after the marker is "outcome unknown - do not retry without the user" instead of the denial or expiry reason; the marker prefix is unchanged, so `TurnCaps` still matches. Match rule: a tool message counts as a rejection only when its content STARTS WITH the marker AND its `tool_call_id` belongs to the tool calls of the last AI message. Untrusted tool output is wrapped in the spec's envelope, so it cannot start with the marker (inference; the envelope is the spec's untrusted-content wrapper). In `before_model` the deny/expiry jump is checked BEFORE the step cap. That the reject message reaches the tool message content is unverified; the deny spike confirms it. Deep Agents built-in tools and the `task` tool return text that is not the spec's envelope, so either wrap their results in the envelope with a `wrap_tool_call` middleware (passed in `middleware=`), or record the residual risk in `build.md`: a built-in or subagent result that starts with `DENIED:`, `EXPIRED:` or `CAP:` and belongs to the last AI message's calls would be read as a marker.
  - If the spec says a deny ends the turn: no further tool may execute after the reject. `TurnCaps.before_model` finds a tool message carrying the marker after the last AI message and returns `{"jump_to": "end"}` (valid targets are end, tools and model; declared with `@hook_config(can_jump_to=["end"])`). Source: https://docs.langchain.com/oss/python/langchain/middleware/custom . The reply is the spec's deny reply and the outcome is `hitl_denied`; the tool message is the last message, so no tool call is left without a result.
  - If the spec lets the model continue after a deny: the jump is disabled for `DENIED:` (it stays on for `EXPIRED:`), the model sees the rejection and continues. State which of the two applies in `build.md`.
  - A denied call still counts as a requested tool call for the tool cap (see Caps).
  - Deny and expiry spike (binding spike; failure path: binding defect: STOP and report (build-guide Step 4)): after a reject under deny-ends-turn, and after an `EXPIRED:` reject under either deny policy, zero further tool calls execute and a follow-up turn on the same `thread_id` works; an ordinary deny writes "was not run", and a deny or expiry after a crashed approve-resume (kill the worker mid-resume, then dequeue the next message) writes "outcome unknown - do not retry without the user". The spike also confirms that `SummarizationMiddleware` (it precedes `TurnCaps` in the stack) does not hide the marker message from `before_model`.
- Tier mapping, built from the spec's tool contracts into `interrupt_on`: destructive -> `{"allowed_decisions": ["approve", "reject"]}` every time, never cached (no edit, no respond); reversible -> per design policy (`["approve", "edit", "reject"]`, or a `when` predicate that receives the `ToolCallRequest` and returns True to interrupt, which needs `langchain>=1.3.3` and is satisfied by the pin); safe -> `False`. The write-capable built-ins the spec keeps (`write_file`, `edit_file`, `delete`, `execute`) are destructive unless the spec says otherwise. List every tool the agent keeps explicitly; do not rely on unlisted tools defaulting to auto-approve (the page does not state the default for an unlisted tool; unverified). A `FilesystemPermission` with `mode="interrupt"` (needs `deepagents>=0.6.8`) merges into `interrupt_on` with user entries winning; the binding does not use it, so there is one place to read the tiers. Source: https://docs.langchain.com/oss/python/deepagents/human-in-the-loop , https://docs.langchain.com/oss/python/deepagents/permissions
- Subagents (only when the spec declares them; the spec must give each declared subagent its gates and caps, otherwise STOP and raise a spec re-entry): each subagent spec carries its OWN complete `interrupt_on` (it overrides the inherited one; every tool the subagent keeps is listed) and its own `tools`, `permissions` and `middleware` (subagent middleware does not inherit from the parent). Inheritance of `interrupt_on` is not documented for a `CompiledSubAgent` or async subagent (unverified); treat it as not inherited, so such a subagent is forbidden unless it carries its own gate (proved by its own spike). The subagent interrupt surfaces in the parent's `updates` stream as `__interrupt__` and the worker resumes it with the same `Command(resume=...)` on the same `thread_id`. Sources: https://docs.langchain.com/oss/python/deepagents/subagents , https://docs.langchain.com/oss/python/deepagents/human-in-the-loop , https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/graph.py
- Idempotency: the interrupted node restarts from its beginning on resume, so any code before the interrupt in that node runs again; keep it idempotent (the HITL middleware's own pre-interrupt work only inspects the model's message, inference). Gated tools run only after approval, so a destructive tool body never runs before the pause. Interrupts are matched to resume values by position: never reorder them. Do not wrap interrupt-raising code in a bare try/except. A tool that calls `interrupt()` itself is not used (the gate is `interrupt_on`). Idempotency key for a destructive tool: `<approval_id>:<tool_call_id>`, where `approval_id` is the fresh UUID of the pending record written at this pause; a resume that pauses again writes a new record with a new id, so keys are never reused across pauses or turns. The worker passes `approval_id` to the run in `config["configurable"]` and the tool reads it (inference; the key spike confirms how the tool sees it). The key is stable across queue redelivery because the record is deleted only in the post-run transaction. Key spike (binding spike; failure path: binding defect: STOP and report (build-guide Step 4)): resume -> second pause -> second approval yields distinct keys and the second tool body runs. Source: https://docs.langchain.com/oss/python/langgraph/interrupts
- Eval runner: the fixture's approvals enter the worker handler as decision messages; the handler resumes with `Command(resume={"decisions": <list from the worker's builder>})` on the same `thread_id`, until the agent finishes or the fixture runs out.

## Caps
- One small custom middleware, `TurnCaps` (a subclass of `AgentMiddleware`), owns both caps, passed in `middleware=`; the built-in `ModelCallLimitMiddleware` and `ToolCallLimitMiddleware` are not used. Reason (same as the langchain-create-agent card, inference): their run counters are private untracked state in the LangChain library source on master, so they are not saved in checkpoints and a `Command(resume=...)` invocation starts them at zero; the docs say `run_limit` is "per single invocation". A spec turn that pauses for approval and resumes would then get a second budget. A global `ToolCallLimitMiddleware` also cannot use `exit_behavior="end"` (single tool only). Deep Agents does not wire either limit itself (neither appears in its `graph.py`), and no Deep Agents page shows them persisting across a resume. Sources: https://docs.langchain.com/oss/python/langchain/middleware/built-in , https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/tool_call_limit.py , https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/model_call_limit.py
- Why custom middleware is allowed and where it lands: `create_deep_agent` accepts instances via `middleware=`; a non-matching instance is inserted after the last core entry (Filesystem, SubAgent, Summarization, PatchToolCalls) and before the profile extras, prompt caching, memory and the HITL middleware. An instance whose `.name` matches a built-in entry replaces it, so never name it after a built-in. The customization page warns not to mutate middleware instance attributes in hooks (subagents, parallel tools and concurrent invocations race), which is why the counters live in graph state, not on `self`. Source: https://docs.langchain.com/oss/python/deepagents/customization . That `create_deep_agent` registers a middleware's custom `state_schema` fields (its `graph.py` hands `create_agent` only the `state_schema` argument, and merging middleware schemas happens inside `create_agent`) is unverified: the cap spike confirms the two fields exist in state and that input values overwrite them.
- Hook order consequence (inference from the documented hook order, https://docs.langchain.com/oss/python/langchain/middleware/custom , and the placement above): before-model hooks run first to last and after-model hooks last to first. Deep Agents appends HITL AFTER `TurnCaps`, so `HITL.after_model` runs BEFORE `TurnCaps.after_model`: the pause for an over-cap request happens before the cap check. This differs from the `create_agent` binding, where `TurnCaps` sits after HITL in the list and trips first. The binding does not reorder anything: the worker's pre-prompt guard (HITL gate, step 4) sees the pause, sends no approval prompt, and resumes with `DENIED: tool-call cap` rejects, so `TurnCaps.after_model` raises `ToolCapExceeded` with no tool executed and no approver involved. The guard does not cover interrupts raised inside a subagent. Cap spike test (f) proves it.
- State: a custom `AgentState` subclass assigned as the middleware's `state_schema` with two `NotRequired[int]` fields, `model_calls` and `tool_calls_requested`, and NO reducer, so an input value overwrites. Custom fields are passed in the invoke input next to `messages`. Source: https://docs.langchain.com/oss/python/langchain/middleware/custom
- Per turn: the worker puts `model_calls: 0` and `tool_calls_requested: 0` in the input of every NEW turn. A resume after approval is `Command(resume=...)` and carries no input, so the counters keep their checkpointed values across the pause (inference from the reducer-less state; the cap spike proves it).
- `before_model`: if `model_calls >= <spec step cap>` raise the binding's `StepCapExceeded`; otherwise return `{"model_calls": model_calls + 1}`. The check runs before each main-agent model call, so a cap of N allows N model calls. This hook also holds the deny jump (see HITL gate).
- `after_model`: read the last AI message, set `tool_calls_requested += len(ai_message.tool_calls)` and, if the total exceeds `<spec tool-call cap>`, raise `ToolCapExceeded`. The hook runs before the tool node, so the cap counts each tool call REQUESTED, not each tool-execution step, and parallel calls cannot overshoot; denied and blocked calls count as requested. Raising from a hook is not documented on the custom-middleware page, though the built-in limit middlewares raise from their hooks (library source above): the cap spike confirms the exception reaches the worker.
- Both exits map to the spec's single failure reply and a cap outcome: `StepCapExceeded` -> outcome `step_cap`, `ToolCapExceeded` -> outcome `tool_call_cap`, wall-clock expiry -> outcome `wall_clock`. The exception text is never sent to the user.
- Unit conversion (inference): the spec's step is one main-agent model call (one pass of model -> tools); `<spec step cap>` is used 1:1. The final answer is also a model call, so a turn that spends all N calls on tool use has no call left to answer and trips the cap; record this definition in `build.md`. Model calls made by the harness itself (the summarization middleware's own LLM call when it compacts history) do not pass through the agent's model node and are not counted (inference); they cost tokens, so the budget and economics sections count them as overhead. LangGraph's `recursion_limit` counts super-steps, not model calls, so it is not the step cap: `create_deep_agent` sets it to 9999 on the returned graph (library source above), so leave that unless the cap spike's measured super-steps per model call, multiplied by the step cap, exceeds it, in which case set it explicitly in the call config; catch `GraphRecursionError` as a backstop mapped to the same reply and the outcome `step_cap`. Source for `recursion_limit` and the error: https://docs.langchain.com/oss/python/langgraph/graph-api
- Subagent calls (only when the spec declares subagents; with none, the `task` tool is excluded and this does not apply): the main agent's `TurnCaps` counts the `task` call as ONE requested tool call and does not see the subagent's inner model and tool calls, because a subagent runs its own graph and its `middleware` does not inherit from the parent (inference from the subagents page, which says only that the subagent's own list is merged into its stack). So each subagent spec carries its own `TurnCaps` instance with the spec's per-subagent caps; a spec without per-subagent caps is a STOP (raise a spec re-entry; never invent a default). In a subagent `TurnCaps` reads its counters with `state.get("model_calls", 0)` and `state.get("tool_calls_requested", 0)`, because the subagent's state may not carry the fields at start (a fresh run starts at 0, inference). State in `build.md` that, with subagents, total work in a turn is bounded by (main tool-call cap x subagent caps) plus the wall-clock limit. Subagent cap exits must PROPAGATE to the worker: cap spike test (g) proves the worker receives `StepCapExceeded` / `ToolCapExceeded`. If instead the exception arrives only as an error tool message in the `task` result (a tool node may convert exceptions into tool messages; unverified), the subagent's `TurnCaps` does not raise: it returns `{"messages": [AIMessage("CAP:step ..." or "CAP:tool ...")], "jump_to": "end"}` (declared with `@hook_config(can_jump_to=["end"])`), so the subagent's final result starts with the marker, and the main `TurnCaps.before_model` raises the matching exception when a tool message STARTS WITH that marker and its `tool_call_id` belongs to the last AI message's `task` calls (checked before the deny jump and the step cap). Source: https://docs.langchain.com/oss/python/deepagents/subagents
- Wall-clock cap: the worker bounds each turn, including the time spent on a resume, with the spec's wall-clock limit (timeout around the agent call); expiry produces the same failure reply and the outcome `wall_clock`.
- No aborted turn (either cap, wall-clock, crash, deny-ends-turn) may leave an AI message with tool calls lacking tool results; most providers reject such a history (https://docs.langchain.com/oss/python/langchain/short-term-memory ). A cap raised in `after_model` leaves exactly that, and so can a timeout or crash during a tool call. Repair runs at TURN START, before new input (idempotent, so it survives a crash), and only when no approval is pending: read `agent.get_state(config)`; if the last AI message has tool calls without matching tool messages, append one notice per dangling call with `agent.update_state(config, {"messages": [...]}, as_node="tools")` (`tools` is the tool node's name in the streaming examples, https://docs.langchain.com/oss/python/langchain/streaming ; confirm the name in the abort spike). Notice text: for cap and deny exits, "not executed: <reason>"; for a wall-clock abort or crash, "outcome unknown - do not retry without the user" (the tool may have run). Deep Agents also ships `PatchToolCallsMiddleware`, which repairs an interrupted run's dangling calls automatically (https://docs.langchain.com/oss/python/deepagents/human-in-the-loop ); it is not relied on, because its wording would not say "outcome unknown" and when it fires is not documented (unverified). The abort spike checks that the binding's repair and `PatchToolCallsMiddleware` do not both leave duplicate tool results for one call.
- `harness_condition.force_step_cap`: script responses (through the test-only scripted-response middleware, see Eval runner mapping) that never give a final answer (a cycling script emitting one safe tool call per message, inference) and set the tool-call cap above the step cap, so the model-call cap is the one that trips. A tool-cap case, if the suite defines one, does the reverse.
- Never use one limit for both: a model call, a tool call and a super-step are different units.
- Cap spike (binding spike; runs at build-guide Step 4; failure path: binding defect: STOP and report (build-guide Step 4)). Pass tests: (a) tool cap 2: the model requests 1 gated call, the agent pauses for approval, the worker resumes, the model then requests 2 more calls to a SAFE-tier tool (so the cap, not an approval pause, is what stops them): `ToolCapExceeded` is raised on the 3rd cumulative call and neither of the 2 extra calls executed; (b) step cap N: exactly N model calls happen, then `StepCapExceeded`; (c) 3 parallel requested calls under cap 2 execute none of them; (d) the counters are 0 at the start of the next new turn on the same `thread_id`; (e) the exception reaches the worker from both hooks; (f) with a gated tool and a request that exceeds the cap: the pause occurs, the pre-prompt guard sends NO approval prompt, resumes with `DENIED: tool-call cap`, `ToolCapExceeded` reaches the worker and no tool executes; (g) with a declared subagent, the subagent's own caps trip and the worker receives `StepCapExceeded` / `ToolCapExceeded` (or, via the `CAP:` marker fallback, the main `TurnCaps.before_model` raises them), and the worker returns the single failure reply; (h) both `model_calls` and `tool_calls_requested` appear in `get_state(...).values`, proving the custom state fields are registered; (i) in a subagent whose state lacks the fields, `state.get(..., 0)` yields 0 and the counters advance.
- Abort spike (binding spike; failure path: binding defect: STOP and report (build-guide Step 4)): abort a turn mid-way (the tool cap, then a wall-clock timeout during a tool call), then run a follow-up turn on the same `thread_id` after the turn-start repair, against the real provider; the follow-up must succeed.

## Eval runner mapping
- Fresh agent and a fresh `InMemorySaver` per test, passed as `checkpointer=` (inference: the testing page uses `InMemorySaver` in tests; per-test isolation is the binding's own rule; LangChain's post says Deep Agent evals need an environment that resets per test, which for StateBackend is the fresh checkpointer and for a sandbox a fresh sandbox per test). Sources: https://docs.langchain.com/oss/python/langchain/test/unit-testing.md , https://www.langchain.com/blog/evaluating-deep-agents-our-learnings
- Model double: no fake chat model is passed as `model=`. The agent is built with the PRODUCTION model string (so the harness-profile key resolves and the tool surface is the production one) and a test-only scripted-response middleware (`ToolSurfaceProbe` extended with a script): its `wrap_model_call` hook returns the next scripted `AIMessage` (tool_calls with name, args and id, or a reply) without calling the handler, so no model call happens. Each model call consumes the next item. Whether this short-circuit works on the pin is Least-privilege spike test (d). With a real model profile, the summarization middleware uses its normal trigger, which short scripted cases do not reach. Sources: https://docs.langchain.com/oss/python/langchain/middleware/custom , https://docs.langchain.com/oss/python/deepagents/context-engineering
- Tool-surface preflight: before the first scripted response of every case, the runner asserts that the FIRST model request's tool names (recorded by the same middleware) equal the expected set (the spec's tool names plus the kept built-ins of K, each with its reason in `build.md`); the same assertion is a permanent CI unit test, repeated per declared subagent against that subagent's declared tools. The test double must not change the tool surface.
- Capture source: run the agent with `stream_mode="updates"` and `version="v2"` (needs LangGraph 1.1 or later; each chunk has `type`, `ns` and `data`, and `data` maps the node name to that node's update). Source: https://docs.langchain.com/oss/python/langchain/streaming
  - Trajectory = the REQUESTED calls: `(tool name, args)` from the `tool_calls` of the AI messages in the `model` node's updates, in order. This includes calls the HITL gate rejected or the cap blocked.
  - `forbidden` is checked against the EXECUTED calls plus the reply text (`skills/build/references/adapter-bindings.md`). The source of truth for executed is the tool wrapper: it records `(tool name, args, call id)` into the turn's executed list at body entry, AFTER argument validation and immediately before the body runs, so a refusal (unknown tool, invalid args, cap-blocked, denied, expired) never reaches it; executed = a tool body actually ran, whether it succeeded or raised. One rule, no per-case guessing.
  - Declared subagents: stream with `subgraphs=True` so the subagent's updates arrive with a non-empty `ns`; the trajectory is the main agent's requested calls (empty `ns`, including the `task` call) and `forbidden` checks the executed calls of ALL namespaces (inference; subagent calls are matched in a case only when the case names them). Source for `subgraphs=True`: https://docs.langchain.com/oss/python/deepagents/human-in-the-loop
- The PIPELINE runner implements EXACT, IN_ORDER and ANY_ORDER itself over the trajectory list, with `args_subset` matching (the golden-format: expected args must be a subset of actual args; never full-argument equality). The agentevals evaluators (`create_trajectory_match_evaluator`: strict, unordered, subset, superset; no in-order-with-extras mode; default argument matching is exact) are optional references only, as is the LangSmith pytest integration LangChain describes for Deep Agents. Sources: https://docs.langchain.com/oss/python/langchain/test/evals.md , https://www.langchain.com/blog/evaluating-deep-agents-our-learnings
- Approvals in a case: the fixture's approvals enter the worker handler as decision messages, answered by the worker's decisions-list builder (see HITL gate). The pre-prompt guard of HITL gate step 4 is the same function the worker uses.
- `harness_condition.force_step_cap` = scripted responses that never give a final answer (see Caps); `tool_always_errors` = the tool's injected BACKEND double raises and the real tool returns the spec's error observation (build-guide Step 5); the tool surface never changes (inference). The runner drives the worker's single turn handler (dequeue logic, expiry, repair, resume-or-end, cap mapping) against the in-memory saver and an in-memory repository, never the compiled graph's run call directly, so the deny, expiry and cap branches match production (inference).
- pass^k is computed by the pipeline runner; it is not native to the stack (research file `docs/superpowers/research/2026-10-07-stack-catalog/langchain-family.md`).
