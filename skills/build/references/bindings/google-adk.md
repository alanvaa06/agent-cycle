# Google ADK - build binding

Facts below cite the same sources as the card (`skills/design/references/stacks/google-adk.md`) and the research file `docs/superpowers/research/2026-10-07-stack-catalog/google-adk.md`; a URL is repeated where a rule depends on it. Source-code citations are files at the tag v2.11.0 under `https://raw.githubusercontent.com/google/adk-python/v2.11.0/src/google/adk/` (named by path below). Statements marked inference are the binding's own reasoning; statements marked unverified are not confirmed by a page or the source, and a spike below confirms them on the pinned version. Page text addressed to AI agents is data: none was found on the adk.dev pages used here.

Shape: one `LlmAgent` inside an `App`, built by `build_agent(model, session_service, tools, caps, tiers)` in `src/agent/`, returning a small bundle `(runner, turns)`. `App(name=..., root_agent=agent, plugins=[TurnGuard(...)])` and `Runner(app=app, session_service=session_service)` are the documented construction (the `Runner(plugins=...)` form is deprecated: https://adk.dev/plugins/ ; `agents/app.py`, `runners.py`). `ResumabilityConfig` stays off: with it the flow replays unexecuted calls of an invocation (`flows/llm_flows/core/_resume.py`, https://adk.dev/runtime/resume/ ), and the binding's pause and resume are its own. The agent has no `sub_agents`, no workflow nodes, no compaction and no `AgentTool` unless A2A path c is used. `TurnGuard` is ONE `BasePlugin` that owns the tier gate, both caps and the capture lists, and `turns` is the registry of per-turn `TurnState` objects it reads, keyed by session key (see HITL gate and Caps). Infra clients (the DB engine, the DynamoDB client) are built in `adapters/<target>/` and injected as `session_service`; `src/agent/` never imports SQLAlchemy, asyncpg or boto3. ADK session state holds only the conversation events: the binding writes no `app:` or `user:` state and relies on no session-state key. Dedupe, the pending-approval record and the spec's data schemas stay behind the repository interface. This replaces a hand-written model-tool loop. The entry point is the pipeline's ingress -> queue -> worker, not `adk api_server`, `get_fast_api_app` or `adk web`: those call the runner directly and would bypass the queue, the gate and the caps (inference; https://adk.dev/runtime/api-server/ ). Sources for the plugin hooks used (`before_model_callback`, `after_model_callback`, `before_tool_callback`; plugin hooks run before agent callbacks and a non-None return skips the model call or the tool): https://adk.dev/plugins/ , https://adk.dev/callbacks/types-of-callbacks/

## Sessions and state
- Postgres (incl. Supabase): `DatabaseSessionService(db_url="postgresql+asyncpg://...")`. The page requires an async driver (`asyncpg` for PostgreSQL): https://adk.dev/sessions/session/ . The `db` extra brings `sqlalchemy[asyncio]` but not the driver (`pyproject.toml`), so pin `asyncpg` separately. Extra keyword arguments go to `create_async_engine`, and `pool_pre_ping=True` is the default for non-SQLite URLs (`sessions/database_session_service.py`). The service writes the tables `sessions`, `events`, `app_states`, `user_states` and `adk_internal_metadata` (`sessions/schemas/v1.py`).
- Keys: `app_name` = the `App` name (one constant), `user_id` = the principal that OWNS the session (never an approver's id), `session_id` = the spec's session key. Each is limited to 128 characters by the schema (`sessions/schemas/shared.py`); ingress rejects longer keys.
- Per-session serialization: ADK serializes `append_event` per session in-process and takes `SELECT ... FOR UPDATE` row locks on PostgreSQL (https://adk.dev/sessions/session/ ), and `append_event` raises `StaleSessionError` when the `Session` object it is given is older than the stored one (`sessions/database_session_service.py`). The docs give no guidance for concurrent invocations on one session (https://adk.dev/runtime/event-loop/ ). The guarantee is the queue: queue ordering key = the session key, so one turn per session holds even when the approver is a different sender. Ingress resolves an approver's reply to the pending session's key before enqueueing. Every worker-side write to the session (repair, notices) uses a `Session` fetched with `get_session` immediately before it and retried once with a fresh one on `StaleSessionError`; a `Session` is never held across a run.
- Supabase connection: use the direct connection or the Supavisor session mode (port 5432); never the transaction pooler (port 6543), which does not support prepared statements (asyncpg prepares statements by default, inference). Source: https://supabase.com/docs/guides/database/connecting-to-postgres . Schema: put the ADK tables in a schema not exposed through the Data API (for example `agent_state`), selected with `connect_args={"server_settings": {"search_path": "agent_state"}}` on the engine (the asyncpg wiring is unverified), and enable RLS on them: https://supabase.com/docs/guides/database/postgres/row-level-security . The Free plan pauses projects after 1 week of inactivity, so it is not for production: https://supabase.com/pricing
- Schema setup runs once as the named one-shot migration job `agent-migrate` (compose service / ECS task / Cloud Run job): `await DatabaseSessionService(db_url).prepare_tables()`. `prepare_tables()` is public and its docstring says it can be called eagerly at startup (`sessions/database_session_service.py`). The service also calls it lazily before each database operation, so the worker's first operation re-runs the create-if-missing checks against an already migrated database; whether that works for a role without DDL rights is unverified (spike 3 below).
- DynamoDB: no ADK service found (unverified absence), so the AWS adapter subclasses `BaseSessionService` and implements `create_session`, `get_session`, `list_sessions`, `delete_session` and `append_event` (`sessions/base_session_service.py`). It stores each event as `event.model_dump(exclude_none=True, mode="json")` in an item keyed by session and event order, as the database service does (`sessions/schemas/v1.py`; JSON storage needs no change for the 2.0 Event schema, https://adk.dev/2.0/ ), calls the base `append_event` first so the in-memory session sees the state delta (as the base class does), and rejects a stale writer with `StaleSessionError` using a revision attribute and a conditional write (inference). DynamoDB item-size limits apply to an event with a large tool result: check them against the target table in the store spike (not verified here).
- Firestore: the official session service is Java only (https://adk.dev/integrations/firestore-session-service/ ). If the design's sessions seam names Firestore, STOP and raise a re-entry on the design's sessions seam (Cloud SQL Postgres used as plain Postgres is the candidate, inference); never swap the store silently.
- Pending-approval record: `pending_approvals(approval_id, session_key, calls, requested_at, elapsed_s, model_calls, tool_calls_requested)`. Every pause writes a NEW record with a fresh UUID `approval_id` (never the session key; at most one live record per session key, enforced by a unique index). `calls` holds, per pending call, `(index, call id, tool name, args, invocation id)`. Any run started from a record deletes it in its post-run transaction unless the run ended in a NEW pause, which writes a fresh record (new id) in that same transaction; within the transaction, delete the old record before inserting the new one (the unique index is per session key). "Ended in a pause" = `TurnState.pending` non-empty AND the run completed without an exception or timeout; otherwise `pending` is discarded, so a wall-clock abort with a gated call pending writes no record.
- Post-run commit order (ADK commits events to its store DURING the run, like a checkpointer stack): (a) the run has committed its events; (b) ONE repository transaction applies the lifecycle above (writes the new record with `requested_at` = now, taken just before sending, plus the calls, `elapsed_s` and both counters; deletes the record the run started from), writes the turn outcome to the dedupe record's `outcome` field (the same value is the `outcome` attribute of the `agent.turn` span), and sets `processed_at` and the reply text on the ingress dedupe record of the dequeued message; (c) send the prompt or the reply; (d) ack the queue message. A crash between (a) and (b) redelivers the message with `processed_at` unset: the turn runs again, the user message appears twice in the session, and a model proposal that pauses again writes a fresh pending record (nothing destructive ran, because every destructive call waits for approval; inference).
- Redelivery: the ingress dedupe record (keyed by the channel message id) carries `processed_at` and the reply text. On dequeue, a message whose record has `processed_at` set is not re-run: re-send the stored reply if the send may not have happened, then ack. Ingress dedupe alone only catches channel retries; this closes queue redelivery after a worker crash. The step-2a expiry commit does NOT set `processed_at`: only the final post-run commit of the turn that handles the message sets it.
- Crash marker: not used, because this is not an own-loop stack and the repair never needs to tell "not executed" from "unknown". The binding's cap and deny exits never leave an unanswered tool call in the session (see Caps and HITL gate), so every unanswered call the repair finds comes from a wall-clock abort, a tool failure or a crash, and ALWAYS gets "outcome unknown" (inference).
- Spikes (each runs before build-guide Step 4; numbered once here and defined in the section named). A failed store spike (1, 2) STOPS and raises a re-entry on the design's sessions seam, never a silent store swap; the other spikes state their own failure path:
  1. Supabase adds: the tables exist in `agent_state` and not in `public`, RLS is enabled, and the round trip works as the app's DB role. DynamoDB adds: the custom service passes the same round trip, rejects the stale writer, and stores an event with a large tool result under the item limit.
  2. Key limits (store spike; pass test: a 128-character `session_id` and `user_id` round trip; ingress rejects 129).
  3. Worker role (binding spike; pass test: after the migration job, a worker whose DB role has no CREATE privilege completes a turn; failure path: grant what the lazy `prepare_tables()` call needs and record it in `build.md`, a binding defect and not a sessions-seam re-entry).
  4. Pause (HITL gate).
  5. Resume (HITL gate).
  6. Deny and expiry (HITL gate).
  7. Caps (Caps).
  8. Abort (Caps).
  9. Model route (Model provider).

## HITL gate
- Why not the native flow: `require_confirmation` and `tool_context.request_confirmation` pause the tool and resume in a new run that carries an `adk_request_confirmation` FunctionResponse, found again in the session events (`flows/llm_flows/tools/_confirmation.py`). The feature is experimental and the docs list `DatabaseSessionService` and `VertexAiSessionService` as unsupported: https://adk.dev/tools-custom/confirmation/ . Nothing in the source read here explains why: a contract test that a confirmation request survives `append_event` covers the `database` backend (`tests/unittests/sessions/test_session_service.py`), while the runner-level confirmation test read uses an in-memory runner, so the database case is untested there (inference). The binding therefore does not set `require_confirmation` on any tool. A build that wants the native flow must first pass its own spike on the chosen store; that is not part of this binding.
- Recommended placement: ONE tier gate, `TurnGuard.before_tool_callback`. It reads the spec's tier table (tool name -> `safe`, `reversible`, `destructive`, plus a per-tool predicate for the reversible policy); a tool missing from the table is treated as destructive (fail closed). It covers function tools and MCP tools in one place. Plugin hooks run before agent callbacks, and a dict return skips the tool: https://adk.dev/plugins/ , https://adk.dev/callbacks/types-of-callbacks/ . The gate runs before ADK's own confirmation gate (`flows/llm_flows/tools/_caller.py`), which stays idle because no tool sets `require_confirmation`.
- Pausing (the first run). For a gated call with no matching one-shot approval the callback (1) appends `(index = its position in pending, call id from tool_context.function_call_id, tool name, args, invocation id)` to `TurnState.pending`, (2) sets `tool_context.actions.skip_summarization = True`, (3) returns `{"status": "PENDING_APPROVAL", "detail": "not run; waiting for an approver"}`. The tool body never runs, the response event is a final response (`events/event.py`: `skip_summarization` makes `is_final_response()` true) and the flow ends the run (`flows/llm_flows/base_llm_flow.py`). The session now holds the model event with the call and a function-response event answering it, so nothing dangles. Safe siblings of the same response ran normally in the first run; parallel responses are merged into one event (`flows/llm_flows/tools/_batch_executor.py`) and the pause spike confirms that one gated call among safe calls still ends the run (inference from the merge code: actions are deep-merged).
- Worker sequence:
  1. Dequeue the message for the session (ordering key = session key). If the ingress dedupe record of the message has `processed_at` set, do not re-run it: re-send the stored reply if the send may not have happened, then ack.
  2. Read the `pending_approvals` record for the session key (own repository; there is no framework state to inspect).
  2a. If an approval is pending, check its expiry now: when it is older than the spec's TTL, the worker does not run the agent. It appends one `EXPIRED:` notice per pending call to the session (see Deny), commits (delete the record only; the dedupe record's `processed_at` is NOT set here, because the dequeued message has not been handled yet), records the outcome `hitl_expired` as a span event on the span of the turn that then handles the message (not as a dedupe-record field), sends the spec's expiry notice only if the spec defines one (no model reply from this step), then handles the dequeued message as a new turn; only that turn's final post-run commit sets `processed_at` (inference). The record's `requested_at` is the time the worker sent the approval prompt.
  3. If an approval is pending and not expired: parse the message (or the approver's reply) into a decision. Approve: run the resume (below). Deny: see Deny. Anything else: keep the approval pending and reply with the spec's pending-approval prompt (or deny if the spec says so). Otherwise, with nothing pending, start a NEW turn: run the turn-start repair (see Caps), build a fresh `TurnState`, and run with the user's text as `new_message`.
  4. Post-run: commit order under Sessions and state.
- Resume = a new run that replays the exact approved call (the framework cannot resume a skipped tool, so the worker re-issues it; inference, proven by spike 5):
  - The worker builds `TurnState(approved=<the record's calls, each with its key "<approval_id>:<index>">, replay=<the same calls>, model_calls and tool_calls_requested from the record)` and runs with `new_message` = a short user-role text such as "APPROVED: the pending request was approved". The text is context for the model only; the approval is the `TurnState` entry, never the text.
  - `TurnGuard.before_model_callback` finds `replay` non-empty on the first model call of the run, sets `TurnState.replay` to empty BEFORE returning it (so the replay is returned at most once per run, however many model calls follow), and returns an `LlmResponse` whose content is the approved function calls (same name and args, role `model`). A callback response skips the model call, and `increment_llm_call_count` runs only after the callbacks (`flows/llm_flows/core/_model_call.py`), so the replay costs no model call and no counter step; the flow then finishes the event (assigns `adk-` call ids, `flows/llm_flows/core/_finalizer.py`) and executes the calls like any model response. `after_model_callback` is not run for it, so the replayed calls are not counted again (they were counted when first requested).
  - The gate then finds each call in `approved` by (tool name, canonical JSON of args), removes it (one-shot, so approvals are never cached), records `TurnState.keys[tool_context.function_call_id] = <that call's key>` and lets the call run. If the model later proposes any other destructive call, the gate pauses again.
  - Idempotency key: unique per APPROVED CALL, `"<approval_id>:<index>"`, where `approval_id` is the fresh UUID of the pending record written at that pause and `index` is the call's position in the record (not the function call id: replayed calls get fresh `adk-` function_call_ids on every run, so a function_call_id is not stable across redelivery). A resume that pauses again writes a new record with a new `approval_id`, so keys are never reused across pauses or turns. Every destructive tool reads its key with the helper `approval_key(tool_context)`, built with the `turns` registry and injected into the tools factory (it returns `TurnState.keys.get(tool_context.function_call_id)`), passes it to its backend as the idempotency key, and refuses to run when it is None. The key map is keyed by call id, not kept in `temp:` state, because parallel calls of one run would share one `temp:` slot (inference). The key is stable across redelivery because the record is deleted only in the post-run transaction, so a crash after the tool ran but before the commit re-runs the resume with the same keys (inference). The card's trap "tools run at least once" is this obligation.
  - Non-gated calls of the original response already ran in the first run and are not replayed: only the pending calls are in `replay`.
- Decision value. The spec's three outcomes map to the worker's own `Decision` value (ADK's `ToolConfirmation` is not used):
  - approve -> `Decision("approve")`.
  - deny -> `Decision("deny", reason)`.
  - edit -> not supported. The framework re-executes only the original arguments (the native resume checks that arguments match, `_confirmation.py`) and this binding replays them verbatim. If the spec requires an edit outcome, STOP and raise a re-entry on the design's hitl_gate seam (inference).
  - Reply covering several gated calls (design choice, inference): one approve or deny reply applies to every pending call of the record, and the worker's single decision builder is used by the eval runner too.
- Deny. The worker writes ONE notice event per pending call, with the text prefix `DENIED:` (or `EXPIRED:` from step 2a): `Event(invocation_id=<the record's invocation id>, author="user", content=Content(role="user", parts=[Part(text="DENIED: <tool> (call <index>) was not run: <reason>")]), custom_metadata={"agent_notice": "denied", "approval_id": <id>, "call_index": <index>})`, appended through `session_service.append_event`. The write is idempotent: before appending, the worker fetches the session and skips every call index whose notice with the same `approval_id` already exists, so a crash between two notices or a redelivery repeats the step safely.
  - If the spec says a deny ends the turn: no further tool executes and no model request is made. The construct that routes to the end is the worker itself: it does NOT run the agent. It appends the notices above, so later turns know the pending request was not run. Then it commits (delete the record, outcome `hitl_denied`, dedupe record with `processed_at` and the deny reply), sends the spec's deny reply, and acks.
  - If the spec lets the model continue after a deny: run with `new_message` = the `DENIED:` text, `approved` and `replay` empty, and `model_calls`, `tool_calls_requested` and `elapsed_s` taken from the record (a deny does not reset the turn's budgets); the model sees the denial and continues, a repeated destructive proposal pauses again, and the record is deleted in the post-run transaction unless that run ends in a new pause. State which of the two applies in `build.md`.
  - A denied call still counts as a requested tool call for the tool cap (see Caps).
  - Deny and expiry spike (spike 6; binding spike; failure path: fix this binding): after a deny under deny-ends-turn, and after a step-2a expiry, a recording tool shows zero further executions, no model request happens for the deny, the notices exist once per call even when the step is run twice, the expiry commit leaves the dedupe record's `processed_at` unset, and a follow-up turn on the same session succeeds against the real provider.
- Tier mapping, built from the spec's tool contracts: destructive -> gated every time, never cached (each approval is one-shot and bound to one tool name plus one argument set), decisions approve or deny only; reversible -> per design policy (gated, or auto); safe -> auto. Approval is not an authorization boundary: only an authenticated approver identity resolved by ingress may produce a decision, and each sensitive tool also checks authorization in its own body.
- Fail closed when bypassed: `TurnGuard` raises if no `TurnState` is registered for the session. The plugin wrapper turns that into a `RuntimeError` that fails the run (https://adk.dev/plugins/ ), so a run started outside the worker cannot execute ungated tools.
- Eval runner: the fixture's approvals enter the worker handler as decision messages (see Eval runner mapping); the runner never calls `Runner.run_async` itself.
- Pause spike (spike 4; binding spike; failure path: fix this binding). Pass tests: a destructive call ends the run with the tool body run zero times, the model double called once, `TurnState.pending` holding the call, and the stored session ending with the model event and a function-response event whose id matches the call (record the tail shape in `build.md`); a response with one gated and one safe call runs the safe tool once, the gated tool zero times and makes no second model request; a tool absent from the tier table pauses; a safe tool never pauses; a run with no registered `TurnState` fails.
- Resume spike (spike 5; binding spike; failure path: fix this binding). Pass tests: (a) approve runs the tool body exactly once with the key `"<approval_id>:<index>"`; the replayed call has an `adk-` id, the stored events hold exactly ONE replayed model event, each stored call id has exactly one response, and a final model answer follows; (b) two parallel approved calls (identical or different) each run once with DISTINCT keys; (c) resume -> second pause (a different destructive call) -> second approval yields a new `approval_id`, keys distinct from the first resume's, and the second tool body runs; (d) deny-and-continue runs the body zero times; (e) a wall-clock abort of a resume deletes the record it started from and a run aborted with a gated call pending writes no record; (f) the resume's own post-replay model call is made against the spec's REAL route with thinking or reasoning configured as in production and succeeds: the history it sends contains a function call the model did not produce, and some providers validate such calls (for example thought signatures on Gemini function calls; assuming this can happen, since the signature section of the Gemini thinking guide, https://ai.google.dev/gemini-api/docs/thinking , did not describe injected function calls or a dummy or skip value in what was read, so any such mechanism is unverified); (g) after the resume a follow-up turn on the same session succeeds against the real provider. Failure paths: if the replayed call is not executed by the flow, the binding is wrong: fix this binding, not the sessions seam. If (f) fails, use the provider-documented mechanism for injected function calls (a dummy or skip signature value) in the replay response and cite it in `build.md`, if the provider documents one; otherwise STOP and raise a re-entry on the design's hitl_gate seam.

## Caps
- Step cap: own counter in `TurnGuard`, plus the native limit as a backstop. Reason: `RunConfig.max_llm_calls` is counted on the invocation context (`agents/invocation_context.py`, `_InvocationCostManager`), every `run_async` builds a new context, so an approval resume restarts it; the page offers no way to carry it (https://adk.dev/runtime/runconfig/ ); compositional function calling also counts against it since 2.7.0 (https://github.com/google/adk-python/releases/tag/v2.7.0 ), which is not the spec's unit.
  - `TurnState.model_calls` counts model calls. `before_model_callback`: if `model_calls >= <spec step cap>`, set the outcome `step_cap` and return a stub `LlmResponse` (role `model`, one text part holding the spec's failure reply); otherwise add 1 and return None. The check runs before each model call, so a cap of N allows N model calls. The stub is a final text response, so the run ends and no tool call is left dangling. The replay response (HITL gate) is returned before this check and does not count.
  - Backstop: every run passes `RunConfig(max_llm_calls=max(<step cap> - model_calls, 1), streaming_mode=StreamingMode.NONE)`. The `max(..., 1)` matters: 0 or below means unlimited (https://adk.dev/runtime/runconfig/ ). An explicit value overrides the `ADK_MAX_LLM_CALLS` default (`agents/run_config.py`, `default_factory`). `LlmCallsLimitExceededError` is also mapped to the outcome `step_cap`.
  - Unit conversion (inference): the spec's step is one model call, used 1:1. The final answer is also a model call, so a turn that spends all N calls on tool use has no call left to answer and trips the cap; record this definition in `build.md`.
- Tool-call cap: own counter. `after_model_callback` (skip partial responses): read every function call of the response, append `(name, args)` to `TurnState.requested`, add `len(calls)` to `TurnState.tool_calls_requested`, and if the total exceeds `<spec tool-call cap>`, set the outcome `tool_call_cap` and return a stub `LlmResponse` with the spec's failure reply and NO function calls. The callback runs before any tool of that response, so the cap counts each tool call REQUESTED (denied, pending and blocked calls included) and parallel calls cannot overshoot. A replaced response is what the flow persists, so the blocked calls never reach the session and nothing dangles (after-model hooks may replace the response: https://adk.dev/callbacks/types-of-callbacks/ ; `flows/llm_flows/core/_finalizer.py`).
- Both caps are PER TURN: a new turn starts `TurnState` at 0 and 0; a resume (and a deny-and-continue run) starts from the values stored in the `pending_approvals` record (`model_calls`, `tool_calls_requested`, `elapsed_s`). Both counters are separate; never use one limit for both.
- Both cap exits produce the spec's single failure reply and a cap outcome: `step_cap`, `tool_call_cap`, `wall_clock` (and `error` for any other exception, which also gets the failure reply). The worker sends the reply from the spec, taken from `TurnState`, not from model text; the stub text is the same string so the stored history agrees.
- Wall-clock cap: the budget is per TURN, resume time included. The worker stores `elapsed_s` in the record at each pause and gives a resume the remainder (limit minus `elapsed_s`; the wait for the approver is not counted; inference); a new turn gets the full limit. The worker wraps the whole `async for event in runner.run_async(...)` in `asyncio.timeout(remaining)` (`asyncio.timeout` needs Python 3.11 or later and the package supports 3.10, so on 3.10 use `asyncio.wait_for` around a coroutine that consumes the generator; standard-library behavior). The timeout cancels the consumer; since 2.11.0 ADK cancels the in-flight tool call when the caller is cancelled (https://github.com/google/adk-python/releases/tag/v2.11.0 ). `abort_signal` is NOT used for this cap: it seals dangling calls with the text "Invocation was aborted by client." (`events/_abort_events.py`), which reads as "not executed" (https://github.com/google/adk-python/blob/v2.11.0/docs/guides/runners/runner/abort.md ). Tools must be `async def` or run on `tool_thread_pool_config`, because a synchronous tool blocks the loop and the timeout cannot fire until it returns (`tool_thread_pool_config` is a `RunConfig` field: `agents/run_config.py`; the blocking limitation is on the same abort page). Expiry gives the single failure reply and the outcome `wall_clock`.
- No aborted turn may leave a model event with tool calls lacking responses. The cap exits and deny-ends-turn never do (above). A wall-clock abort, a tool exception or a crash can. ADK drops unanswered calls when it builds the next request, so the provider does not reject the history, but the model then never learns that the tool may have run (abort page above). Repair runs at TURN START, before new input (idempotent, so it survives a crash), and only when no approval is pending: fetch the session; collect every function call with an id in the events that has no function response with that id; for each model event that has such calls, append `Event(invocation_id=<that event's invocation id>, author=<that event's author>, branch=<that event's branch>, content=Content(role="user", parts=[Part(function_response=FunctionResponse(id=<call id>, name=<call name>, response={"error": "outcome unknown - do not retry without the user"}))]), custom_metadata={"agent_notice": "repair"})` through `session_service.append_event`. The shape copies ADK's own abort sealing (`events/_abort_events.py`). A call whose id is empty is not matched by ADK either; the spike records whether the model double and the real provider return ids. Every repaired call says "outcome unknown", never "not executed".
- `harness_condition.force_step_cap`: the model double never gives a final answer (every response is one safe tool call) and the tool-call cap is set above the step cap, so the step cap is the one that trips. A tool-cap case does the reverse.
- Cap spike (spike 7; binding spike; runs before build-guide Step 4; failure path: fix this binding). Pass tests: (a) tool cap 2: the model requests 1 call, the turn pauses for approval, the worker resumes, the model then requests 2 more calls: the cap trips on the 3rd cumulative call, neither extra call ran, and the stored events hold no function call from the blocked response; (b) step cap N: exactly N model calls happen, then the stub, and across an approval pause the total is still N; (c) 3 parallel requested calls under cap 2 execute none of them; (d) both counters are 0 at the start of the next new turn on the same session; (e) a resume with `model_calls == <step cap>` runs the replayed tool and then ends with the stub, and `max_llm_calls` was passed as 1, not 0; (f) the stub replaces the response when a real provider returns the function calls (not only the double).
- Abort spike (spike 8; binding spike; failure path: fix this binding): abort a turn mid-tool with the wall-clock timeout, record what the stored events end with (expected: the model event with the call and no response), run the next new turn after the turn-start repair against the real provider, and require that it succeeds, that each call id has exactly one response, and that the next session write raises no `StaleSessionError`. Also run a tool that raises an exception: the worker maps it to the failure reply and the outcome `error`, and the repair covers the dangling call. Also abort a run that has a gated call pending (the timeout fires after the gate paused): no pending record is written.

## Model provider
- Selection rule: when the spec's route is a Gemini model, pass the model name string (or a `Gemini` object) to `LlmAgent(model=...)`; for any other route use `LiteLlm(model=<spec route>)` from `google.adk.models.lite_llm`. Source: https://adk.dev/agents/models/litellm/ . Claude in Python is native on Agent Platform (Vertex); the direct Anthropic API goes through LiteLLM (research file, citing https://adk.dev/agents/models/anthropic/ ).
- Format conversion: LiteLLM routes are `provider/model` and `LiteLlm` takes that string unchanged; a route that starts with `gemini/` is converted to the native route by dropping the prefix (inference that the names match). Keys come from the secret store, never from the route string.
- `litellm>=1.84` is a minimum; pin an exact version in the lockfile with hashes and never 1.82.7 or 1.82.8 (compromised on PyPI 2026-03-24). On Windows set `PYTHONUTF8=1` (cp1252 decoding error in LiteLLM). Source: https://adk.dev/agents/models/litellm/
- `FallbackModel` exists (2.9.0, research file citing https://github.com/google/adk-python/releases ); use it only if the spec asks for provider fallback, and count its calls against the step cap in the cap spike (the callbacks run once per `LlmAgent` model step; whether a fallback attempt is a second counted call is unverified).
- Model route spike (spike 9; binding spike; failure path: fix this binding or the route): one turn with a tool call through the chosen route against the real provider returns the function call with its arguments.

## Telemetry
- ADK emits OTel GenAI spans (`invoke_agent`, `execute_tool`, `generate_content`) with `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` on the `generate_content` span (https://adk.dev/observability/traces/ ). Set `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (or `OTEL_EXPORTER_OTLP_ENDPOINT`) to the design's backend and call `maybe_set_otel_providers()` from `google.adk.telemetry.setup` once at process start; it adds OTLP exporters only when one of those variables is set, and it imports the HTTP exporter lazily (`telemetry/setup.py`), so install `opentelemetry-exporter-otlp-proto-http` yourself. The endpoint variable is a base URL (OpenTelemetry convention, inference).
- Content: prompts and responses are elided from the log events unless `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` is enabled (`telemetry/_stable_semconv.py`); its default is unverified, so set it explicitly to false unless the spec's data policy allows content in traces. The adk.dev traces page documents a content flag only for Kotlin.
- The worker opens one per-turn span (for example `agent.turn`) carrying the spec's attributes and the turn outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`, `error`; names follow the spec). A turn that spans an approval pause is one span per run linked by the turn id; ADK's spans nest under the ambient span (inference).
- Egress: do not use `--otel_to_cloud` or `get_gcp_exporters()` (Cloud Trace is opt in: https://adk.dev/observability/traces/ ), and do not install the `gcp` extras unless the design uses them.
- MANDATORY SPIKE (spike 10) before the build relies on it, with a REAL model call (fakes report no usage): emit one turn and confirm the backend receives `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` above zero on the `generate_content` span, and that no prompt or response text is present when the content flag is false. Fallback spans (failure path): `TurnGuard.after_model_callback` opens a child span of `agent.turn` and sets those attributes from `llm_response.usage_metadata` (inference); if even that yields no usage, record the gap in `build.md` and raise a telemetry re-entry on the design.
- Egress check (part of the spike): pass test = with outbound traffic limited to the OTLP endpoint and the model provider's hosts, a traced turn completes and no connection to any other host is attempted; failure path: find the offending host, remove its cause (unused extra, env variable) and re-run; if egress persists, raise a telemetry re-entry on the design.

## Eval runner mapping
- Runner = worker: the eval runner drives the worker's single turn handler (dequeue logic, pending check, expiry, repair, resume-or-end, cap mapping, commit order) against an in-memory implementation of the repository interface and a fresh `InMemorySessionService` per test, never `Runner.run_async` directly, so the deny, expiry and cap branches cannot diverge from production. The fixture's messages and approvals enter as queue messages; the expiry clock is injected.
- Model double: a `BaseLlm` subclass (`models/base_llm.py`: a `model` string and `generate_content_async(llm_request, stream)` that yields `LlmResponse` objects) scripted with function-call and text responses, passed as `LlmAgent(model=double)`. It replaces only the model, never the tools or the plugin, so the tool surface and every callback run as in production (inference: custom `BaseLlm` is the documented model extension point; spike 11 confirms it on this version).
- Capture source: the `TurnState` lists filled by `TurnGuard`, read by the runner after each turn.
  - Trajectory = the REQUESTED calls: `TurnState.requested`, the `(name, args)` of every function call in every model response as the plugin received it, in order, including calls the cap blocked and calls the gate paused. Replayed calls are not added (they were requested before the pause).
  - `forbidden` is checked against the EXECUTED calls, `TurnState.executed` (a `(name, args)` is added when the gate lets a call proceed to its body, whether or not the body then fails), plus the reply text (`skills/build/references/adapter-bindings.md`). One rule, no per-case guessing.
- The PIPELINE runner implements EXACT, IN_ORDER and ANY_ORDER itself over the trajectory list, with `args_subset` matching (golden-format: expected args must be a subset of actual args; never full-argument equality). ADK's `tool_trajectory_avg_score` has the same three match types but compares arguments for equality unless they are ignored (`evaluation/trajectory_evaluator.py`), so `AgentEvaluator` is an optional reference only. It loads the agent from a module path (`agent_module`, `evaluation/agent_evaluator.py`), which does not fit the injected factory.
- pass^k is computed by the pipeline runner from its own per-case results. `AgentEvaluator` averages scores across `num_runs` (default 2) and compares the mean with the threshold (`statistics.mean`, `evaluation/agent_evaluator.py`), which is not pass^k; do not use `num_runs`.
- Judge and simulator models: set explicitly to the rubric's model in every metric's `judge_model_options`. The `JudgeModelOptions.judge_model` default is `gemini-2.5-flash` in the 2.11.0 source (`evaluation/eval_metrics.py`) and the docs examples use `gemini-flash-latest` (https://adk.dev/evaluate/criteria/ ); the user simulator's default model is unverified. A judge call to a Gemini model needs Google credentials and sends data to Google; the pipeline's LLM judges keep using the rubric's model.
- Approvals in a case: the fixture's approvals enter the worker handler as decision messages and are answered by the worker's decision builder (see HITL gate). `harness_condition.force_step_cap` is specified under Caps. `tool_always_errors` = the tool's injected BACKEND double raises and the real tool catches it and returns the spec's error observation as its result (build-guide Step 5); the tool surface never changes. A tool that lets the exception escape fails the run, and the worker maps it to the failure reply and the outcome `error`.
- Tool-surface preflight: the eval runner and a permanent CI unit test assert that the FIRST model request's tool names equal the spec's tool set (plus any built-in kept on purpose, each with its reason in `build.md`; this binding keeps none: a single `LlmAgent` with no sub-agents, output schema or `AgentTool` adds none, inference). Capture source: the model double records, on its first call, the function-declaration names in `llm_request.config.tools[*].function_declarations[*].name` (what a provider would receive) and the keys of `llm_request.tools_dict`; the production `TurnGuard` adds nothing to either. Negative control (the surface is filtered by `McpToolset(tool_filter=...)`): a fake MCP server exposes one extra tool outside the spec; with the filter the preflight passes, and a second run of the same test with the filter removed MUST fail on that extra name, proving the preflight can see a filtered tool.
- Eval double spike (spike 11; binding spike; failure path: fix this binding): the scripted `BaseLlm` double drives a full pause, resume and finish through the worker handler on `InMemorySessionService` and on the real `DatabaseSessionService` with the same trajectory.

## A2A and MCP
- A2A is experimental in both roles (https://adk.dev/a2a/quickstart-exposing/ , https://adk.dev/a2a/quickstart-consuming/ ); install `google-adk[a2a]`; ADK works with `a2a-sdk` 0.3.x (compatibility mode) and 1.x, and the page says new integrations should target 1.x. Record which path in interop.md.
  - (a) `to_a2a(agent, port=...)` builds its own runner unless `runner=` is passed, and a task served that way would not go through the ingress queue, the worker, the gate or the caps (`TurnGuard` fails such a run, see HITL gate). Use it only for an agent without gated tools, and only after a spike shows each task goes through the same queue (key = session key) (inference).
  - (b) Recommended when HITL is on: an own server built with `a2a-sdk` that enqueues into the same ingress queue and answers from the repository (own code, inference).
  - (c) A2A client: `RemoteA2aAgent` (`from google.adk.agents.remote_a2a_agent import RemoteA2aAgent`, constructor `name=` and `agent_card=`) exposed to the root agent as one tool with `AgentTool`, whose tier in the tier table follows the design (inference; whether `AgentTool` runs the remote agent under this runner's plugins is unverified, so the A2A spike must show the gate and the counters see the call).
  - A2A spike (spike 12, when the design names A2A; binding spike; failure path: fix this binding or use path b): a task through the chosen path appears in the ingress queue with the session key as ordering key, and a gated tool reached through it pauses.
- MCP client: `McpToolset` from `google.adk.tools.mcp_tool` with `connection_params=StreamableHTTPConnectionParams(url=..., headers=...)` (remote) or `StdioConnectionParams`; ALWAYS pass `tool_filter=[...]` with only the tools the spec names; use `auth_scheme` and `auth_credential` for auth rather than hand-built headers; call `await toolset.close()` at worker shutdown; connections are not restored with sessions (agents re-initialize them). Source: https://adk.dev/tools-custom/mcp-tools/ . Every MCP tool name must appear in the tier table (an unlisted tool is treated as destructive). The MCP spike (spike 13; pass test: the server's filtered tool names appear in the first model request and a destructive MCP tool pauses; failure path: fix this binding) runs when the design names an MCP server.
- MCP serving: `to_mcp_server` exposes an agent (research file); route calls through the ingress queue so the HITL and cap rules still hold (inference). Not part of this binding unless the design asks for it.
