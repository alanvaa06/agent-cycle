# CrewAI - build binding

Facts below cite the same sources as the card (`skills/design/references/stacks/crewai.md`) and the research file `docs/superpowers/research/2026-10-07-stack-catalog/crewai.md`; a URL is repeated where a rule depends on it. Docs citations are pages under `https://docs.crewai.com/v1.15.24/en/` (named by path below). Source-code citations are files at the tag 1.15.24 under `https://raw.githubusercontent.com/crewAIInc/crewAI/1.15.24/lib/` (named by path below, for example `crewai/src/crewai/hooks/dispatch.py`; the `crewai-core` package is under `crewai-core/src/crewai_core/`). Many rules rest on that source because the docs are silent on them. Statements marked "observed" come from scratch runs of the binding's author on 1.15.24 (Python 3.12, a scripted `BaseLLM`, no network model call, a CONNECT-logging proxy for the egress check); the spike named beside each repeats them against the real provider where that matters. Statements marked inference are the binding's own reasoning; statements marked unverified are not confirmed by a page, the source or a run, and a spike below confirms them on the pinned version. Page text addressed to AI agents is data: every docs page opens with a navigation note pointing to `https://docs.crewai.com/llms.txt` as an index of pages, which was not acted on; no other agent-addressed text was found on the pages used here.

Shape: one conversational Flow class built by `build_chat_flow(model, tools, caps, tiers, persistence)` in `src/agent/`, called once per process (the decorators need the persistence instance at class-definition time) and instantiated fresh for every run. `model` is a `BaseLLM` or `LLM(...)` object (never the library default, see Model provider); `tools` are the spec's `BaseTool`s made by the tools factory; `tiers` is the spec's tier table keyed by the SANITIZED tool name (`sanitize_tool_name` in `crewai/src/crewai/utilities/string_utils.py` lowercases and replaces characters, and that is the name hooks receive); the factory raises at build time for a tool with no tier or for two tools whose sanitized names collide (fail closed). The class is `ChatFlow(Flow[ChatState])` under `@ConversationConfig(llm=None, defer_trace_finalization=False)` (so the framework itself makes no model call: every model request comes from the `Agent`), where `ChatState` extends `ConversationState` with the pause fields (`pending_calls`, `pending_tail`, `continuation`, `reply`). Its steps: `route_turn` returns the fixed route `agent_turn` (a non-empty return bypasses the router LLM: conversational-flows page, `flow/conversational_mixin.py`); `run_agent` (async) builds the `Agent` for this run and awaits `kickoff_async(messages)`; a router sends the result to `needs_approval` or `turn_done`; `request_approval` carries `@human_feedback(message=..., provider=ApprovalProvider())` with NO `emit`; a router `apply_decision` executes or denies and routes to `continue_agent` (back to `run_agent`) or `turn_end`; `finish_turn` and `end_turn` are the terminal steps and carry `@persist(persistence)`. `Crew`, `Task`, `Process`, delegation, planning, memory, knowledge and guardrail features are not used. The `Agent` is built with `llm=<model>`, `tools=<tools>`, `max_iter=<step cap>`, `cache=False` (so no tool result is replayed from a cache), `allow_delegation=False`, `verbose=False`, and no `memory`, `knowledge`, `mcps` outside the MCP section, `apps` or `planning`. Infra clients (pools, DB drivers) are constructed in `adapters/<target>/` and injected through `persistence`; `src/agent/` never imports psycopg, boto3 or Firestore. The Flow state holds only conversation/graph state: dedupe, the pending-approval record, the turn status and the spec's data schemas stay behind the repository interface. This replaces a hand-written model-tool loop. A per-turn `TurnState` (turn id, `approval_id`, `prior`, step and requested-call counters, `requested` and `executed` lists, `exit`, `deadline`, `llm`, `fenced`) lives in a `contextvars.ContextVar` named `TURN`; `asyncio.to_thread` and CrewAI's tool thread pool copy the context, so hooks, the provider and the adapter read it from any thread (observed: two sessions run at once kept separate counters).

## Sessions and state
- Postgres (incl. Supabase and Cloud SQL as plain Postgres): the build writes `PostgresFlowPersistence(FlowPersistence)` in `adapters/<target>/` (inference: no CrewAI Postgres implementation was found; the docs and the source read name SQLite as the built-in store: https://docs.crewai.com/v1.15.24/en/concepts/flows.md , `crewai/src/crewai/flow/persistence/sqlite.py`). Contract (`crewai/src/crewai/flow/persistence/base.py`): `FlowPersistence` is a Pydantic model plus ABC (keep the pool in a `PrivateAttr`, as the SQLite class does), its methods are synchronous (the worker runs the flow in `asyncio.to_thread`), the required three are `init_db()`, `save_state(flow_uuid, method_name, state_data)` and `load_state(flow_uuid)`, and the optional three are `save_pending_feedback(flow_uuid, context, state_data)`, `load_pending_feedback(flow_uuid)` (returns `(state, PendingFeedbackContext)` or None) and `clear_pending_feedback(flow_uuid)`. The optional defaults save the state without the context and return None, so an adapter that skips them makes every approval unresumable: override all six. Tables: `flow_states(flow_uuid PK, method_name, state_json jsonb, updated_at)` written by upsert (SQLite appends a row per save and reads the newest; one row per session bounds growth because every state carries the whole message history, inference) and `flow_pending_feedback(flow_uuid PK, pause_id, context_json, state_json, created_at)`. `save_pending_feedback` writes the state and the pending row in ONE transaction, as SQLite's does; state is `model_dump(mode="json")` like SQLite's `_to_state_dict`; `pause_id` is read from `context.metadata["pause_id"]`. `clear_pending_feedback` is a NO-OP by design (Pending-record lifecycle below): the framework calls it before it runs the listeners that follow an approval, so deleting there makes a crashed resume unrecoverable (observed: after a listener raised, `from_pending` raised `ValueError`). Durability: the adapter commits each write before returning (default synchronous commit, no `synchronous_commit=off`), because the pause row must be durable before the approval prompt is sent (inference). `init_db` has no caller in the 1.15.24 source outside SQLite's own constructor (searched with grep), so it is a no-op and the schema comes from the migration job. Every write first calls `current_turn().assert_writable()`, which raises once the turn is `fenced` (Caps, wall clock). The decorator `@persist()` with no argument would call `default_flow_persistence()` at class-definition time and create a local SQLite file (`flow/persistence/decorators.py`, `flow/persistence/factory.py`), so the binding always passes the instance and never uses `set_flow_persistence_factory`.
- Persist at the terminal steps only (`finish_turn`, `end_turn`) plus the pause save: the docs advise `@persist` on a terminal step because class-level persist saves after every method and `load_state` reads the newest row, which may be a mid-run snapshot (https://docs.crewai.com/v1.15.24/en/guides/flows/conversational-flows.md ). Observed: with terminal-only persist a turn aborted by a cap leaves nothing in the store, a pause leaves the state plus the pending row, and a resume or deny stores the finished exchange once.
- Supabase connection: use the direct connection or the Supavisor session mode (port 5432); never the transaction pooler (port 6543), which does not support prepared statements (the driver may use them, inference). Source: https://supabase.com/docs/guides/database/connecting-to-postgres . Put the tables in a schema not exposed through the Data API (for example `agent_state`) and enable RLS on them: https://supabase.com/docs/guides/database/postgres/row-level-security . The Free plan pauses projects after 1 week of inactivity, so it is not for production: https://supabase.com/pricing
- DynamoDB: tables `flow_state` and `flow_pending`, partition key `flow_uuid`; `save_pending_feedback` is one `TransactWriteItems` of both items, `save_state` a put (newest wins). The state JSON, message history included, is ONE item, so the item-size limit bounds conversation length (inference; the limit is not verified here: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html is not read): `finish_turn` trims the oldest turns to a configured budget.
- Firestore: documents `flows/{flow_uuid}` and `flows/{flow_uuid}/pending/current`, one batched write for the pause (inference); a document is limited to 1 MiB (https://firebase.google.com/docs/firestore/quotas ), so the same trim applies and a very large tool result is truncated before it enters the transcript.
- Queue ordering key = the session key, so one turn per session holds even when an approver is a different sender. Ingress resolves an approver's reply to the pending session's key before enqueueing. This also satisfies the docs rule never to run two turns concurrently on one Flow (https://docs.crewai.com/v1.15.24/en/guides/flows/conversational-flows.md ); every run builds a fresh Flow object.
- Schema setup runs once as the named one-shot migration job `agent-migrate` (compose service / ECS task / Cloud Run job), never from the worker.
- Record tables, all behind the repository interface:
  - `pending_approvals(approval_id, session_key, pause_id, calls, crewai_version, requested_at, elapsed_s, steps, tool_calls_requested, turn_id, tokens_in, tokens_out, resume_started)`: every pause writes a NEW record with a fresh UUID `approval_id` (never the session key; at most one live record per session key, enforced by a unique index). `pause_id` links the record to the framework's pending row; `calls` holds, per pending call, `(tool_call_id, name, args)`; the counters, `elapsed_s` and token totals are copied from the framework row's `context.metadata`, where `ApprovalProvider.request_feedback` wrote them at the pause (below); `crewai_version` is the pin at the pause; `resume_started` is set, in a committed write, before a tool-running resume (HITL gate).
  - `turns(session_key, turn_id, status, started_at, request_text)`: `status` is `running` from turn start (written after the repair, before the run) and is overwritten with the outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`, `error`; names follow the spec) on every exit; a turn that ended in a pause is `awaiting_approval`, and the same value is the `outcome` on the dedupe record of the message that caused the pause. `request_text` is the user text of the turn, kept for the repair notice.
- Crash marker (T2 decision): USED, as for an own-loop stack, although the framework has a state store. Reason (`flow/persistence/decorators.py` plus the terminal-only rule above): the flow commits state only at the terminal step and at a pause, never per model call or tool call, and the agent's tool transcript lives in executor memory only, so a crash or abort in the middle of a turn leaves no trace that tools may have run; the status row is the only record. The repair rule is under Caps.
- Post-run commit order (the framework commits state DURING the run, like a checkpointer stack): (a) the flow has committed (the terminal step, or the pause with its pending row); (b) ONE repository transaction applies the lifecycle below: deletes the record the run started from and, unless the run ended in a NEW pause, the framework pending row it consumed (by `pause_id`; after a new pause that row already holds the new pause), writes the new record when the run ended in a pause (`requested_at` = now, taken just before sending), sets the turn status, and sets `processed_at`, the `outcome` (`awaiting_approval` when the run ended in a pause) and the reply text on the ingress dedupe record of the dequeued message; (c) send the approval prompt or the reply; (d) ack the queue message. A crash between (a) and (b) leaves the status `running` and `processed_at` unset, so the message is redelivered and the turn runs again: the conversation then holds the exchange twice and safe tools may repeat (inference); destructive calls need a fresh approval.
- Redelivery: the ingress dedupe record (keyed by the channel message id) carries `processed_at`, the `outcome` (`awaiting_approval` for a message whose turn ended in a pause, otherwise the turn's outcome) and the reply text. On dequeue, a message whose record has `processed_at` set is not re-run: re-send the stored reply if the send may not have happened, then ack. Ingress dedupe alone only catches channel retries; this closes queue redelivery after a worker crash. The step-2a expiry commit does NOT set `processed_at`: only the final post-run commit of the turn that handles the message sets it.
- Pending-record lifecycle: any run started from a record deletes it in the post-run transaction unless the run ended in a NEW pause, which writes a fresh record (new `approval_id`) in that same transaction; within the transaction, delete the old record (and its framework row) before inserting the new one (the unique index is per session key). "Ended in a pause" = `handle_turn` or `resume` RETURNED a `HumanFeedbackPending` AND the run completed without an exception or timeout; otherwise the pending calls are discarded, so a wall-clock abort with a gated call pending writes no record. Framework row versus record, decided at step 2 (a resume that pauses again calls `save_pending_feedback` with the same `flow_uuid`, which replaces the single row of a one-row-per-session store while the worker's transaction is still open; observed with such a store):
  - row and record with the same `pause_id`: the normal case.
  - row with no record (a crash between the pause and the transaction, or a timeout after the pause was saved): write a fresh record (new UUID `approval_id`, `requested_at` = now, everything else from the row's metadata) before prompting or resuming.
  - row and record with different `pause_id`: the earlier approval's resume got past its next pause before a crash. Delete the record, write a fresh record for the row, do NOT apply the dequeued decision to the new pause, and reply with the pending-approval prompt of the new pause.
  - record with no row: nothing can be resumed; take the step-2a path through the repository with the marker `EXPIRED:`.
- Spikes (each runs before build-guide Step 4; numbered once here and defined in the section named). A failed store spike (1) STOPS and raises a re-entry on the design's sessions seam, never a silent store swap; the other spikes state their own failure path:

## HITL gate
- Why a gate of this shape (each fact with its source): a `PRE_TOOL_CALL` hook can block a call, but the run CONTINUES and the agent receives "Tool execution blocked by hook. Tool: <name>" (https://docs.crewai.com/v1.15.24/en/learn/tool-hooks.md ; observed), and any exception other than `HookAborted` raised inside a hook is swallowed so the tool RUNS (`crewai/src/crewai/hooks/dispatch.py`, `_invoke_hook`; the page's best practice 4; observed). `@human_feedback` runs after the decorated method has returned and pauses that FLOW STEP; with a provider that raises `HumanFeedbackPending`, `kickoff` and `handle_turn` RETURN the pending object (observed) after the framework saved state and context through the persistence object (https://docs.crewai.com/v1.15.24/en/learn/human-feedback-in-flows.md ). `Flow.from_pending(flow_id, persistence)` builds a NEW Flow object from the saved state and `resume(feedback)` completes the paused step and runs the listeners of the same flow definition: the same flow execution, a new object and possibly a new process (`crewai/src/crewai/flow/runtime/__init__.py`; the saved context stores the original execution uuid "to restore on resume", `crewai/src/crewai/flow/async_feedback/types.py`). The agent loop is not resumed: it ended before the pause, and each `kickoff_async` starts its executor at `iterations = 0` (`crewai/src/crewai/experimental/agent_executor.py`, `invoke_async`), so the framework's step count restarts (Caps). With `emit` set, every non-empty feedback goes through an extra LLM call that picks the outcome (`_finalize_human_feedback`), so this binding uses no `emit` and its own closed vocabulary. The Enterprise webhook path (`humanInputWebhook` and `/resume`, https://docs.crewai.com/v1.15.24/en/learn/human-in-the-loop.md ) is never used. So the gate PROPOSES, PAUSES and then EXECUTES: the hook blocks the gated call, the next model call ends the agent run, the flow pauses with the pending calls, and after approval the flow itself runs the approved call and lets the model continue.
- Recommended placement: ONE gate made of two global hooks installed once at process start by `install_guards(tiers)` (idempotent), plus the flow steps above. The tool hook (`@on(InterceptionPoint.PRE_TOOL_CALL)`) reads `TURN`, counts the call, and blocks (raises `HookAborted`) a call whose tier is not safe after marking `turn.paused`; the model hook (`@on(InterceptionPoint.PRE_MODEL_CALL)`) is described under Caps and, when `turn.paused` is set, stores `list(ctx.messages)` of the agent executor as the transcript and raises `HookAborted` before the model is called (observed: the deny reaches the caller of `kickoff_async`; the upstream test https://raw.githubusercontent.com/crewAIInc/crewAI/1.15.24/lib/crewai/tests/hooks/test_deny_reaches_the_caller.py asserts the same for the public entry points). Both hook bodies are wrapped: any exception other than `HookAborted` is converted into `HookAborted` (fail closed), a tool missing from the tier table is destructive, and when `TURN` holds no turn state both hooks refuse (observed: with no turn state no tool ran and no model call was made). The model hook raises `HookAborted`; it never returns `False`, because a legacy `False` becomes `LLMCallBlockedError`, a `ValueError` that the fail-open handlers around internal model calls absorb (`crewai/src/crewai/llms/base_llm.py`, `_invoke_before_llm_call_hooks`). Model hooks are copied into each executor when it is created (`before_llm_call_hooks`, used by `_setup_before_llm_call_hooks` in `crewai/src/crewai/utilities/agent_utils.py`), so `install_guards` runs before the first `Agent` is built; tool hooks are looked up at call time. Hooks are synchronous and run in the tool thread pool, so counters sit behind a lock; `ToolCallHookContext.request_human_input` is console-only and is never used. Hooks are process-global, so tests that call `clear_all_hooks()` remove the gate: the worker checks that both hooks are registered (`get_hooks(InterceptionPoint.PRE_TOOL_CALL)`) before every turn and refuses the turn otherwise, and a permanent CI test asserts it.
- Tier mapping from the spec's tool contracts: destructive -> the hook blocks and proposes EVERY time, never cached (each approval authorizes exactly the calls stored in that pause, by call id, and nothing else; no "always allow"); reversible -> per design policy (the tier table says gated or auto); safe -> auto. MCP tools follow the same table under their prefixed names (A2A and MCP).
- Flow steps on a pause: `run_agent` catches the `HookAborted`, and when `turn.exit == "pause"` stores `pending_tail` (the transcript messages after the last `user` message: the assistant tool-call message and its tool messages, safe results included) and `pending_calls` (the assistant tool calls whose tool message is the blocked placeholder, as `(id, name, args)` from the model's own message, because the hook context has no call id) in the state, then routes to `request_approval`. `ApprovalProvider.request_feedback(context, flow)` mints `pause_id`, copies the counters and `elapsed_s` and token totals from `TURN` and the pending calls into `context.metadata`, and raises `HumanFeedbackPending`. The saved snapshot therefore carries the tail with tool arguments and results: it stays in server-side storage with the same access rules and encryption at rest as the history, and is never sent to a client.
- Worker sequence:
  1. Dequeue the message for the session (ordering key = session key). If the ingress dedupe record of the message (keyed by the channel message id) has `processed_at` set, do not re-run it: re-send the stored reply if the send may not have happened, then ack (inference; ingress dedupe alone only catches channel retries, this closes queue redelivery after a worker crash).
  2. Read the `pending_approvals` record for the session key and the framework row (`persistence.load_pending_feedback(session_key)`), reconcile them by the table under Pending-record lifecycle, and capture `prior` = the record's `resume_started` (G8).
  2a. If an approval is pending, check its expiry now: when it is older than the spec's TTL, or its `crewai_version` differs from the running pin (a snapshot from before an upgrade; the upgrade rule drains these first), the worker does not apply a decision. It resumes with `"expire"` (the listener appends the `EXPIRED:` notice, see Deny), commits (delete the record and the framework row, turn status `hitl_expired`; the dedupe record's `processed_at` is NOT set here), sends the spec's expiry notice only if the spec defines one (no model reply from this step), then handles the dequeued message as a new turn (inference). If `from_pending` raises (an unreadable context after an edit or an upgrade), the same commit goes through the repository: `append_turn_record` writes the notice into the stored conversation. The record's `requested_at` is the time the worker sent the approval prompt. Expiry is evaluated when the next message for the session is dequeued (intended; a sweep is optional).
  3. If an approval is pending and not expired: parse the message (or the approver's reply) into a decision (builder below) and RESUME. Right before a resume that can run tools (approve, edit, deny-and-continue), commit `resume_started` = true and the turn status `running` on the record in one write (the approved call may run and the worker then crash); a deny-ends-turn or `expire` resume never sets the flag. Otherwise start a NEW turn: run the turn-start repair (see Caps), then write the turn status `running`. Both use ONE canonical call:
     ```python
     remaining = WALL_CLOCK - elapsed_s            # new turn: elapsed_s = 0; resume: the record's elapsed_s
     turn = TurnState(turn_id=turn_id, approval_id=aid, prior=prior, steps=n_steps,
                      tool_calls_requested=n_calls, tokens_in=ti, tokens_out=to,
                      deadline=time.monotonic() + remaining)   # new turn: aid None, zeros; resume: the record's values
     token = TURN.set(turn)                        # hooks, provider and adapter read it; to_thread copies the context
     try:
         async with asyncio.timeout(remaining + GRACE):        # outer wall clock (see Caps)
             if resumed:
                 # resume_started and status `running` were committed on the record just before this block (G8)
                 flow = ChatFlow.from_pending(session_key, persistence=persistence, tracing=False, suppress_flow_events=True)
                 result = await asyncio.to_thread(flow.resume, decision.feedback)  # "approve", "deny: <reason>", "edit: <json>" or "expire"
             else:
                 flow = ChatFlow(persistence=persistence, tracing=False, suppress_flow_events=True)
                 result = await asyncio.to_thread(flow.handle_turn, user_text, session_id=session_key)
     except HookAborted: ...                       # outcome mapping under Caps
     finally:
         turn.fenced = True
         TURN.reset(token)
     paused = isinstance(result, HumanFeedbackPending)
     ```
     `resume()` raises inside a running event loop, so it runs in a thread (docs: use `resume_async` in async code; this binding keeps the synchronous tools and hooks off the worker's loop). `from_pending` passes `tracing=False` and the other keyword arguments to the Flow constructor. `asyncio.timeout` needs Python 3.11 or later and the package supports 3.10, so on 3.10 use `asyncio.wait_for` (standard-library behavior). The reply of a finished run is the last assistant message in `flow.state.messages`.
  4. Post-run, in this order (commit order): the transaction (b), then send (c), then ack (d), all under Sessions and state. On a pause the worker builds the approval prompt from the stored `calls` (tool name and arguments), never from model text.
- Decision value, built by the worker's single decision builder (the eval runner uses the same one). The feedback string is generated from the parsed decision, never the approver's raw text, so the listener matches a closed vocabulary:
  - approve -> `"approve"`: the listener runs every pending call.
  - deny -> `"deny: <reason>"` (reason trimmed and length-capped; model-visible only when the spec lets the model continue): see Deny.
  - edit -> `"edit: <json>"`, accepted only when exactly one call is pending and the arguments validate against that tool's `args_schema` in the builder; the listener runs the call with the edited arguments. If the spec has no edit outcome the builder rejects it.
  - expire -> `"expire"`, issued only by step 2a.
  - One approve or deny reply applies to every pending call of the record (design choice, inference). The listener treats any other string as a deny (fail closed).
- If a message for a pending session does not parse as a decision: keep the approval pending, call neither `resume` nor `handle_turn`, and reply with the spec's pending-approval prompt (or deny if the spec says so). Interpreting free text is the builder's job and never the framework's (no `emit`, so no collapse LLM call).
- Execution after approval (`apply_decision`): for each pending call it sets the ContextVar `IDEMPOTENCY_KEY` to `"<approval_id>:<tool_call_id>"`, runs the tool object directly (`tool.run(**args)`), appends `(name, args)` to `turn.executed`, and writes the result over the blocked placeholder in `pending_tail` (matched by `tool_call_id`). It then stores `continuation = history_messages + pending_tail` and routes to `continue_agent`: `run_agent` calls `kickoff_async(continuation)`, so the model sees its own tool calls with the real results, with the original conversation as history and the original request unchanged (observed; passing the whole captured transcript instead double-wraps the request as "Current Task: Current Task: ..."). The continuation is a new `kickoff`, so it counts against the same per-turn counters restored from the record (Caps), and a further gated call pauses again with a new `pause_id` and, after the transaction, a new `approval_id`.
- Deny.
  - If the spec says a deny ends the turn: no further tool executes and no model request is made. The construct that routes to the end is the `apply_decision` router label `turn_end`: the listener never calls a tool and never calls `kickoff_async`, clears `pending_*`, appends ONE assistant message (below) and `end_turn` persists it. The worker still goes through `resume`, because the conversation lives in the Flow state and the framework row must be consumed by the same path.
  - The appended text is "DENIED: <tool names> not run: <reason>"; when `prior` is set, an earlier resume may have run the tool, so the text is "DENIED: <tool names>: outcome unknown - do not retry without the user" instead of "not run" (and `EXPIRED:` for step 2a). The user-visible deny reply is the spec's text, sent by the worker (outcome `hitl_denied`).
  - If the spec lets the model continue after a deny: the listener writes "DENIED: <reason>" (or the outcome-unknown text when `prior` is set) over each blocked placeholder, no tool body runs, and it routes to `continue_agent`; the resume sets `resume_started` like an approve because the model may then call tools. A denied call still counts as a requested tool call (counted when requested, see Caps). State which of the two applies in `build.md`.
- Idempotency key for a gated/destructive call: unique per APPROVED CALL, `"<approval_id>:<tool_call_id>"`. `approval_id` is the fresh UUID of the record written at that pause; `tool_call_id` is the model's own call id read from the stored tail (the hook context has none; for Gemini-style responses CrewAI synthesizes `call_<python object id>` in `extract_tool_call_info`, `crewai/src/crewai/utilities/agent_utils.py`, and the stored value is the one used, so it is stable). The key is read from `IDEMPOTENCY_KEY` by the destructive tool's backend call; a destructive body that finds it unset refuses to run, so any other path to the body (a gate defect) fails. Stability across redelivery: the record is deleted only in the post-run transaction and the adapter's no-op clear leaves the framework row, so a redelivered resume restores the same snapshot and reuses the same ids (observed: the same resume run twice invoked the body twice with the same key and left one assistant reply and one user message in the stored conversation). A resume that pauses again writes a new record with a new id, so keys are never reused across pauses or turns (observed: `AP1:y1`, then `AP2:y2`, and the second body ran).
- Resume-started marker (G8): at step 2 capture `prior` = the record's `resume_started` and choose the deny/expiry notice text from `prior`. Set (commit) the flag ONLY right before a resume that can run tools. If `prior` is set at step 2a or a deny, the notice for the pending calls is "outcome unknown - do not retry without the user", never "was not run"; the flag is deleted with the record.
- Approval is not an authorization boundary against an untrusted client: only an authenticated approver identity resolved by ingress may produce a decision, and each sensitive tool also checks authorization in its own body. Replay: the record is consumed in the post-run transaction and the ingress dedupe record absorbs a repeated channel message, which is the atomic consume given one worker per session key (inference); a queue redelivery after a crash is a deliberate re-run covered by the idempotency key. If the approval id travels back through an untrusted channel (for example a button payload), ingress signs it (HMAC over `approval_id`, session key and expiry, key from the secret store) and verifies it before enqueueing; the stored record, not the token, authorizes the resume (inference).
- Eval runner: the fixture's approvals enter the worker's turn handler as decision messages (see Eval runner mapping); the runner never calls `handle_turn` or `resume` itself.
- Gate and pause spike (spike 4; binding spike; failure path: fix this binding). Pass tests: (a) a response with one safe and one destructive call runs the safe body once and the destructive body zero times, `handle_turn` RETURNS `HumanFeedbackPending`, the framework row holds the pending call `(id, name, args)` and a `pause_id`, the model double is called once, and the stored conversation holds the user message and no `tool_calls` or `tool` entry; (b) fault injection: a hook body made to raise a plain exception blocks the call instead of running it (the library alone would run it), an unknown tool name pauses, and with no turn state bound no tool runs and no model call is made; (c) a safe tool never pauses; (d) the model hook stores the tail and the pending calls equal the blocked placeholders; (e) two sessions run at once keep separate counters and pending rows.
- Resume spike (spike 5; binding spike; failure path: fix this binding; if `from_pending` restores a state other than the pause snapshot, STOP and raise a re-entry on the design's sessions seam). Pass tests: (a) approve in a NEW process runs the destructive body once with the key `"<approval_id>:<tool_call_id>"`, the safe sibling is not run again, the model double is called exactly twice in total, the second request carries the assistant tool-call message and one tool message per call with the real results and offers the same tool names, and each `tool_call_id` has exactly one result; (b) resume -> second pause -> second approval yields a new `approval_id` and `pause_id`, keys distinct from the first, and the second body runs; (c) redelivery: run the same resume twice from the same stored rows (simulating a crash after the body ran and before transaction (b)): the body is invoked twice with the same key, and the stored conversation holds the user message once and one assistant reply; (d) crash window: after a resume paused again, redeliver the first approver's message: the dequeued decision is NOT applied to the new pause (the `pause_id` mismatch case) and a fresh record is written; (e) when the spec lets the model continue after a deny, deny-and-continue runs the body zero times and the next model request contains the denial text; (f) edit runs the body once with the edited arguments and an invalid edit is refused by the builder; (g) a follow-up turn on the same session succeeds against the real provider; (h) with the stored context edited to be unreadable, `from_pending` raises and the worker takes the step-2a repository path instead of failing out of the handler.
- Deny and expiry spike (spike 6; binding spike; failure path: fix this binding). ## Caps
- Step cap: CUSTOM, because the native `max_iter` is not the spec's unit, scope or exit. Facts: the runtime default is 25 although the docs say 20 (observed `Agent.max_iter`; https://docs.crewai.com/v1.15.24/en/concepts/agents.md ); the count goes up once per round of tool execution and not per model call (`increment_and_continue` in `crewai/src/crewai/experimental/agent_executor.py`); when it is reached, `force_final_answer` makes one more model call that asks for a best answer, and that answer comes back as a NORMAL result with no exception or flag (observed: with `max_iter=N` and a model that always asks for a tool, N tool rounds and N+1 model calls happen); and every `kickoff` starts the executor at zero. So the binding counts model calls itself: the model hook adds 1 per model request and raises `HookAborted` when the count exceeds `<spec step cap>`, i.e. a cap of N allows N model calls and the final answer is also a call. Unit conversion: the spec's step is one model request, used 1:1 (inference); record this definition in `build.md`. `max_iter` is set to the same number only as a backstop: its forced best-answer call goes through the model hook (observed), so the hook trips first and no best-effort answer ever reaches the user. Calls the library makes on its own (context-window summarization, `respect_context_window` defaults to True) also pass the hook and count; the router and feedback-classification calls are avoided by design (fixed route, no `emit`). Native provider classes call `_invoke_before_llm_call_hooks` once per request, and it does nothing when the executor already dispatched the hooks for that call (`crewai/src/crewai/llms/base_llm.py`; the provider classes and `crewai/src/crewai/llm.py` call it; observed with the scripted double, which calls the same method: one hook call per model call), and spike 7(f) confirms it against the real provider.
- Tool-call cap: own counter, because no native per-run cap was found (https://docs.crewai.com/v1.15.24/en/concepts/tools.md ). Implementation, two places that count one call at most once between them: (1) the tool hook adds 1 per call BEFORE that call's body and, past `<spec tool-call cap>`, marks `turn.exit = "tool_call_cap"` and blocks it and every later call (the hook runs once per call, in the thread that will run the body: observed); (2) the model hook rescans `ctx.messages` for assistant tool-call messages not yet seen (only for a context that carries the agent executor, `ctx.executor`; a direct model call such as a summarization has `executor` None and its own message list) and sets the total to the larger of the two counts, because a malformed call (unparseable arguments) never reaches the tool hook (observed: 4 requested calls, 3 hook calls, one parse-error result) and the same scan is the trajectory source (Eval runner mapping). The scan runs before the next model call, so a trip found there raises `HookAborted` before the model is asked. Parallel calls: CrewAI runs a multi-call response in a thread pool (up to 8 workers) when no tool has `result_as_answer` or `max_usage_count` (`_should_parallelize_native_tool_calls`), so no hook sees the whole batch first. Consequence, different from bindings where a hook sees the batch: calls whose hook count is within the cap run and the rest are blocked, so executed calls never exceed the cap but "none of the batch runs" is not guaranteed, and which calls of an over-cap batch run depends on thread timing (observed: 3 parallel calls under cap 2 ran 2 and blocked 1). Every request counts, denied, gated and unknown-tool calls included.
- Both caps are PER TURN: a new turn starts `TurnState` at zero; a resume restores `steps`, `tool_calls_requested`, `elapsed_s` and the token totals from the record (the framework restarts its own counter on every `kickoff`, so nothing is carried by CrewAI). The counters travel from the pause to the record through `context.metadata`, so even an orphan record (crash after the pause) restores them.
- Both exits map to the spec's single failure reply and a cap outcome: a `HookAborted` whose `turn.exit` is `step_cap` -> `step_cap`, `tool_call_cap` -> `tool_call_cap`, `wall_clock` -> `wall_clock`; any other exception -> `error` (also the failure reply). The exception text is never sent to the user. The exception reaches the worker unwrapped (observed: `handle_turn` raised `HookAborted`); the framework also logs it at error level ("Error executing listener ...", also for a plain pause), so alerts must not key on that line.
- `harness_condition.force_step_cap`: a `ScriptedLLM` with exactly `<step cap>` steps, each a single safe tool call and no final answer, and the tool-call cap set above the step cap; the test asserts `HookAborted` with exit `step_cap` was raised and `len(double.calls) == <step cap>`, i.e. the hook tripped before the double was asked again. A tool-cap case does the reverse. `tool_always_errors` = the tool's injected BACKEND double raises and the real tool catches it and returns the spec's error observation (build-guide Step 5); the tool surface never changes. A tool that lets the exception escape is shown to the model as `Error executing tool: <exception text>` (`crewai/src/crewai/experimental/agent_executor.py`), which leaks internals and invites a retry, so the tools factory wraps every body.
- Wall-clock cap: the budget is per TURN, resume time included. The record stores `elapsed_s` at each pause and a resume gets the remainder (limit minus `elapsed_s`; the wait for the approver is not counted; inference); a new turn gets the full limit. Enforcement is cooperative: both hooks check `turn.deadline` on every model request and every tool call and raise or block with `turn.exit = "wall_clock"` (observed: with the deadline already past no model call was made), and the worker wraps the thread in `asyncio.timeout(remaining + GRACE)`. A thread cannot be cancelled, so on the outer timeout the worker sets `turn.fenced`: the adapter then refuses every write (an abandoned run cannot store a finished exchange after the failure reply went out), and the thread stops at its next hook call. A single call in flight is bounded only by its own timeout: set `timeout=` on the `LLM` (https://docs.crewai.com/v1.15.24/en/concepts/llms.md ) and a timeout in every tool body. Whether a running tool body stops when its thread's turn is abandoned is unverified; spike 8 measures it. Expiry gives the single failure reply and the outcome `wall_clock`; an in-flight destructive body is covered by the idempotency key.
- Persisting a turn: nothing to diff. The flow writes the conversation itself at the terminal step and at a pause (Sessions and state); the worker writes the record, the status and the dedupe record. The conversation holds text only: `finish_turn` and `apply_decision` append plain assistant text, and the agent's tool transcript exists only in executor memory and, during a pause, in `pending_tail`. So the failure "an AI message with tool calls lacking tool results" cannot arise in `state.messages`, and spike 8 asserts it after every exit.
- Repair of aborted turns, at TURN START and only when no approval is pending (idempotent, survives a crash): read the latest `turns` row. Status `ok`, `hitl_denied`, `hitl_expired` or `awaiting_approval` -> nothing (the flow stored the finished exchange or the pending record owns the turn). Status `running`, `step_cap`, `tool_call_cap`, `wall_clock` or `error`, or no row while a stored conversation exists -> nothing was stored for that turn although tools may have run: `append_turn_record(session_key, turn_id, ...)` appends one user-role message `[agent-notice turn <turn_id>] The user's previous message ("<request_text>") was not answered: the turn was interrupted and its tools may have run. Outcome unknown - do not retry without the user.` to the stored conversation, unless the tail already holds that notice for that turn id. The user role is used because every provider route accepts it (inference; spike 9 sends it to the real provider). Only then write the new status `running`. Every repaired turn says "outcome unknown", never "not executed". `append_turn_record` edits the newest `flow_states` JSON through the repository, so its message shape (`role`, `content`, `name`, `tool_call_id`, `tool_calls`, `files`, `metadata`) is pinned to 1.15.24 and spike 8 checks that the next turn's first model request contains the notice.
- Abort and repair spike (spike 8; binding spike; failure path: fix this binding). Pass tests: (a) a wall-clock abort during a slow tool: the worker sends the failure reply with the outcome `wall_clock`, a write attempted by the abandoned thread afterwards raises, nothing is stored, the next new turn writes the notice once and succeeds against the real provider, and the model's reply shows it was told the outcome is unknown; record whether the tool body kept running; (b) a tool that raises its backend error returns the spec's error observation and the turn ends normally, while an exception made to escape the body maps to the failure reply and `error`; (c) kill the worker process during a tool, then run the repair twice: exactly one notice exists; (d) kill the worker between the pause and the transaction: step 2 finds the row with no record and writes a fresh one, and the approval can be answered; (e) after each cap exit and after each abort above, the stored `messages` hold no `tool_calls` or `tool` entry and a follow-up turn succeeds against the real provider.
- Cap spike (spike 7; binding spike; runs before build-guide Step 4; failure path: fix this binding). Pass tests: (a) tool cap 2: the model requests 1 destructive call, the turn pauses, the worker approves, the model then requests 2 more calls: the third cumulative call is blocked and `HookAborted` with exit `tool_call_cap` reaches the worker, no body past the cap ran, and the stored conversation holds no `tool_calls` entry; (b) step cap N: exactly N model requests happen, then `HookAborted` with exit `step_cap`, across an approval pause the total is still N (`len(double.calls)`), and with `max_iter` equal to N no best-answer text is ever returned; (c) 3 parallel safe calls under cap 2: at most 2 bodies run, the third is blocked, the turn ends with `tool_call_cap` (documents the difference from a hook that sees the batch); (d) both counters are 0 at the start of the next new turn on the same session; (e) both exceptions reach the worker as `HookAborted` with `turn.exit` set; (f) with the real provider, the number of model-hook calls equals the number of provider requests; (g) a malformed call is counted by the rescan; (h) pause during the turn that reaches the cap, approve: the approved tool runs and its result is stored in the tail, then the next model request trips the cap and a follow-up turn succeeds.

## Eval runner mapping
- Runner = worker: the eval runner drives the worker's single turn handler (dequeue logic, pending check, expiry, repair, resume-or-end, cap mapping, commit order) against an in-memory implementation of the repository interface and an in-memory `FlowPersistence` subclass (the same six methods; it passes spike 1's contract test), never `handle_turn` or `kickoff` directly, so the deny, expiry and cap branches cannot diverge from production. The fixture's messages and approvals enter as queue messages; the expiry clock is injected. The in-memory persistence stores the real context and state JSON, and `build_chat_flow` is called once per test with that persistence, so the cross-instance resume path is exercised.
- Model double: a custom `BaseLLM` subclass (the documented way: https://docs.crewai.com/v1.15.24/en/learn/custom-llm.md ), `ScriptedLLM(steps)`, passed as `model` through the factory. A step is a string (the final answer) or a list of tool-call dicts `{"id", "type": "function", "function": {"name", "arguments": <json string>}}` with a unique `id` per call; `supports_function_calling()` returns True; `call()` accepts the extra keywords `from_task`, `from_agent`, `response_model` and `**kwargs` that the executor passes, and calls `self._invoke_before_llm_call_hooks(messages, from_agent)` first, as the provider classes do, so the cap and gate hooks behave as in production (the upstream stub in the test file cited under HITL gate does the same). It records every request (`calls`: messages, tool names) and has `assert_complete()` for deterministic cases. The same instance is returned by the factory on every build so the script continues across the resume. It replaces only the model, never the tools, the hooks or the persistence.
- Capture source: `TurnState`, filled by the two hooks and `apply_decision`, read by the runner after each turn.
  - Trajectory = the REQUESTED calls: `(name, arguments)` of every assistant tool call in `ctx.messages` as the model hook sees them, in the model's own order, including malformed calls, calls the cap blocked and calls the gate paused (observed: 4 requested, 3 seen by the tool hook). The tool hook's order is not used for trajectories because parallel calls run in separate threads.
  - `forbidden` is checked against the EXECUTED calls, `TurnState.executed` (the tool hook appends `(tool_name, tool_input)` only for a call it let through, and `apply_decision` appends each approved call it ran; paused, blocked and denied calls are not in it), plus the reply text (`skills/build/references/adapter-bindings.md`). A call the hook let through can still fail before its body (an unknown tool), which errs on the side of `forbidden` (inference). One rule, no per-case guessing.
- The PIPELINE runner implements EXACT, IN_ORDER and ANY_ORDER itself over the trajectory list, with `args_subset` matching (golden-format: expected args must be a subset of actual args; never full-argument equality). `crewai test` is never used: it prints task scores from 1 to 10, the page says the only provider available is OpenAI, and the page describes no trajectories, LLM mocking or golden cases (https://docs.crewai.com/v1.15.24/en/concepts/testing.md ). The `crewai eval` command named in the 1.15.24 release notes (https://github.com/crewAIInc/crewAI/releases/tag/1.15.24 ) was not evaluated and is not used (unverified).
- pass^k is computed by the pipeline runner from its own per-case results.
- Approvals in a case: the fixture's approvals enter the worker handler as decision messages and are answered by the worker's decision builder (see HITL gate). `harness_condition.force_step_cap` and `tool_always_errors` are specified under Caps.
- Tool-surface preflight: the eval runner and a permanent CI unit test assert that the FIRST model request's tool names equal the spec's tool set (plus any built-in kept on purpose, each with its reason in `build.md`; this binding keeps none). Capture source: `ScriptedLLM.calls[0]` records the `tools` argument of the first `call()` (a list of `{"type": "function", "function": {"name": ...}}`), and the preflight reads each `function.name`; the double replaces only the model, so it does not change the surface (observed: exactly the two agent tools were offered, with delegation off). MCP tool names are part of the set under their prefixed form. Negative control (the surface is filtered by `create_static_tool_filter`): a fake Streamable HTTP MCP server exposes one extra tool outside the spec; with the filter the preflight passes, and a second run of the same test with the filter removed MUST fail on the extra prefixed name, proving the preflight can see a filtered tool (observed: with the filter only `127_0_0_1_8765_mcp_echo` was offered, without it `127_0_0_1_8765_mcp_wipe` appeared too). Because the docs say an unreachable MCP server is skipped without an error, a missing spec tool also fails the preflight.
- Eval double spike (spike 11; binding spike; failure path: fix this binding): the scripted double drives a full pause, resume and finish through the worker handler on the in-memory persistence and on the real adapter with the same trajectory, and the preflight and its negative control pass.

## A2A and MCP
- A2A: native client and server configuration exists (`A2AClientConfig`, `A2AServerConfig`, protocol version 0.3.0 by default; https://docs.crewai.com/v1.15.24/en/learn/a2a-agent-delegation.md ) and needs `crewai[a2a]`, which pins `a2a-sdk~=0.3.10`. Record the protocol version in interop.md. Under HITL the native SERVER path is not used: each incoming task is run by `agent.aexecute_task(task=...)` (`crewai/src/crewai/a2a/utils/task.py`), outside the ingress queue, the session key, `handle_turn`, the caps and the approval pause; with the gate installed it can only refuse (observed: with no turn state every tool and model call was refused), and no HTTP host for it was found in the package source (a search for a2a-sdk server application classes returned nothing; the page points to AMP for production), so serving it is unverified. Own server built with `a2a-sdk` (Apache-2.0; 1.2.2 was the latest on PyPI on 2026-10-08, https://pypi.org/project/a2a-sdk/ ) that enqueues into the same ingress queue (key = session key) and answers from the repository, so the gate, the caps and the repair apply (own code, inference); do not install the `a2a` extra in the same environment as `a2a-sdk` 1.x (the extra pins 0.3.x; resolver conflict, inference). A2A client: a tool wrapping the `a2a-sdk` client, with the tier the design gives it (inference). The native `A2AClientConfig` wraps the agent's `kickoff` and task execution (`crewai/src/crewai/a2a/wrapper.py`); whether its remote calls pass the tool hook is unverified, so it is used only after spike 12 shows the gate sees them. `A2AConfig` is deprecated for removal in v2.0.0: use the client and server classes.
  - A2A spike (spike 12, when the design names A2A; binding spike; failure path: fix this binding): a task through the own server appears in the ingress queue with the session key as ordering key, and a gated tool reached through it pauses; for the native client, a delegation either appears as a tool call at the gate or the native client is not used.
- MCP client: structured configurations only, `Agent(mcps=[MCPServerHTTP(url=..., headers=..., tool_filter=create_static_tool_filter(allowed_tool_names=[...]), cache_tools_list=True)])` (Streamable HTTP is the default transport of `MCPServerHTTP`; SSE and stdio exist). Source: https://docs.crewai.com/v1.15.24/en/mcp/overview.md . ALWAYS pass the allow-list filter with only the tools the spec names. Never use string references: a slug such as `"snowflake"` resolves against the CrewAI platform's connected-MCP catalog, and `https://host/mcp?api_key=...` puts a key in the URL. The tool names the model and the hook see are the sanitized server name plus the tool name: observed `127_0_0_1_8765_mcp_echo` for `http://127.0.0.1:8765/mcp`, and for a stdio server a truncated name ending in a hash because the name is built from the command line (`sanitize_tool_name` shortens past 64 characters), so use Streamable HTTP and key the tier table by the prefixed names recorded by the preflight; a name missing from the table is destructive (fail closed). Only MCP tools are supported, not prompts or resources (research file, citing the same page; unverified here). The approved call is run through the tool object the agent holds; for MCP tools that is unverified and spike 13 covers it.
  - MCP spike (spike 13; binding spike; failure path: fix this binding): the server's filtered tool names appear in the first model request under their prefixed names, a destructive MCP tool pauses, the pause serializes, and the resume in a new process with the same server configuration runs it once with the key; a stale tier table (renamed URL) pauses instead of running.
- MCP serving: not documented (unverified); not part of this binding unless the design asks for it, and then routed through the ingress queue so the gate and the caps still hold (inference).
