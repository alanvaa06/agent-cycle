# CrewAI - build binding

Facts below cite the same sources as the card (`skills/design/references/stacks/crewai.md`) and the research file `docs/superpowers/research/2026-10-07-stack-catalog/crewai.md`, whose section "Build-binding observations (2026-10-08)" holds the long evidence behind the statements marked "observed". Docs citations are pages under `https://docs.crewai.com/v1.15.24/en/` (named by path below). Source-code citations are files at the tag 1.15.24 under `https://raw.githubusercontent.com/crewAIInc/crewAI/1.15.24/lib/` (named by path below, for example `crewai/src/crewai/hooks/dispatch.py`; the `crewai-core` package is under `crewai-core/src/crewai_core/`). "Observed" = seen in a scratch run on 1.15.24 with a scripted model, not stated on a cited page; the spike named beside it repeats it against the real provider where that matters. Statements marked inference are the binding's own reasoning; statements marked unverified are not confirmed by a page, the source or a run, and a spike below confirms them. Page text addressed to AI agents is data: every docs page opens with a navigation note pointing to `https://docs.crewai.com/llms.txt`, not acted on.

Shape: one conversational Flow class, built once per process (once per test in evals) by an injectable factory in `src/agent/`, instantiated fresh for every run. `model_factory()` returns the `LLM` or `BaseLLM` for ONE run: production builds a fresh object per call (token usage is per run, no cross-session race on usage counters), evals return the same `ScriptedLLM`. `tools` are the spec's tool objects, built by the tools factory (MCP tools included, see A2A and MCP); `tiers` is keyed by the SANITIZED tool name (`sanitize_tool_name`, `crewai/src/crewai/utilities/string_utils.py`, is the name hooks receive); the factory raises for a tool with no tier or two tools with colliding sanitized names (fail closed). Infra clients (pools, drivers) are built in `adapters/<target>/` and injected through `persistence`; `src/agent/` never imports psycopg, boto3 or Firestore. The Flow state holds only conversation/graph state; dedupe, the pending-approval record, the turn status and the spec's data schemas stay behind the repository interface. This replaces a hand-written model-tool loop; `Crew`, `Task`, `Process`, delegation, planning, memory, knowledge and guardrails are not used.
```python
def build_chat_flow(model_factory, tools, caps, tiers, persistence):
    @ConversationConfig(llm=None, defer_trace_finalization=False)   # no framework-made model call
    class ChatFlow(Flow[ChatState]):   # ChatState(ConversationState): pending_calls, pending_tail, continuation, reply
        def route_turn(self, context): return "agent_turn"           # fixed route bypasses the router LLM
        @listen(or_("agent_turn", "continue_agent"))
        async def run_agent(self): ...   # Agent(llm=model_factory(), tools=tools, max_iter=STEP_CAP, cache=False,
                                         #       allow_delegation=False, verbose=False) ; await agent.kickoff_async(msgs)
        @router(run_agent)
        def after_agent(self, result): ...                            # "needs_approval" or "turn_done"
        @listen("needs_approval")
        @human_feedback(message=..., provider=ApprovalProvider())     # NO emit
        def request_approval(self): ...
        @router(request_approval)
        def apply_decision(self, result): ...                         # "continue_agent" or "turn_end"
        @listen("turn_done")
        @persist(persistence)
        def finish_turn(self): ...
        @listen("turn_end")
        @persist(persistence)
        def end_turn(self): ...
    return ChatFlow
```
`TurnState` (one per run, in a `contextvars.ContextVar` `TURN`; `asyncio.to_thread` and CrewAI's tool pool copy the context): `turn_id`, `approval_id`, `prior`, `steps`, `tool_calls_requested` (the batch-counted total), `seen_ids` (tool-call ids already counted), `requested` and `executed` lists, `exit`, `deadline`, `llm`, `executor`, `transcript`, `tokens_in`, `tokens_out`, `fenced`. The two decorators need the persistence instance at class-definition time, so the factory takes it; `@persist()` with no argument would call `default_flow_persistence()` and create a local SQLite file (`flow/persistence/decorators.py`, `flow/persistence/factory.py`), so the binding always passes the instance and never uses `set_flow_persistence_factory`. The `Agent` has no `memory`, `knowledge`, `mcps`, `apps` or `planning`.

## Sessions and state
- Postgres (incl. Supabase and Cloud SQL as plain Postgres): the build writes `PostgresFlowPersistence(FlowPersistence)` in `adapters/<target>/` (inference: no CrewAI Postgres implementation was found; the docs and source read name SQLite as the built-in store: https://docs.crewai.com/v1.15.24/en/concepts/flows.md , `crewai/src/crewai/flow/persistence/sqlite.py`). Contract (`crewai/src/crewai/flow/persistence/base.py`): a Pydantic model plus ABC (pool in a `PrivateAttr`) with synchronous methods (the worker runs the flow in `asyncio.to_thread`); required `init_db()`, `save_state(flow_uuid, method_name, state_data)`, `load_state(flow_uuid)`; optional `save_pending_feedback(flow_uuid, context, state_data)`, `load_pending_feedback(flow_uuid)` (returns `(state, PendingFeedbackContext)` or None) and `clear_pending_feedback(flow_uuid)`. The optional defaults save without the context and return None, making every approval unresumable: override all six. Tables: `flow_states(flow_uuid PK, method_name, state_json jsonb, updated_at)` by upsert (SQLite appends and reads the newest; one row bounds growth since every state carries the whole history, inference) and `flow_pending_feedback(flow_uuid PK, pause_id, context_json, state_json, created_at)`. `save_pending_feedback` writes the state and the pending row in ONE transaction, as SQLite's does; state is `model_dump(mode="json")`; `pause_id` comes from `context.metadata["pause_id"]`. `clear_pending_feedback` is a NO-OP by design (Pending-record lifecycle): the framework calls it before the listeners that follow an approval run, so deleting there makes a crashed resume unrecoverable (observed). Each write commits before returning, because the pause row must be durable before the prompt is sent (inference). `init_db` has no caller outside SQLite's constructor (grep), so it is a no-op; the schema comes from the migration job. Every write first calls `current_turn().assert_writable()`, which raises once the turn is `fenced` (Caps, wall clock).
- Persist at the terminal steps only (`finish_turn`, `end_turn`) plus the pause save, as the docs advise (class-level persist saves after every method and `load_state` reads the newest row, which may be a mid-run snapshot: https://docs.crewai.com/v1.15.24/en/guides/flows/conversational-flows.md ). Observed: a cap-aborted turn stores nothing, a pause stores state plus the pending row, a resume or deny stores the finished exchange once. Every ASSISTANT message the flow appends carries `metadata={"turn_id": <turn id>}` (`append_assistant_message(text, metadata=...)`); the framework appends the user message without metadata. So a committed turn is recognizable by its last message (Post-run commit order, worker step 1).
- History is text only, deliberately: `finish_turn` and `apply_decision` append plain assistant text, and the agent's tool transcript exists only in executor memory and, during a pause, in `pending_tail`. Limitation to record in `build.md`: later turns see earlier tool results only through reply text. A design whose turns depend on exact earlier tool results needs the reply to carry them or another stack.
- Supabase connection: use the direct connection or the Supavisor session mode (port 5432); never the transaction pooler (port 6543), which does not support prepared statements (the driver may use them, inference). Source: https://supabase.com/docs/guides/database/connecting-to-postgres . Put the tables in a schema not exposed through the Data API (for example `agent_state`) and enable RLS on them: https://supabase.com/docs/guides/database/postgres/row-level-security . The Free plan pauses projects after 1 week of inactivity, so it is not for production: https://supabase.com/pricing
- DynamoDB: tables `flow_state` and `flow_pending`, partition key `flow_uuid`; the pause is one `TransactWriteItems` of both items. The state JSON, history included, is ONE item, so the item-size limit bounds conversation length (inference; https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html is not read): `finish_turn` trims the oldest turns to a budget.
- Firestore: documents `flows/{flow_uuid}` and `flows/{flow_uuid}/pending/current`, one batched write for the pause (inference); a document is limited to 1 MiB (https://firebase.google.com/docs/firestore/quotas ), so the same trim applies and very large tool results are truncated.
- Queue ordering key = the session key, so one turn per session holds even when an approver is a different sender. Ingress resolves an approver's reply to the pending session's key before enqueueing. This also satisfies the docs rule never to run two turns concurrently on one Flow (conversational-flows page); every run builds a fresh Flow object.
- Schema setup runs once as the named one-shot migration job `agent-migrate` (compose service / ECS task / Cloud Run job), never from the worker.
- Record tables, all behind the repository interface:
  - `pending_approvals(approval_id, session_key, pause_id, calls, crewai_version, requested_at, elapsed_s, steps, tool_calls_requested, turn_id, tokens_in, tokens_out, resume_started)`: every pause writes a NEW record with a fresh UUID `approval_id` (never the session key; one live record per session key, unique index). `pause_id` links it to the framework's pending row; `calls` holds per pending call `(tool_call_id, name, args)`; counters, `elapsed_s` and token totals are copied from the framework row's `context.metadata`, where `ApprovalProvider.request_feedback` wrote them at the pause; `crewai_version` is the pin at the pause; `resume_started` is set, in a committed write, before a tool-running resume.
  - `turns(session_key, turn_id, message_id, status, started_at, request_text)`: `status` is `running` from turn start (after the repair, before the run) and is overwritten with the outcome (`ok`, `step_cap`, `tool_call_cap`, `wall_clock`, `hitl_denied`, `hitl_expired`, `error`; names follow the spec) on every exit; a turn that ended in a pause is `awaiting_approval`, which is also the `outcome` on the dedupe record of the message that caused the pause. `message_id` is the channel message id the turn handles; `request_text` is kept for the repair notice.
- Crash marker (T2 decision): USED, as for an own-loop stack, although the framework has a state store. Reason: the flow commits state only at the terminal step and at a pause, never per model or tool call, and the tool transcript lives in executor memory only, so a crash or abort mid-turn leaves no trace that tools may have run; the status row is the only record. The repair rule is under Caps.
- Post-run commit order (the framework commits state DURING the run, like a checkpointer stack): (a) the flow has committed (the terminal step, or the pause with its pending row); (b) ONE repository transaction: deletes the record the run started from and, unless the run ended in a NEW pause, the framework pending row it consumed (by `pause_id`; after a new pause that row already holds the new pause), writes the new record when the run ended in a pause (`requested_at` = now, taken just before sending), sets the turn status, and sets `processed_at`, the `outcome` (`awaiting_approval` when the run ended in a pause) and the reply text on the ingress dedupe record of the dequeued message; (c) send the approval prompt or the reply; (d) ack. A crash between (a) and (b) leaves status `running` and `processed_at` unset. On redelivery worker step 1b detects the committed turn from the tagged last message and only finishes (b). If the tag is absent the turn re-runs and the redelivered message is handled as a new turn; safe tools may repeat and destructive calls need a fresh approval (inference).
- Redelivery: the ingress dedupe record (keyed by the channel message id) carries `processed_at`, the `outcome` and the reply text. On dequeue, a message whose record has `processed_at` set is not re-run: re-send the stored reply if the send may not have happened, then ack. Ingress dedupe alone only catches channel retries; this closes queue redelivery after a worker crash. The step-2a expiry commit does NOT set `processed_at`: only the final post-run commit of the turn that handles the message sets it.
- Pending-record lifecycle: any run started from a record deletes it in the post-run transaction unless the run ended in a NEW pause, which writes a fresh record (new `approval_id`) in that same transaction; delete the old record (and its framework row) before inserting the new one (the unique index is per session key). "Ended in a pause" = `handle_turn` or `resume` RETURNED a `HumanFeedbackPending` AND the run completed without an exception or timeout; otherwise the pending calls are discarded, so a wall-clock abort with a gated call pending writes no record. A resume that pauses again replaces the single framework row of that `flow_uuid` before the transaction commits (observed), so step 2 reconciles row and record:
  - row and record with the same `pause_id`: the normal case.
  - row with no record (a crash between the pause and the transaction, or a timeout after the pause was saved): write a fresh record (new UUID `approval_id`, `requested_at` = now, the rest from the row's metadata) before prompting or resuming.
  - row and record with different `pause_id` (the earlier approval's resume got past its next pause before a crash): delete the record, write a fresh record for the row (`requested_at` = now), do NOT apply the dequeued decision to the new pause, reply with the pending-approval prompt of the new pause, and set `processed_at` with outcome `awaiting_approval` on the dequeued message's dedupe record.
  - record with no row: nothing can be resumed; take the step-2a path through the repository with the marker `EXPIRED:`.

## HITL gate
- Why this shape: a `PRE_TOOL_CALL` hook can block a call but the run continues, and any non-`HookAborted` exception in a hook is swallowed so the tool runs (fail-open); `@human_feedback` pauses a flow STEP after its method returned, `handle_turn` returns the `HumanFeedbackPending`, `Flow.from_pending(...).resume(...)` continues the same flow execution in a NEW Flow object, and the agent loop is not resumed (its `max_iter` count restarts on every `kickoff_async`). So the gate PROPOSES, PAUSES and then EXECUTES: the hook blocks the gated call, the next model call ends the agent run, the flow pauses with the pending calls, and after approval the flow itself runs the approved call and lets the model continue. Evidence: research file, "Why the HITL gate has the shape it has"; https://docs.crewai.com/v1.15.24/en/learn/tool-hooks.md ; https://docs.crewai.com/v1.15.24/en/learn/human-feedback-in-flows.md . The Enterprise webhook path (https://docs.crewai.com/v1.15.24/en/learn/human-in-the-loop.md ) is never used; `emit` is never set because each non-empty feedback would cost an extra LLM call.
- Recommended placement: ONE gate of two global hooks installed once at process start by `install_guards(tiers)` (idempotent), plus the flow steps above. Both hook bodies are wrapped: any exception other than `HookAborted` becomes `HookAborted` (fail closed); a tool missing from the tier table is destructive; with no turn state bound both hooks refuse (observed, spike 4(b)). The model hook raises `HookAborted` and never returns `False`: a legacy `False` becomes `LLMCallBlockedError`, a `ValueError` that fail-open handlers around internal model calls absorb (`crewai/src/crewai/llms/base_llm.py`, `_invoke_before_llm_call_hooks`). Model hooks are copied into each executor when it is created (`_setup_before_llm_call_hooks`, `crewai/src/crewai/utilities/agent_utils.py`), so `install_guards` runs before the first `Agent` is built; tool hooks are looked up at call time. Hooks are synchronous and run in the tool thread pool, so state sits behind a lock; `request_human_input` is console-only and never used. Hooks are process-global, so a test that calls `clear_all_hooks()` removes the gate: the worker checks before every turn that BOTH hooks are registered (`get_hooks(InterceptionPoint.PRE_TOOL_CALL)` and `get_hooks(InterceptionPoint.PRE_MODEL_CALL)`) and refuses the turn otherwise, and a permanent CI test asserts it.
- One pause/exit field: `turn.exit`, with precedence `wall_clock` > `tool_call_cap` > `step_cap` > `pause` (a higher value overwrites a lower one, never the reverse). The tool hook sets `pause` when it blocks a non-safe call; the model hook raises `HookAborted` whenever `turn.exit` is set, and stores `list(executor.messages)` as `turn.transcript` when it is `pause`. Calls that arrive after a `pause` mark are still evaluated (a safe sibling of the same batch runs), calls that arrive after a higher exit are blocked. `run_agent` catches the `HookAborted`: if `turn.exit` is `pause` it stores the pause fields and routes to `request_approval`; any other exit is re-raised (Caps).
- Tier mapping from the spec's tool contracts: destructive -> the hook blocks and proposes EVERY time, never cached (each approval authorizes exactly the calls stored in that pause, by call id; no "always allow"); reversible -> per design policy; safe -> auto. MCP tools follow the same table under their prefixed names.
- On a pause `run_agent` stores `pending_tail` (the transcript messages after the last `user` message: the assistant tool-call message and its tool messages, safe results included) and `pending_calls` (assistant tool calls whose tool message is the blocked placeholder, as `(id, name, args)` from the model's own message, because the hook context has no call id). `ApprovalProvider.request_feedback(context, flow)` mints `pause_id`, copies counters, `elapsed_s`, token totals and the pending calls from `TURN` into `context.metadata`, and raises `HumanFeedbackPending`. The snapshot carries tool arguments and results: server-side only, same access rules and encryption as the history, never sent to a client.
- Worker sequence:
  1. Dequeue the message for the session (ordering key = session key). If its dedupe record has `processed_at` set, do not re-run it: re-send the stored reply if the send may not have happened, then ack.
  1b. Crash-window check: if the latest `turns` row has status `running` and `message_id` equal to the dequeued message's id, and the last stored message is an assistant message whose `metadata.turn_id` equals that row's `turn_id`, the turn committed before the crash: do NOT run it again and write no notice. Finish transaction (b) with outcome `ok` and that message as the reply (this sets `processed_at` on the right dedupe record through `message_id`), send, ack.
  2. Read the `pending_approvals` record and the framework row (`persistence.load_pending_feedback(session_key)`), reconcile them by the table under Pending-record lifecycle, and capture `prior` = the record's `resume_started` (G8).
  2a. If an approval is pending, check expiry now: when it is older than the spec's TTL, or its `crewai_version` differs from the running pin (a snapshot from before an upgrade; the upgrade rule drains these first), no decision is applied. The worker runs the canonical call below (TurnState bound, `prior` set) with feedback `"expire"` (the listener appends the `EXPIRED:` notice, see Deny), commits (delete the record and the framework row, status `hitl_expired`; the dedupe record's `processed_at` is NOT set here), sends the spec's expiry notice only if the spec defines one (no model reply from this step), then handles the dequeued message as a new turn (inference). If `from_pending` raises (unreadable context after an edit or an upgrade), the same commit goes through the repository: `append_turn_record` writes the notice. `requested_at` is the time the worker sent the approval prompt. Expiry is evaluated when the next message for the session is dequeued (intended; a sweep is optional).
  3. If an approval is pending and not expired: parse the message (or the approver's reply) into a decision (builder below) and RESUME. Right before a resume that can run tools (approve, edit, deny-and-continue), commit `resume_started` = true and status `running` on the record in one write; a deny-ends-turn or `expire` resume never sets the flag. Otherwise start a NEW turn: turn-start repair (Caps), then status `running`. Both use ONE canonical call:
     ```python
     remaining = WALL_CLOCK - elapsed_s            # new turn: elapsed_s = 0; resume: the record's elapsed_s
     turn = TurnState(turn_id=turn_id, approval_id=aid, prior=prior, steps=n_steps, tool_calls_requested=n_calls,
                      tokens_in=ti, tokens_out=to, deadline=time.monotonic() + remaining)  # new turn: aid None, zeros
     token = TURN.set(turn)                        # hooks, provider and adapter read it; to_thread copies the context
     try:
         async with asyncio.timeout(remaining + GRACE):        # outer wall clock (see Caps)
             if resumed:
                 # resume_started and status `running` were committed on the record just before this block (G8)
                 flow = ChatFlow.from_pending(session_key, persistence=persistence, tracing=False, suppress_flow_events=True)
                 result = await asyncio.to_thread(flow.resume, decision.feedback)  # "approve", "deny: <reason>", "edit: <json>", "expire"
             else:
                 flow = ChatFlow(persistence=persistence, tracing=False, suppress_flow_events=True)
                 result = await asyncio.to_thread(flow.handle_turn, user_text, session_id=session_key)
     except HookAborted: ...                       # outcome mapping under Caps
     finally:
         turn.fenced = True
         TURN.reset(token)
     paused = isinstance(result, HumanFeedbackPending)
     ```
     `resume()` raises inside a running event loop, so it runs in a thread. `asyncio.timeout` needs Python 3.11 or later and the package supports 3.10, so on 3.10 use `asyncio.wait_for`. The reply of a finished run is the last assistant message in `flow.state.messages`.
  4. Post-run, in this order (commit order): the transaction (b), send (c), ack (d), under Sessions and state. On a pause the worker builds the approval prompt from the stored `calls`, never from model text.
- Decision value, built by the worker's single decision builder (the eval runner uses it too). The feedback string is generated from the parsed decision, never the approver's raw text: approve -> `"approve"` (runs every pending call); deny -> `"deny: <reason>"` (trimmed, length-capped; model-visible only when the spec lets the model continue); edit -> `"edit: <json>"`, only when exactly one call is pending and the arguments validate against that tool's `args_schema` (rejected when the spec has no edit outcome); expire -> `"expire"`, issued only by step 2a. One approve or deny reply applies to every pending call (design choice, inference); the listener treats any other string as a deny (fail closed). A message that does not parse as a decision keeps the approval pending: neither `resume` nor `handle_turn` is called and the worker replies with the spec's pending-approval prompt (or denies, if the spec says so); interpreting free text is the builder's job, never the framework's.
- Approved-call execution (`apply_decision`), for each pending call in order: (1) check `turn.deadline` and `turn.fenced` BEFORE the call; if either is past, stop, set `turn.exit = "wall_clock"` and raise `HookAborted` (the remaining calls keep their placeholder and the failure reply goes out); (2) parse the stored arguments as the executor does (`json.loads` for a string, a dict as is: `parse_tool_call_args`, `crewai/src/crewai/utilities/agent_utils.py`); (3) `token = IDEMPOTENCY_KEY.set("<approval_id>:<tool_call_id>")`, reset in a `finally` per call; (4) run `tool.run(**args)` directly and format the result as the executor does, `format_native_tool_output_for_agent(tool, raw)` (same file; a `ToolFailure` becomes `as_agent_message()`, a tool's own `format_output_for_agent` is honored); (5) append `(name, args)` to `turn.executed` and write the result over the blocked placeholder in `pending_tail`, matched by `tool_call_id`. An exception that escapes a body (the tools factory already wraps bodies) is caught here: the placeholder gets the spec's error observation, never the exception text, the call still counts as executed (it may have partly run), and the turn continues. The direct call skips the library's tool hooks and events, so the approved run is recorded in the own per-turn span as a child `tool.approved` span (name, call id, key, outcome); third-party instrumentors will not see it. After the loop the listener stores `continuation = history_messages + pending_tail` and routes to `continue_agent`: `run_agent` seeds `turn.seen_ids` with every id in `pending_tail` (so the continuation's rescan does not count or log those calls again), then calls `kickoff_async(continuation)`. The model sees its own tool calls with the real results and the original request unchanged (observed, spike 5(a); the whole captured transcript would double-wrap the request). The continuation is a new `kickoff` counted against the counters restored from the record, and a further gated call pauses again with a new `pause_id` and, after the transaction, a new `approval_id`.
- Deny.
  - If the spec says a deny ends the turn: no further tool executes and no model request is made. The construct that routes to the end is the `apply_decision` router label `turn_end`: the listener calls no tool and no `kickoff_async`, clears `pending_*`, appends ONE assistant message tagged with the turn id, and `end_turn` persists it. The worker still goes through `resume`, because the conversation lives in the Flow state and the framework row is consumed by the same path.
  - The appended text is "DENIED: <tool names> not run: <reason>"; when `prior` is set, an earlier resume may have run the tool, so it is "DENIED: <tool names>: outcome unknown - do not retry without the user" (and `EXPIRED:` for step 2a). The user-visible deny reply is the spec's text, sent by the worker (outcome `hitl_denied`).
  - If the spec lets the model continue after a deny: the listener writes "DENIED: <reason>" (or the outcome-unknown text when `prior` is set) over each blocked placeholder, runs no body, and routes to `continue_agent`; the resume sets `resume_started` like an approve. A denied call still counts as requested (counted when requested, see Caps). State which of the two applies in `build.md`.
- Idempotency key for a gated/destructive call: unique per APPROVED CALL, `"<approval_id>:<tool_call_id>"`. `approval_id` is the fresh UUID of the record written at that pause; `tool_call_id` is the model's own call id read from the stored tail (the hook context has none; Gemini-style responses get a synthesized `call_<object id>` in `extract_tool_call_info`, `crewai/src/crewai/utilities/agent_utils.py`, and the stored value is the one used). The destructive tool's backend call reads the key from `IDEMPOTENCY_KEY`; a destructive body that finds it unset refuses to run. Stable across redelivery: the record is deleted only in the post-run transaction and the no-op clear leaves the framework row, so a redelivered resume restores the same snapshot and ids (observed, spike 5(c)). A resume that pauses again writes a new record with a new id, so keys are never reused across pauses or turns (observed, spike 5(b)).
- Resume-started marker (G8): `prior` = the record's `resume_started`, captured at step 2; the deny/expiry notice text comes from `prior` ("outcome unknown - do not retry without the user" when set, never "was not run"). The flag is set (committed) ONLY right before a resume that can run tools, and deleted with the record.
- Approval is not an authorization boundary against an untrusted client: only an authenticated approver identity resolved by ingress may produce a decision, and each sensitive tool checks authorization in its own body. The record is consumed in the post-run transaction and the dedupe record absorbs a repeated channel message (inference); a redelivery after a crash is a deliberate re-run covered by the idempotency key. An approval id that travels through an untrusted channel is signed by ingress (HMAC over `approval_id`, session key and expiry) and verified; the stored record authorizes the resume (inference).
- Eval runner: the fixture's approvals enter the worker's turn handler as decision messages (Eval runner mapping); the runner never calls `handle_turn` or `resume` itself.
- Gate and pause spike (spike 4; binding spike; failure path: binding defect: STOP and report (build-guide Step 4)). ## Caps
- Step cap: CUSTOM, because the native `max_iter` is not the spec's unit, scope or exit. The runtime default is 25 although the docs say 20 (observed; https://docs.crewai.com/v1.15.24/en/concepts/agents.md ); the count goes up once per round of tool execution, not per model call (`increment_and_continue`, `crewai/src/crewai/experimental/agent_executor.py`); at the cap `force_final_answer` makes one more model call asking for a best answer and returns it as a NORMAL result with no exception or flag (observed: N tool rounds and N+1 model calls); and every `kickoff` restarts the count. So the model hook adds 1 per model request and raises `HookAborted` (exit `step_cap`) when the count exceeds `<spec step cap>`: a cap of N allows N model calls and the final answer is also a call. Unit conversion: the spec's step is one model request, 1:1 (inference); record it in `build.md`. `max_iter` is set to the same number only as a backstop: its forced best-answer call passes the model hook (observed), so the hook trips first. Library-made calls (context-window summarization, `respect_context_window` defaults to True) also pass the hook and count; router and feedback-classification calls are avoided by design. Provider classes call `_invoke_before_llm_call_hooks` once per request and it does nothing when the executor already dispatched (`crewai/src/crewai/llms/base_llm.py`); spike 7(f) confirms it against the real provider.
- Tool-call cap: own counter, no native per-run cap was found (https://docs.crewai.com/v1.15.24/en/concepts/tools.md ). Calls are counted by BATCH before any body runs. The executor appends the assistant tool-call message to `executor.messages` BEFORE it starts executing (`execute_native_tool`, `crewai/src/crewai/experimental/agent_executor.py`: `self.state.messages.append(assistant_message)` at line 1782, then the thread-pool submit at line 1798 or the sequential loop at line 1840; `messages` is a property over that state, line 317). So the model hook stores `turn.executor = ctx.executor` (only for a context that carries the executor; a direct model call such as a summarization has `executor` None), and the tool hook, under the lock, reads the newest assistant tool-call message of `turn.executor.messages`. The first time it sees a call id of that message it calls `count_batch(turn, message)`, which adds EVERY not-yet-seen id of the message to `turn.seen_ids` and `turn.tool_calls_requested` in one step (idempotent by call id; both hooks share it). If the total exceeds `<spec tool-call cap>`, it sets `turn.exit = "tool_call_cap"` and blocks every call of the batch, so none of an over-cap batch runs (observed, spike 7(c)). The model hook rescans `executor.messages` with the same `count_batch` as a backstop, because a malformed call (unparseable arguments) never reaches the tool hook (observed), and a trip found there raises `HookAborted` before the model is asked; the scan is also the trajectory source. Parallel execution (a thread pool of up to 8 when no tool has `result_as_answer` or `max_usage_count`, `_should_parallelize_native_tool_calls`) therefore cannot overshoot. Denied, gated and unknown-tool calls count. If the newest assistant message cannot be read (inference: a library change), the hook counts that one call alone and spike 7 fails the build.
- Both caps are PER TURN: a new turn starts `TurnState` at zero; a resume restores `steps`, `tool_calls_requested`, `elapsed_s` and token totals from the record (the framework's own counter restarts on every `kickoff`, so nothing is carried by CrewAI). Counters reach the record through `context.metadata`, so even an orphan record restores them.
- Both exits map to the spec's single failure reply and a cap outcome: a `HookAborted` whose `turn.exit` is `step_cap`, `tool_call_cap` or `wall_clock` -> that outcome; any other exception -> `error` (also the failure reply). The exception text is never sent to the user. The exception reaches the worker unwrapped (observed); the framework also logs it at error level ("Error executing listener ..."), also for a plain pause, so alerts must not key on that line.
- `harness_condition.force_step_cap`: a `ScriptedLLM` with exactly `<step cap>` steps, each a single safe tool call and no final answer, and the tool-call cap above the step cap; the test asserts `HookAborted` with exit `step_cap` and `len(double.calls) == <step cap>`. A tool-cap case does the reverse. `tool_always_errors` = the tool's injected BACKEND double raises and the real tool catches it and returns the spec's error observation (build-guide Step 5); the tool surface never changes. A body that lets the exception escape is shown to the model as `Error executing tool: <exception text>` (`agent_executor.py`), leaking internals and inviting a retry, so the tools factory wraps every body.
- Wall-clock cap: the budget is per TURN, resume time included. The record stores `elapsed_s` at each pause and a resume gets the remainder (the wait for the approver is not counted; inference); a new turn gets the full limit. Enforcement is cooperative: both hooks check `turn.deadline` on every model request and every tool call (exit `wall_clock`), `apply_decision` checks it before each approved call, and the worker wraps the thread in `asyncio.timeout(remaining + GRACE)` with `GRACE` = the `LLM` timeout plus 5 seconds, recorded in `build.md`. A thread cannot be cancelled, so on the outer timeout the worker sets `turn.fenced`: the adapter then refuses every write (an abandoned run cannot store an exchange after the failure reply went out) and the thread stops at its next hook call. A call in flight is bounded only by its own timeout: set `timeout=` on the `LLM` (https://docs.crewai.com/v1.15.24/en/concepts/llms.md ) and in every tool body. Whether a running body stops when its turn is abandoned is unverified; spike 8 measures it. An in-flight destructive body is covered by the idempotency key.
- Repair of aborted turns, at TURN START and only when no approval is pending (idempotent, survives a crash): read the latest `turns` row. Status `ok`, `hitl_denied`, `hitl_expired` or `awaiting_approval` -> nothing. Status `running` whose `turn_id` tags the last stored message -> the turn committed: worker step 1b already finished transaction (b) and nothing is written. Status `running`, `step_cap`, `tool_call_cap`, `wall_clock` or `error`, or no row while a stored conversation exists -> nothing was stored although tools may have run: `append_turn_record(session_key, turn_id, ...)` appends one user-role message `[agent-notice turn <turn_id>] The user's previous message ("<request_text>") was not answered: the turn was interrupted and its tools may have run. Outcome unknown - do not retry without the user.` to the stored conversation unless the tail already holds that notice for that turn id. The user role is used because every provider route accepts it (inference; spike 9). Only then write status `running`. Every repair says "outcome unknown", never "not executed". `append_turn_record` edits the newest `flow_states` JSON, so the message shape (`role`, `content`, `name`, `tool_call_id`, `tool_calls`, `files`, `metadata`) is pinned to 1.15.24; spike 8 checks the next turn's first model request contains the notice. No dangling-call repair is needed: `state.messages` is text only, so an AI message with tool calls lacking results cannot arise; spike 8 asserts it after every exit.
- Abort and repair spike (spike 8; binding spike; failure path: binding defect: STOP and report (build-guide Step 4)). Pass tests: (a) a wall-clock abort during a slow tool: failure reply with outcome `wall_clock`, a write by the abandoned thread raises, nothing is stored, the next new turn writes the notice once and succeeds against the real provider with a reply showing it was told the outcome is unknown; record whether the body kept running; (b) a tool that raises its backend error returns the spec's error observation and the turn ends normally; an exception made to escape a body (in the agent loop and in the approved-call path) is shown to the model as an error observation and the turn continues, and the exception text never reaches the user; (c) kill the worker during a tool, run the repair twice: exactly one notice; (d) kill the worker between the pause and the transaction: step 2 finds the row with no record, writes a fresh one, and the approval can be answered; (e) kill the worker after the terminal step and before transaction (b): the redelivery finds the tagged message, finishes (b) and does not re-run the turn; (f) after each cap exit and abort above, the stored `messages` hold no `tool_calls` or `tool` entry and a follow-up turn succeeds against the real provider.
- Cap spike (spike 7; binding spike; failure path: binding defect: STOP and report (build-guide Step 4)). Pass tests: (a) tool cap 2: one destructive call, pause, approve, the model then requests 2 more: the third cumulative call is blocked, `HookAborted` with exit `tool_call_cap` reaches the worker, no body past the cap ran; (b) step cap N: exactly N model requests then exit `step_cap`, the total across a pause is still N (`len(double.calls)`), and with `max_iter` equal to N no best-answer text is returned; (c) 3 parallel safe calls under cap 2: NONE executes and the turn ends with `tool_call_cap`; (d) both counters are 0 at the start of the next new turn; (e) both exceptions reach the worker as `HookAborted` with `turn.exit` set; (f) with the real provider the number of model-hook calls equals the number of provider requests; (g) a malformed call is counted by the rescan; (h) a pause in the turn that reaches the cap, approve: the approved tool runs, then the next model request trips the cap and a follow-up turn succeeds; (i) the executor's assistant message is readable at the first tool-hook call of a batch (fails if a library change moves the append).

## Eval runner mapping
- Runner = worker: the eval runner drives the worker's single turn handler (dequeue logic, pending check, expiry, repair, resume-or-end, cap mapping, commit order) against an in-memory repository and an in-memory `FlowPersistence` subclass (the same six methods; it passes spike 1's contract test), never `handle_turn` or `kickoff` directly. Fixture messages and approvals enter as queue messages; the expiry clock is injected; the factory is called once per test with that persistence, so the cross-instance resume path runs. `model_factory` returns the same `ScriptedLLM` on every call, so the script continues across the resume.
- Model double: a custom `BaseLLM` subclass (the documented way: https://docs.crewai.com/v1.15.24/en/learn/custom-llm.md ), `ScriptedLLM(steps)`. A step is a string (the final answer) or a list of tool-call dicts `{"id", "type": "function", "function": {"name", "arguments": <json string>}}` with a unique `id` per call; `supports_function_calling()` returns True; `call()` accepts the extra keywords `from_task`, `from_agent`, `response_model` and `**kwargs` the executor passes and calls `self._invoke_before_llm_call_hooks(messages, from_agent)` first, as the provider classes do, so the hooks behave as in production (the upstream stub in the test file cited under HITL gate does the same). It records every request and has `assert_complete()`; it replaces only the model.
- Capture source: `TurnState`, filled by the hooks and `apply_decision`, read by the runner after each run. A turn that pauses has several runs, and the runner joins that turn's per-run `requested` and `executed` lists in order.
  - Trajectory = the REQUESTED calls: `(name, arguments)` of every assistant tool call as `count_batch` sees it in `executor.messages`, in the model's own order, including malformed, cap-blocked and gate-paused calls (observed: 4 requested, 3 seen by the tool hook). Each call id is logged once: the continuation run's `seen_ids` is seeded from `pending_tail`.
  - `forbidden` is checked against the EXECUTED calls plus the reply text (`skills/build/references/adapter-bindings.md`). The source of truth for executed is the tool wrapper: it records `(tool name, args, call id)` into the turn's executed list at body entry, AFTER argument validation and immediately before the body runs, so a refusal (unknown tool, invalid args, cap-blocked, denied, expired) never reaches it; executed = a tool body actually ran, whether it succeeded or raised. One rule, no per-case guessing.
- The PIPELINE runner implements EXACT, IN_ORDER and ANY_ORDER itself over the trajectory list, with `args_subset` matching (golden-format: expected args must be a subset of actual args; never full-argument equality). `crewai test` is never used: it prints task scores from 1 to 10, the page says the only provider available is OpenAI, and it describes no trajectories, LLM mocking or golden cases (https://docs.crewai.com/v1.15.24/en/concepts/testing.md ). The `crewai eval` command in the 1.15.24 release notes was not evaluated and is not used (unverified). pass^k is computed by the pipeline runner from its own per-case results.
- Approvals in a case: the fixture's approvals enter the worker handler as decision messages and are answered by the worker's decision builder. `harness_condition.force_step_cap` and `tool_always_errors` are under Caps.
- Tool-surface preflight: the eval runner and a permanent CI unit test assert that the FIRST model request's tool names equal the spec's tool set (plus any built-in kept on purpose, each with its reason in `build.md`; this binding keeps none). Capture source: `ScriptedLLM.calls[0]` records the `tools` argument of the first `call()` (a list of `{"type": "function", "function": {"name": ...}}`) and the preflight reads each `function.name`; the double replaces only the model, so it does not change the surface (observed: exactly the agent's tools, with delegation off). MCP tool names count under their prefixed form. Negative control (the surface is filtered by `create_static_tool_filter`): a fake Streamable HTTP MCP server exposes one extra tool outside the spec; with the filter the preflight passes, and a second run with the filter removed MUST fail on the extra prefixed name (observed with `mcps=`: `127_0_0_1_8765_mcp_echo` only, then `..._wipe` too). An unreachable MCP server is skipped without an error (docs), so a missing spec tool also fails the preflight.
- Eval double spike (spike 11; binding spike; failure path: binding defect: STOP and report (build-guide Step 4)): the double drives a full pause, resume and finish through the worker handler on the in-memory persistence and on the real adapter with the same trajectory, and the preflight and its negative control pass.

The adapter resolves the configured servers into tool objects (same static filter) before the Flow is built and passes them in `tools`, so the SAME objects serve `Agent(tools=...)` and `apply_decision`. The resolving call is the public `Agent.get_mcp_tools(mcps)`, which `kickoff` itself calls and which delegates to `MCPToolResolver.resolve` (`crewai/src/crewai/agent/core.py`, `get_mcp_tools`; `crewai/src/crewai/mcp/tool_resolver.py`); using it outside `kickoff`, and the lifetime of the MCP connections it opens (the resolver has a `cleanup()`), are inference. Names the model and the hook see are the sanitized server name plus the tool name (observed with `mcps=`: `127_0_0_1_8765_mcp_echo` for `http://127.0.0.1:8765/mcp`; a stdio server gave a truncated, hashed name), so use Streamable HTTP and key the tier table by the prefixed names recorded by the preflight; a name missing from the table is destructive. That the prefixed names survive the adapter-resolved path, and that an MCP tool object runs through `tool.run(**args)`, is unverified; spike 13. Only MCP tools are supported, not prompts or resources (research file, citing the same page; unverified here).
  - MCP spike (spike 13; binding spike; failure path: binding defect: STOP and report (build-guide Step 4)): the resolution call (`Agent.get_mcp_tools`) outside `kickoff` returns the filtered tool objects and its connections stay usable until `apply_decision` runs; the filtered tool names appear in the first model request under their prefixed names, a destructive MCP tool pauses, the pause serializes, and the resume in a new process with the same configuration runs it once with the key; a stale tier table (renamed URL) pauses instead of running.
- MCP serving: not documented (unverified); not part of this binding unless the design asks for it, and then routed through the ingress queue so gate and caps still hold (inference).
